# 面试专题回答：个人贡献与架构取舍

本文覆盖 [`question-checklist.md`](question-checklist.md) 中第 10 个专题和三分钟开场题。
团队规模、个人提交归属和亲历故障无法由当前仓库唯一确认。为遵守“不虚构”原则，相关问题
保留明确的事实边界与待本人补充项，不生成看似完整但无法经受追问的经历。

## 1. 项目有多少人，你负责哪些模块？

这是团队事实，当前简历只写“核心开发者”，仓库 contributor 列表也不能等价为实际项目人数，
所以我不会从 Git 作者数猜团队规模。

我会按真实经历回答为：“项目实际核心协作人数是 `[本人补充]`。我负责 `[本人主导的模块]`，
参与 `[共同实现的模块]`，只接入或维护 `[外部协议/官方 harness]`。”每一项都准备对应代码、测试、
设计讨论或实验记录；在补齐前不能把 Runtime 到 Benchmark 的全部代码都说成个人完成。

## 2. 哪些核心设计由你提出，哪些是共同决策？

当前代码能确认的核心设计包括显式 Agent Loop、项目自有 Message/Event/State、完整历史与 Active
Context 分离、统一 AgentTool、Workflow 复用普通 Runtime，以及 Suite/Backend/Store 正交。
但代码不能证明这些分别由谁提出。

我的最终回答必须逐项标注“我提出并推动”“共同评审后落地”或“沿用外部协议并负责接入”，并举出
至少一个被否决的替代方案。没有本人证据前，我不会把所有架构选择统一说成“我设计的”。

## 3. 你写了哪些关键模块和测试？

这题应直接给文件或模块，而不是泛称“负责 Agent Infra”。候选范围可以从 `core.py`、`state.py`、
`compression/`、`mcp/`、`workflow/`、`trace/`、`evals/` 及对应 unit tests 中选择，但只能选择我
确实实现或主导修改的部分。

回答格式会是：“我直接实现了 `[文件/模块]`，对应不变量是 `[具体行为]`，验证用
`[测试文件或命令]`；`[另一个模块]` 是共同完成，我主要负责 `[边界]`。”当前材料不足以替我填
这些归属。

## 4. 最困难的线上或评测问题是什么？

项目明确是早期教学、实验和小团队项目，仓库没有 production 流量或线上事故记录，所以我不会
虚构“线上事故”。这题应该讲我真实处理过的评测问题。

当前文档能提供候选技术线索，例如 Rosetta 与 Docker BuildKit 的兼容问题、Provider raw 导致
长轨迹膨胀、SWE-bench patch/官方 scorer 对齐或远程 artifact 传输。但只有我亲自定位过的案例
才能按“现象—假设—证据—根因—修改—验证”展开；否则就明确说这是项目记录，不冒充个人经历。

## 5. 举一个你最初设计错误、后来推翻的方案

这必须来自真实决策记录，不能根据当前最终代码倒编故事。可核对的设计变化包括把 Provider raw
外置、把完整历史和 active context 分开，或把 Eval 拆成 Suite/Backend/Store，但是否是“我的
错误方案”需要本人确认。

合格回答需要说明旧方案在具体输入下违反了哪个不变量、如何用 Trace 或测试定位、最小改动是什么、
新方案付出什么代价。没有真实案例时，我宁可说“当前材料无法支持一个个人失败案例”。

## 6. 你做过最重要的一次性能或成功率优化是什么？

仓库能证明一些机制减少体积或提高可用性，例如 Trace raw 外置避免重复历史膨胀、并行独立工具
减少 I/O 等待、Context Compact 控制模型输入。但没有公开把其中某项与 Benchmark 增益做因果
绑定的个人实验。

因此我会选择自己真实测量过的一项，给出优化前后配置、指标和验证命令；若只有机制测试，就说
“优化了文件体积/控制流”，不说“提高成功率”。没有测量数据时不报百分比。

## 7. 如果删除你实现的一个机制，对成绩影响最大的是哪个？

没有组件级 Ablation，我不能把任何模块说成“对成绩影响最大”。从必要性看，模型—工具—结果的
基本闭环和外部验证是软件工程、终端任务成立的前提；但“必要”不等于能够量化对公开分数的贡献。

更准确的回答是：我会优先保留显式 Runtime、真实工具反馈和评分闭环，随后用相同预算的 remove-one
实验判断 Context、Task Tool 或 Workflow 的边际价值，而不是凭架构重要性代替数据。

## 8. 为什么没有直接使用成熟 Agent 框架？

因为这个项目的首要目标是让 Agent 系统容易理解、修改和教学。核心循环需要能直接看到模型调用、
工具执行、State 更新和停止条件；引入图执行引擎或隐式插件系统会让最想研究的部分先被框架隐藏。

代价是 Provider、工具、Trace 和 Eval 边界需要自己维护，也没有成熟框架的分布式 durable
execution。对于当前教学、实验和小团队范围，这是有意识的取舍；如果未来需要组织级调度，我会
把 durable scheduler 放在外围，而不是把教学核心先变复杂。

## 9. 这个项目目前最严重的技术债是什么？

我认为最明显的不是缺少更多 Workflow，而是运行恢复和生产治理还没有形成闭环。State/Event 能
重建观察状态，Submit/Reconcile 能恢复容器批次，但任意 Agent 在模型调用或有副作用工具中间崩溃
后，还没有通用 checkpoint、幂等执行和 exactly-once 语义。

同时公开 Benchmark 缺完整逐任务 artifacts、重复统计和组件消融，这使架构机制与结果之间的因果
证据不足。继续演进时，我会先补持久化/幂等边界和实验可审计性，而不是继续增加名词和策略数量。

## 10. 它距离生产可用还缺少哪些能力？

至少还缺多租户鉴权和隔离、统一 secret 管理、不可绕过的 policy enforcement、持久化队列与租约、
崩溃恢复和幂等副作用、全局资源/成本配额、完善脱敏与审计保留、Provider 降级，以及 SLO、告警和
容量治理。

当前已有超时、abort、Hook、Docker、Trace、远程 Backend 等构件，但它们不是 production 平台的
充分条件。项目 README 也明确定位为早期、教学研究和小团队实验，我不会声称它已承载生产流量。

## 11. 三分钟介绍 Simple Long Horizon Agent

Simple Long Horizon Agent 解决的是模型怎样在多个回合里持续操作真实环境，而不是只生成一次答案。
长任务的难点是环境会变化、上下文会膨胀、工具会失败，而且模型说“完成”不代表任务真的通过。

架构上我把系统分成五个清晰边界。Runtime 用显式 Agent Loop 串起模型决策、工具执行、状态更新和
停止；Message、Event、State 分别承载模型可见内容、运行事实和当前投影。Context 层把完整历史与
Active Context 分开，通过工具结果压缩、摘要、Compact 和 Recall 控制长期输入，同时保留原始证据。
Tool 层统一本地工具、MCP 和子 Agent；Workflow 在同一个 Runtime 上组合 Planner-Executor、
Reflection、Parallel 和 Goal Loop。Trace 和 Eval 层再把过程写成 JSONL，并用容器和官方 scorer
验证真实结果。

我在简历中的定位是核心开发者，但个人完成的模块和共同决策边界必须按真实经历补充为：
`[本人主导的设计与代码]`、`[共同完成部分]`、`[仅负责接入的外部系统]`。我不会用仓库整体能力
替代个人贡献证据。

当前公开结果是 SWE-bench Pro 63.20%、Terminal-Bench 2.1 77.53%、PostTrainBench 45.88%。
对应分数差是 4.10、12.83、1.91 个百分点；README 展示的相对提升是 6.94%、19.83%、4.34%。
这些是组合配置的端到端结果，没有组件消融，所以我不会把提升单独归因到 Compact、Task Tool 或
某个 Workflow。这个项目最核心的取舍，是保持控制流小而显式，让学习者能读懂、团队能修改、实验
能核对；代价是它还没有生产级分布式恢复和治理能力。
