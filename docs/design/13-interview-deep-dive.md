# 13. 面试深挖：证据边界与模拟回答

> 本篇用于面试准备，不为项目补造事实。每个主题都区分“已有事实”、
> “当前缺失”和“模拟回答”。其中模拟回答只是一套前后自洽的表达，不能当作
> 已完成实验、已实现能力或个人履历的证明。

## 1. 如何使用本篇

面试回答应先说明证据，再给结论。这里使用三个固定标签：

- **已有事实**：能由当前设计文档、实验说明或已发布结果直接支持；
- **当前缺失**：当前文档没有提供，因而不能对外声称已经证明；
- **模拟回答**：在不虚构数字和经历的前提下，演示如何回答追问。

| 主题 | 当前覆盖状态 | 面试结论 |
| --- | --- | --- |
| 定量实验 | 有三项总分和部分配置，缺少消融与不确定性分析 | 可以讲组合结果，不能做组件因果归因 |
| 性能与容量 | 有运行预算和并发配置，没有容量测量 | 可以讲已跑配置，不能承诺上限或 SLO |
| 安全威胁模型 | 有安全边界和责任，没有完整威胁模型 | 可以讲现有边界，不能宣称生产级沙箱 |
| 故障恢复 | 有分层错误处理，没有进程级一致性协议 | 可以讲可恢复故障，不能承诺无损续跑 |
| 方案演进 | 有当前取舍，没有可核验历史时间线 | 只能讲逻辑演进，需用历史记录校正 |
| 个人贡献 | 没有个人归属证据 | 只能提供模拟模板，必须由本人确认 |

“当前缺失”不等于项目没有做过任何实验。例如三项端到端 Benchmark 已经有
结果；缺失的是组件消融、置信区间、实例级案例等更细的归因材料。面试时应把
“系统组合有效”与“某个组件造成了多少提升”分开。

## 2. 定量实验与结果归因

### 2.1 已有事实

项目已经发布三项长周期任务结果：

| Benchmark | 模型与设置 | 项目结果 | Baseline | 绝对提升 | 相对提升 | 成本/任务 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| SWE-bench Pro | GPT-5.4, xHigh | 63.20% | 59.10% | 4.10 个百分点 | 6.94% | $7.7823 |
| Terminal-Bench 2.1 | GPT-5.3-Codex, xHigh | 77.53% | 64.70% | 12.83 个百分点 | 19.83% | $0.5667 |
| PostTrainBench | GPT-5.5, xHigh | 45.88% | 43.97% | 1.91 个百分点 | 4.34% | 未发布 |

这里的相对提升按 `(项目结果 - Baseline) / Baseline` 计算，而不是百分点差。
README 将 Baseline 定义为同模型、同任务预算下的对照，因此这些结果用于隔离
Agent 方案与基础模型能力，而不是比较不同模型。

已记录的运行条件还包括：

- SWE-bench Pro 使用 `ScaleAI/SWE-bench_Pro` test split；完整 split 为 731 个
  instance，deep manifest 含 47 条 multi-issue chain、261 个 chain instance；
- SWE-bench Pro 默认每个 instance 最多 250 个 solver turn，在 217,600 个估算
  Token 处 handoff，并保存 trajectory；
- SWE-bench Pro 的可配置变量包括 Agent flavor、Task Tool、压缩、handoff 和
  context window，但当前结果表没有给出这些变量的逐项消融结果；
- Terminal-Bench 2.1 使用 xHigh、每个 Agent 150 turn、10 个 trial 并发、
  timeout multiplier 3 和 Bash 300 秒最大命令超时；
- PostTrainBench 使用 Qwen3-4B-Base，在 AIME 2025、BFCL、GSM8K、HumanEval
  上按 PostTrainBench Lite 方法计算 normalized reward；
- Trace 中的模型调用保存 usage；成本分析将 usage 与 price book 组合，并能
  汇总子 Agent 调用。缺失 usage 或未知模型不能被记成精确的零成本。

### 2.2 当前缺失

当前文档没有提供：

- 多次重复运行、随机性控制、方差、置信区间或显著性检验；
- 按任务类别、难度或 chain 长度拆分的结果；
- 真实 instance id 对应的成功案例、失败案例和完整轨迹解读；
- Task Tool、handoff、compression、workflow 等组件的消融结果表；
- 三项结果采用同一成本口径的完整核算明细；
- PostTrainBench 的本地实验配置、逐子集分数和每任务成本；
- 能把总分提升因果归因到某一个组件的证据。

因此，已有结果可以支持“当前整套方案在这些配置下优于列出的 Baseline”，但
不能支持“Task Tool 单独贡献了 X 个百分点”或“handoff 是主要提升来源”。

### 2.3 模拟回答

> 实验不是没做，我们已经完成了三项端到端评测。SWE-bench Pro 是 63.20%，
> 相比 59.10% 的同模型同预算 Baseline，高 4.10 个百分点；Terminal-Bench
> 2.1 是 77.53%，高 12.83 个百分点；PostTrainBench 是 45.88%，高 1.91 个
> 百分点。前两项已发布的平均每任务成本分别是 7.7823 美元和 0.5667 美元。
>
> 我会把结论限制在“组合方案有效”。当前材料没有组件级消融，所以我不会把
> 提升硬归因给 Task Tool、handoff 或某个 workflow。设计上我有三个机制假设：
> 显式工具反馈减少不可观察的行动失败；handoff/压缩让长任务不因窗口耗尽而
> 中断；外部评分和轨迹让 Agent 可以验证并迭代。但机制合理不等于因果已经被
> 证明，真正的归因要固定模型、任务集合、预算和并发设置，只切换一个变量，
> 再报告 paired task 差异和置信区间。
>
> 现阶段我最愿意先补 Task Tool on/off、handoff on/off、compression 与 none
> 三组配对实验。它们已经是 runner 的显式变量，控制成本最低，也最能回答
> “提升到底来自架构还是更大的上下文/调用预算”。在这些数据出来前，我会把
> 提升来源称为假设，不称为实验结论。

### 2.4 常见追问

**问：6.94% 为什么不是 4.10%？**

答：4.10 是绝对百分点差；6.94% 是相对提升，即 `4.10 / 59.10`。报告中应
同时给出，避免把相对提升误读成百分点。

**问：一次总分能说明稳定吗？**

答：不能。确定性官方评分能说明这一批提交的结果，但模型生成仍有随机性。
没有重复运行和 paired bootstrap 之类的不确定性分析时，不应声称提升稳定到
某个置信水平。

**问：给一个典型失败案例。**

答：当前文档没有实例级案例，我不会临场编造 instance id。可以从 trajectory
按失败阶段分类，例如定位错误、工具执行失败、上下文丢失、验证不足和预算耗尽，
再选取真实轨迹复盘；在完成这一步之前，只能讲失败分类，不能讲具体案例事实。

## 3. 性能与容量

### 3.1 已有事实

设计已经定义若干资源和并发边界：

- Runtime 有 turn、Token、时间等停止预算，防止无限运行；
- 工具可在线程池并行；同组只要有 sequential 工具，就串行执行以保护共享资源；
- Eval 的每个 instance 使用独立 run directory，结果按输入顺序汇总；
- Docker/Remote Backend 通常按 instance 隔离并发；共享 workspace 的
  LocalProcess 应串行或提供 workspace factory；
- Terminal-Bench 的已记录运行配置是 10 个 trial 并发；
- SWE-bench Pro 的 runner 按 provider auth lane 分配 chain，长任务最多 250
  solver turn，并在 217,600 个估算 Token 处 handoff；
- Trace 保存工具和模型调用耗时，可作为后续性能分析的数据来源。

这些数字是运行配置或预算，不是系统容量上限。特别是“曾以 10 并发运行”不能
推出“最大稳定并发是 10”。

### 3.2 当前缺失

当前文档没有发布以下测量：

- 端到端延迟的 p50、p95、p99；
- 吞吐量、排队时间和不同并发下的扩展曲线；
- Runtime 自身 CPU、RSS、线程数和 artifact I/O 开销；
- Trace、压缩、Task Tool 对延迟和 Token 的增量成本；
- 最大稳定并发、Provider quota、容器槽位和磁盘容量构成的容量包络；
- 压力测试、长时间 soak test、性能回归阈值或 SLO。

因此项目目前不能给出“单机支持 N 个并发”或“p95 小于 N 秒”的可信承诺。

### 3.3 模拟回答

> 我们有可工作的并发配置，但还没有发布容量基准。Terminal-Bench 的 10 并发
> 证明这套运行链路在该配置下跑通过，不代表 10 是上限。这个系统的端到端时间
> 主要由模型调用、工具/容器任务和官方评分器组成，Runtime 调度只是其中一层；
> 不拆分 Span 就报一个总延迟，无法指导优化。
>
> 我会用 trajectory 的 Span 分四段测量：排队、模型、工具/环境、评分。然后在
> 固定任务集和模型配额下做 1、2、4、8、16 等阶梯并发，记录吞吐、p95、错误率、
> RSS、artifact 写入量和单位任务成本。容量上限定义为错误率和 p95 仍在目标内的
> 最大并发，而不是进程没有崩溃时的线程数。
>
> 架构上每个 Eval instance 的状态和目录隔离，适合横向扩容；真正的限制更可能
> 来自 Provider quota、容器槽位、磁盘和外部服务。这个判断目前是待验证假设。
> 在测量完成前，我不会对外承诺 SLA，只会给出已经跑过的具体配置。

### 3.4 常见追问

**问：你认为第一瓶颈是什么？**

答：长周期任务中模型和环境调用很可能占主导，但不能只凭直觉定论。先用 Span
算各阶段占比；若排队上升则看 quota/worker，若 Runtime CPU 或锁等待上升再优化
调度。优化顺序由测量决定。

**问：如何避免扩容后结果互相污染？**

答：保持每 instance 独立 State、run directory 和容器；只共享明确只读的配置，
对共享 workspace 的 LocalProcess 禁止无保护并发。结果汇总按输入身份，而不是
按完成顺序。

## 4. 安全威胁模型

### 4.1 已有事实

设计对安全边界已有明确但有限的承诺：

- 项目是教学和实验 Runtime，不是通用安全沙箱，也不宣称解决敌对多租户隔离；
- 工具入口需要做真实输入校验，JSON Schema 只帮助模型生成参数；
- 路径/cwd、命令权限、容器隔离、输入输出大小、认证、超时和高风险操作审批
  由工具与宿主环境共同承担；
- PRE_TOOL_USE Hook 可以阻止调用，高风险操作可以接宿主审批；
- task input 与私有 eval input 分离，gold 数据不能进入模型可见任务；
- 密钥由受控环境注入，不应写入 Profile、普通 Trace 或模型可见结果；
- Trace 可能包含源码、命令输出和 provider raw，共享场景需要最小化、脱敏、
  权限控制与保留策略。

### 4.2 当前缺失

当前没有一份完整威胁模型来定义：

- 受保护资产、攻击者能力和各信任边界；
- prompt injection、恶意仓库内容和恶意工具输出的处理策略；
- 任意命令、绝对路径、网络访问和数据外传的强制隔离；
- 密钥最小权限、轮换、日志脱敏和泄漏响应；
- MCP/依赖/容器镜像等供应链风险；
- 跨 run、跨用户或跨租户的数据隔离；
- DoS、Token/磁盘耗尽、超大输出和 fork bomb 等资源攻击；
- 安全测试、审计责任、漏洞响应流程与残余风险验收。

现有说明列出了责任，但不能等价为这些控制都已强制实现或经过攻击测试。

### 4.3 模拟回答

> 我把威胁模型分成四条边界：用户/任务到模型、模型到工具、Worker 到宿主、
> 运行产物到观察者。核心资产是宿主文件和命令权限、Provider 凭证、私有评分
> 数据、源码/任务内容以及结果完整性。主要不可信输入包括任务文本、仓库文件、
> 网页/MCP 返回和模型生成的工具参数。
>
> 当前设计已有几类控制：工具入口校验、超时和输出预算；高风险调用的 Hook gate；
> Eval 公私输入分离；密钥通过环境注入；每实例目录和容器隔离；Trace 与 Runtime
> 解耦。它们降低误操作和部分泄漏风险，但我不会把它描述成安全沙箱。模型仍可能
> 被 prompt injection 诱导调用 Bash 或读取敏感路径，宿主若给了过大权限，Runtime
> 自身不能补救。
>
> 如果进入不可信生产场景，我会把强控制放在模型之外：只挂载临时 workspace，
> 容器使用非 root、只读基础文件系统、网络 allowlist、最小权限短期凭证和资源
> quota；高风险命令需要结构化策略或人工批准；Trace 写入前做秘密扫描和分级访问。
> 同时用恶意仓库、prompt injection、路径逃逸和资源耗尽用例做回归。敌对多租户
> 仍不在当前项目承诺内，除非另建隔离控制面并完成安全评审。

### 4.4 威胁与回答边界

| 威胁 | 当前设计中的控制 | 仍需证明或补充 |
| --- | --- | --- |
| 工具参数畸形 | 入口校验、错误结果 | 路径/命令策略的统一强制执行 |
| Prompt injection | 可用 Hook 阻止高风险调用 | 内容信任标记、攻击测试、默认拒绝策略 |
| 密钥泄漏 | 环境注入、禁止进入 Profile/Trace | 最小权限、轮换、自动脱敏和响应流程 |
| 私有评分泄漏 | task/eval input 分离 | 端到端泄漏测试和产物审计 |
| 任意代码破坏宿主 | 可使用容器与权限约束 | 强制沙箱、网络策略和主机加固 |
| 资源耗尽 | turn/Token/超时/输出预算 | CPU、内存、进程、磁盘和网络 quota |
| Trace 数据泄漏 | 建议权限与保留策略 | 默认实现、脱敏覆盖率和删除验证 |

## 5. 故障恢复

### 5.1 已有事实

现有设计按故障所属边界处理恢复：

- Provider 暂时限流在 LLM 边界有限退避重试；最终错误向调用者传播；
- 模型生成非法工具调用时使用独立的有限修复重试；
- 工具异常、未知工具、阻止和超时应变成可配对的错误 ToolResult，使模型能修正；
- Compressor 失败时保留完整历史，不以损坏上下文继续；
- 外部 abort、预算耗尽、blocked、完成和评分失败使用不同终态语义；
- Eval 只重试基础设施或暂时异常，不把任务失败重跑成成功；
- 可脱离 Host 的 Backend 可用 submit manifest 和 reconcile 恢复协调进程；
- `result.json` 是终态事实；trajectory 增量写完整 JSONL 行，最终文件可原子重建；
- Agent 可以从调用者提供的 State 继续，但该能力不是跨进程持久化协议；
- SWE-bench Pro repo-chain runner 明确不支持中断 chain 原地恢复，需要新的 run id。

### 5.2 当前缺失

当前文档没有完整定义：

- 进程在模型调用、工具副作用或事件写入中途死亡时的 crash consistency；
- SESSION_END、AgentEnd 等终止事件在 fatal exception 下是否一定存在；
- 外部副作用工具的幂等键、去重、补偿和 exactly-once/at-least-once 语义；
- Agent State 的可靠快照、schema 迁移和自动重启入口；
- 部分写入、损坏 artifact、磁盘满和 writer 永久失败的恢复流程；
- RPO、RTO、最大重试次数的系统级标准和故障演练结果。

所以“可恢复错误有明确处理”是成立的；“任意进程崩溃后都能无损续跑”并不成立。

### 5.3 模拟回答

> 我们不是用一个全局 retry 包住所有失败，而是按边界分类。限流属于模型边界，
> 可以在没有新增假 transcript 的前提下有限重试；工具异常要转成 ToolResult，
> 因为这是一条模型应该看到并可能修正的事实；评分未通过是业务结果，不能当作
> 基础设施异常重跑；Host 协调进程退出时，可持久化 Backend 则依靠 manifest 和
> reconcile 找回运行。
>
> 当前恢复能力的边界也很明确：Agent resume 需要调用者重建 State 和外部资源，
> repo-chain 中断不支持原地续跑。对进程在副作用中途死亡的 exactly-once 语义，
> 当前没有完整协议，我不会声称无损恢复。尤其是 Edit、Bash 或外部 API 已执行、
> 结果事件尚未持久化时，盲目重试可能重复副作用。
>
> 要补齐这一层，我会先为副作用工具引入稳定 operation id 和幂等性声明：只读
> 操作可重放；幂等写操作按 id 去重；非幂等操作进入人工确认或补偿流程。State
> 在 turn 边界做版本化 checkpoint，恢复时先核对 artifact 和外部环境，再决定
> replay、skip 或 abort。最后用故障注入覆盖模型响应前后、工具执行前后、事件
> flush 前后，而不是只测正常 retry。

### 5.4 常见追问

**问：为什么不对所有异常自动重试？**

答：重试必须知道副作用边界。模型限流通常尚未改变外部环境，非幂等工具却可能
已经完成操作；统一重试会把一次故障变成重复修改。失败分类比重试次数更重要。

**问：恢复后如何保证 Trace 可信？**

答：保留原 run id、checkpoint id 和恢复原因，事件只追加，不改写既有事实；
重放或跳过都产生显式事件。当前文档尚未定义这套跨进程协议，因此这是设计方案，
不是现有能力。

## 6. 方案演进

### 6.1 已有事实

现有设计文档详细解释了当前边界和取舍，例如：

- 核心循环保持紧凑显式，不在重框架后隐藏行为；
- 使用项目自有 Message、Event 和 State，Provider 对象停留在适配边界；
- 完整历史、活跃上下文和模型可见上下文分离；
- 子 Agent 与 Workflow 复用普通 Agent run，并拥有独立 State；
- Trace 和 Eval 从 Event 事实派生，不反向控制 Runtime；
- 对象 Store、通用分布式调度和完整安全沙箱不是当前已实现目标。

这些材料说明“为什么是当前设计”，但没有按时间记录每一阶段由什么问题触发、
尝试过哪些替代方案、何时废弃以及由谁决策。

### 6.2 当前缺失

当前没有可核验的：

- 架构时间线、里程碑和关键变更日期；
- 早期方案、被否决方案及其运行数据；
- ADR/RFC、决策参与者和评审结论；
- 重构前后复杂度、可靠性或评测结果对比；
- 关键兼容性迁移和历史事故如何推动设计变化。

### 6.3 模拟回答：逻辑演进叙事

> 下面是根据当前架构反推的一条逻辑演进，不是已经核验的 Git 历史。
>
> 第一阶段先做一个可检查的单 Agent 循环，项目自己拥有 Message 和 State。目标是
> 让观察、模型决策、工具行动和反馈能从上到下读懂。第二阶段接入多 Provider 和
> 工具后，把 Runtime Message、LLM Message、Provider wire 分层，避免供应商对象
> 污染核心，也把工具失败变成模型可见结果。
>
> 第三阶段面对长任务，引入追加式 Event、活跃 ContextView、Compression 和
> Recall。关键取舍是不删除原始事实：压缩只是改变当前投影，精确信息仍可恢复。
> 第四阶段处理复杂任务时，没有另造一套多 Agent Runtime，而是让子 Agent 和
> Workflow 复用普通 run、隔离 State，通过显式结果组合。
>
> 第五阶段为了证明方案有效，把 Event 派生为 Trace、成本和 ModelTurn，再把 Suite、
> Backend、Store 和 Scorer 拆开，支持本地、容器和远程评测。我们刻意没有把对象
> Store、分布式调度或生产级沙箱塞进核心，因为它们会扩大教学 Runtime 的复杂度，
> 且当前需求可以在外围边界实现。
>
> 这条演进的主线不是“不断加功能”，而是每遇到新问题都保持一个稳定原则：核心
> 循环显式、外部细节停在边界、事实只记录一次、复杂能力通过组合获得。正式面试
> 前仍应结合 commit、PR 或 ADR 校正时间顺序和个人参与范围。

### 6.4 常见追问

**问：为什么不一开始就用成熟 Agent 框架？**

答：项目目标包含教学、可修改和可检查。框架可以减少接线代码，却可能把循环、
状态和 Provider 转换藏在隐式生命周期中。这里优先保留少量项目自有协议，再在
外围接入能力；代价是部分基础设施需要自行维护。

**问：哪个决策最难回退？**

答：项目自有 Message/Event 协议和追加式事实模型影响 Runtime、Trace、Workflow、
Eval 与导出，是高影响边界。具体 Provider、Tool 或压缩策略是可替换模块，回退
成本相对低。这是架构影响判断，不是历史变更成本的实测结论。

## 7. 个人贡献

### 7.1 当前缺失

设计文档和代码只能说明系统具有什么能力，不能证明某项工作由哪位个人完成。
当前没有作者职责表、PR 归属、评审记录、团队分工或个人复盘，因此不能从仓库
安全推断“我负责了哪些模块”或“某项指标提升由我个人贡献”。

下面给出一套完整模拟口径。它假设候选人是“核心架构与评测闭环负责人”，只是
面试演练，必须按真实经历删改后才能使用。

### 7.2 模拟回答：需本人确认

> 我在项目中的主责是把一个最小 Agent 循环扩展成可支持长任务、又能解释和评测
> 的系统。我的工作集中在三条线：第一，定义 Message、Event、State 与 Runtime
> 的边界，让模型调用和工具反馈形成显式循环；第二，设计 ContextView、压缩和
> Recall，使长任务控制窗口时不删除原始证据；第三，打通 Trace 到 Eval 的闭环，
> 让每次结果能关联模型配置、任务、轨迹、成本和官方评分。
>
> 我做的关键取舍是没有为长上下文、多 Agent 和评测各造一套运行时。子 Agent
> 复用普通 run 并隔离 State，Trace 从 Event 派生，Eval 通过 Suite、Backend 和
> Store 组合。这让核心仍可用 Fake Model 和 Fake Tool 做窄测试，也减少 Provider
> 与 Benchmark 细节对核心的侵入。
>
> 最难的问题是如何同时满足“窗口有限”和“证据可追溯”。如果直接截断历史，
> Debug 和 Recall 都失去依据；如果始终注入全量历史，长任务又无法继续。最后采用
> 完整历史不变、活跃索引可变、摘要带来源、Recall 有界恢复的方案。这个边界也让
> Trace 能同时解释原消息、压缩和后续恢复。
>
> 结果上，整套方案在三项 Benchmark 上分别达到 63.20%、77.53% 和 45.88%。
> 我会明确说这是团队和系统级结果，不把全部提升归到个人或单一模块，因为当前
> 没有组件消融。我的个人价值应由我实际负责的设计、实现、测试、实验运行和问题
> 复盘来证明，而不是只引用最终总分。
>
> 协作上，我会先约定跨模块协议和验收信号，再由不同模块实现者在边界内推进，
> 最后用 Fake 测试、架构检查、Trace 和官方评分收口。对于我没有直接负责的模型
> 能力或官方评分器，我会清楚说明依赖关系，不把外部成果包装成个人实现。

### 7.3 面试前必须替换的证据

使用上面的回答前，至少确认并替换：

- 自己真实主责、协作模块和未参与范围；
- 亲自做出的一个关键决策及当时的备选方案；
- 一项可定位到 PR、commit、文档、测试或实验记录的产出；
- 一个真实故障或失败实验，以及自己如何定位和修正；
- 自己实际运行、分析或复核过哪些 Benchmark；
- 团队结果与个人贡献的清楚分界。

如果这些证据无法补齐，应把“我主导”改成“我参与”，把模块所有权改成具体动作，
例如“我实现了某个边界的测试”或“我负责某次实验的配置和结果核验”。

## 8. 面试结论边界

当前材料足以支持以下结论：

1. 项目有三项已发布的端到端 Benchmark 结果，不应描述为“没有实验”；
2. 设计能解释长周期 Runtime、工具、上下文、组合、轨迹和评测如何协作；
3. 可恢复故障、安全责任和运行配置已有边界说明；
4. 组件因果归因、容量承诺、完整威胁模型、进程级无损恢复、真实演进历史和
   个人贡献仍缺少证据。

面对第 4 类问题，最可靠的回答结构是：先说已有证据能证明什么，再明确不能证明
什么，最后给出验证方案。面试官继续追问时，边界保持一致，不把方案说成现状，
不把机制假设说成实验结论。
