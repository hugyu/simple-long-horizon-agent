# 17. Agent 技术面试问题清单

仅根据你的简历描述
[`15-resume-project-description.md`](15-resume-project-description.md)，面试官会重点
验证三件事：

1. 这些系统是否真是你设计并实现的。
2. 你是否理解内部机制，而不只是会使用 Agent 术语。
3. Benchmark 提升是否可信、可归因、可复现。

**高概率考察方向**

### 1. Agent Runtime 与核心抽象

对应简历第 6-8 行。最高概率是让你从一次用户请求开始，完整讲清运行链路。

专题回答：
[`18-interview-answers-agent-runtime.md`](18-interview-answers-agent-runtime.md)

可能问题：

- 画一下 Runtime 的整体架构和一次 Turn 的完整数据流。
- 为什么选择显式 Agent Loop？它与工作流编排框架有什么区别？
- `Message` 和 `Event` 的核心区别是什么？`State` 在两者之上承担什么职责？
- 三种对象之间为什么需要分离，合并成一个结构有什么问题？
- Event 是否是 append-only？如果不是，哪些 Event 允许修改或丢弃？
- State 是可变对象、事件重放结果，还是持久化状态快照？
- 如果 State 可以由 Event 恢复，为什么还需要持久化 State？
- Tool Call 在协议里属于 Message 还是 Event？它在模型上下文和运行事实中是否需要两种表示？
- LLM Response 属于 Message 还是 Event？流式增量、规范化响应和最终消息分别如何记录？
- 模型调用、工具执行、上下文管理和停止控制的边界在哪里？
- Agent Loop 有哪些退出条件？如何避免无限循环？
- Agent 崩溃后如何 resume？恢复依赖 Event 重放、State 快照还是两者结合？
- 为了避免重复模型调用或重复执行有副作用的工具，resume 前必须持久化哪些信息？
- 你所说的“轻量级”如何衡量？
- 如果重新设计一次，你会保留和删除哪些抽象？

压力追问：

> 给你一块白板，不允许讲 Planner、Reflection 等名词，只用数据结构和伪代码实现最小 Agent Loop。

专题回答：

### 3. Context Engineering

对应第 9-11、29-30 行。这会是你简历最容易被深入追问的部分。

专题回答：
[`20-interview-answers-context-engineering.md`](20-interview-answers-context-engineering.md)

可能问题：

- “完整运行历史”和“模型活跃上下文”分别是什么？
- 为什么完整历史不能直接作为模型上下文？
- 活跃上下文由谁生成，在什么时候更新？
- 工具结果压缩、模型摘要和 Compact 有什么区别？
- Compact 的触发条件是什么：Token 阈值、Turn 数还是模型判断？
- 摘要本身可能遗漏信息，如何防止错误不断累积？
- 如何处理摘要中的事实冲突？
- 哪些内容绝对不能被压缩？
- 原始证据如何保存，摘要如何关联原始证据？
- 被 Compact 移出活跃上下文的信息以后如何定位并恢复？
- Recall 由谁触发：LLM、Runtime、Workflow，还是调用者？
- Recall 是由 LLM 主动调用工具，还是 Runtime 根据上下文缺口自动触发？两种方式如何取舍？
- Runtime 自动 Recall 时，如何判断模型缺少了哪段信息？
- Recall 使用关键词检索、语义检索、事件定位，还是结构化引用？
- Recall 的恢复粒度是什么：完整 Message、单次工具结果、Event、Span，还是其中的文本片段？
- Recall 粒度过大或过小分别会带来什么问题？
- Recall 返回内容后如何重新插入上下文？
- 如何防止模型不断 Recall，导致上下文重新膨胀？
- 上下文压缩到底降低了多少 Token？任务成功率是否下降？
- 如何设计实验，证明收益来自你的上下文机制？

关键场景题：

> Agent 在第 80 个 Turn 需要使用第 3 个 Turn 中工具输出的一行错误信息，但该内容已经被 Compact，你的系统如何恢复它？

### 6. Workflow 与完成判断

对应第 13-14、31-32 行。

可能问题：

- Planner-Executor、Reflection、Parallel、Goal Loop 分别适合什么任务？
- 它们是独立 Runtime，还是同一个 Runtime 上的策略？
- Workflow 状态放在哪里？
- Reflection 为什么可能有效？什么时候会产生反作用？
- Goal Loop 与普通 Agent Loop 的区别是什么？
- Agent 如何知道任务已经完成？完成信号由 LLM、工具、Workflow 还是外部验证器产生？
- 什么是“模型声明完成”，什么是“任务实际完成”？
- 仅依靠 LLM 输出 `done` 有什么问题？Runtime 为什么不能直接相信这一信号？
- 外部验证信号有哪些类型？
- 验证器本身不可靠怎么办？
- 一个 Agent 声称“任务完成”，但测试没有通过，Runtime 应该如何处理？
- 验证失败后如何记录失败事实、把反馈送回 Agent，并决定继续执行还是终止？
- 如何防止 Agent 为了通过验证器而投机？
- 没有明确验证器的开放任务如何停止？
- 最大 Turn 数只是防止失控的兜底，还是一种正常退出机制？
- 达到最大 Turn 时，应标记为任务完成、运行中止还是预算耗尽？
- 最大 Turn、预算耗尽和验证成功之间的优先级是什么？

核心场景题：

> Agent 输出 `done` 并声称代码已经修好，但外部测试没有通过。Runtime 如何拒绝这次
> 完成声明、记录验证结果、把失败反馈给 Agent，并在最大 Turn 限制内继续执行？

### 9. Benchmark 与结果可信度

这是最严格的方向，因为你给出了精确数字。

可能问题：

- 三个分数各自如何计算？
- Baseline 的具体定义是什么？
- Baseline 与实验组是否使用同一模型、Prompt、Token 和成本预算？
- 为什么用“百分点”而不是相对提升比例？
- 提升分别来自哪些机制？
- 做过哪些消融实验？
- 每项 Benchmark 跑了多少任务、几次重复？
- 是否存在随机误差或置信区间？
- 失败任务主要分为哪些类型？

- 是否排除模型升级、Prompt 修改和基础设施变化的影响？

你必须准备清楚，否则容易被判断为项目描述不严谨。

### 10. 个人贡献与架构取舍

“核心开发者”一定会被要求明确边界。

可能问题：

- 项目有多少人，你负责哪些模块？
- 哪些核心设计由你提出，哪些是共同决策？
- 你写了哪些关键模块和测试？
- 最困难的线上或评测问题是什么？
- 举一个你最初设计错误、后来推翻的方案。
- 你做过最重要的一次性能或成功率优化是什么？
- 如果删除你实现的一个机制，对成绩影响最大的是哪个？
- 为什么没有直接使用成熟 Agent 框架？
- 这个项目目前最严重的技术债是什么？
- 它距离生产可用还缺少哪些能力？

**最可能的开场题**

> 请你用 3 分钟介绍 Simple Long Horizon Agent。不要逐条复述简历，请从它解决的问题、核心架构、你个人完成的关键工作，以及可量化结果四个方面回答。

回答时建议严格控制为：

1. **问题**：长任务为什么比单轮调用困难。
2. **架构**：Runtime、Context、Tool、Workflow、Eval 五层。
3. **个人贡献**：明确到设计、编码和验证。
4. **结果**：说明分数、Baseline 口径及代价。
5. **取舍**：为什么采用轻量、显式的实现。

正式模拟面试第一题：

> 请你从一次用户任务进入系统开始，完整描述它经过 Agent Loop、模型调用、工具执行、状态更新、上下文整理，到最终停止的全过程。请同时说明 `Message`、`Event` 和 `State` 在每一步分别承担什么职责。
