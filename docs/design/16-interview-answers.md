# 16. Agent 项目面试问题与回答

本文保存第 14 篇面试问题地图中“项目定位与个人贡献”部分的 10 道开场问题及参考
回答。回答基于当前代码、设计文档和简历口径整理，面试时应替换其中需要个人经历
支持的内容，不要把设计目标或项目结果扩大为未经验证的结论。

## 1. 请用两分钟介绍这个项目，先讲它解决了什么问题、怎么解决、结果如何

**参考回答：**

> Simple Long Horizon Agent 是我从零设计和实现的一套轻量级长周期 Agent Runtime。
> 它解决的不是单轮问答，而是模型如何在真实环境中持续完成多步骤任务。
>
> 例如软件工程任务中，Agent 需要先理解目标，读取仓库，定位问题，修改文件，运行
> 测试，再根据测试结果继续修正。这个过程需要模型、工具、环境状态和外部验证不断
> 交互，不能只依赖一次模型生成。
>
> 我的核心设计是一个显式的 Agent Runtime。Runtime 使用项目自己的 `Message`、
> `Event` 和 `State` 表达运行事实：模型负责决策，工具负责行动，工具结果进入下一轮
> 上下文，`State` 保留完整过程，`ContextView` 决定当前这一轮模型实际看到什么。
> 模型供应商的差异通过 Provider Adapter 隔离，复杂能力则在核心循环之外组合，例如
> 上下文压缩、Recall、Memory、Task Tool、Workflow、Trace 和 Eval。
>
> 在此基础上，我把同一套运行机制接入软件工程、终端任务和模型评测场景，并完成了
> SWE-bench Pro、Terminal-Bench 2.1 和 PostTrainBench 的评测。当前记录的结果分别是
> 63.20%、77.53% 和 45.88%，相对同模型、同任务预算的 Baseline 提升分别为
> 6.94%、19.83% 和 4.34%。
>
> 这里需要谨慎说明：这些结果证明的是整套 Agent 配置在对应评测口径下的组合效果。
> 当前没有足够的组件消融数据，所以不能把提升单独归因于压缩、Task Tool 或某一个
> Workflow。

**回答重点：**

- 先讲长周期任务，不要先罗列模块；
- 明确模型负责决策，Runtime 负责持续推进；
- 结果后主动说明归因边界。

## 2. 你说的“长周期任务”具体指什么？请用一个真实任务说明它为什么不能由一次模型调用完成

**参考回答：**

> 我这里说的长周期，不单纯是耗时长，也不单纯是上下文长，而是任务需要多个连续
> 步骤，并且后续步骤依赖前面在真实环境中获得的新信息。
>
> 以修复一个代码仓库中的 Bug 为例，Agent 可能需要：
>
> 1. 理解任务目标；
> 2. 查看目录和相关文件；
> 3. 搜索错误来源；
> 4. 修改代码；
> 5. 运行测试；
> 6. 根据测试失败信息继续修改；
> 7. 最后由测试或评分器确认是否完成。
>
> 一次模型调用最多只能生成一个决策或一组工具调用，它不知道工具执行后的真实结果，
> 也不能根据尚未发生的测试结果修正方案。真正的任务过程是：
>
> ```text
> 理解目标 → 观察环境 → 决策 → 执行动作 → 获取结果 → 检查目标 → 继续或停止
> ```
>
> 所以长周期 Agent 的核心不是简单地多调用几次模型，而是要维护连续状态、把工具
> 结果正确反馈给下一轮、控制上下文规模，并且区分模型认为完成和外部目标真正完成。
>
> 在当前实现中，`Agent.run()` 通过显式循环推进这些步骤；每一轮都会基于当前 `State`
> 构建 `ContextView`，调用模型，记录响应，执行工具，并把工具结果写回 State。对于
> 需要外部验证的任务，还可以由 Goal Loop 在模型输出 `final` 后继续检查测试或工作区
> 状态。

**关键澄清：**

> “长周期”最好定义为：多步骤、状态持续演进、后续决策依赖环境反馈，并且需要外部
> 完成检查的任务。

## 3. 这个项目最核心的设计是什么？如果只能保留一个部分，你保留什么？

**参考回答：**

> 我认为最核心的设计是显式、可观察的 Agent Runtime，而不是某一个具体的压缩策略或
> Workflow。
>
> 它把一次 Agent 运行拆成几个清楚的责任：
>
> - `Agent` 保存模型生成函数、工具、Prompt、上下文策略和 Hook；
> - `State` 保存一次运行中追加的事实；
> - `Message` 表达任务、模型输出和工具反馈；
> - `ContextView` 决定当前模型可见的内容；
> - `run()` 按固定顺序推进模型调用、工具执行、事件记录和停止判断。
>
> 如果只能保留一个部分，我会保留“显式循环加 State/Event 协议”这个最小核心。因为
> 没有它，压缩、Memory、Workflow 和 Trace 都只能是外围功能，无法共享稳定的运行语义。
>
> 具体来说，每一轮大致是：
>
> ```text
> 检查中止
> → 尝试上下文压缩
> → 构建 ContextView
> → 调用模型
> → 记录模型响应
> → 记录 Assistant Message
> → 执行 ToolCall
> → 写入 ToolResult
> → 判断是否停止
> ```
>
> 这个设计的价值在于运行过程不是黑盒。调用者可以消费 Event Stream 来实时观察，
> State 可以保留完整事实，Trace 可以从 Event 派生，Workflow 和子 Agent 也可以复用
> 同一个 Runtime，而不需要再实现第二套循环。

**补充说明：**

> 我保留的不是一个孤立的 `while` 循环，而是“显式循环 + 项目自有 State/Event 数据
> 协议”。循环负责推进，协议负责让状态、工具结果、停止原因和观察证据保持一致。

## 4. 这个项目和一个带工具的普通 ReAct Agent，关键差异在哪里？

**参考回答：**

> 从推理形式上看，两者并不是完全不同的算法。普通 ReAct 也是让模型在“思考、调用
> 工具、读取结果、继续决策”之间循环。所以我不会声称这个项目发明了新的 Agent 推理
> 范式。
>
> 一个简单的带工具 ReAct Agent 可能只需要：
>
> ```text
> 调模型 → 如果有工具调用就执行 → 把结果放回消息 → 再调模型
> ```
>
> 当前项目进一步把这个过程结构化了：
>
> 1. **运行事实独立保存**：`Message` 表达对话和工具反馈，`Event` 表达模型请求、
>    工具生命周期、停止和压缩等事实，`State` 保存完整运行状态；
> 2. **上下文不等于完整历史**：完整历史继续保留，但每一轮通过 `ContextView` 决定
>    模型实际看到什么，并支持压缩和 Recall；
> 3. **停止语义明确**：区分正常完成、最大回合数、用户中止和工具主动终止；
> 4. **工具边界统一**：成功、失败、超时、部分成功和主动终止都有明确结果语义；
> 5. **模型供应商隔离**：Runtime 不直接依赖 OpenAI 或 Anthropic 的 SDK 对象；
> 6. **复杂能力复用同一个核心循环**：Task Tool、Workflow 和子 Agent 都建立在普通
>    Agent Run 之上；
> 7. **可以验证而不只是返回文本**：Trace 记录模型实际输入、工具结果、停止原因和
>    成本，Eval 再通过外部评分器检查最终产物。
>
> 所以项目的重点不是让 ReAct 概念更复杂，而是把一个隐含的循环变成可观察、可替换、
> 可验证并可以扩展到长任务的运行基础。
>
> 一句话总结：普通 ReAct 主要描述“模型如何行动”，这个项目进一步解决“运行事实如何
> 保存、上下文如何管理、错误如何处理、任务如何验证和结果如何复现”。
>
> 如果只比较最小的单 Agent 工具调用循环，当前项目和 ReAct 在基本控制流上是相通的；
> 差异主要体现在 Runtime 工程化，而不是基础推理范式。

## 5. 为什么选择自己实现 Runtime，而不是使用 LangGraph、AutoGen 或其他现成框架？

**参考回答：**

> 选择自己实现，首先是因为这个项目的目标不是快速拼装一个应用，而是理解和研究
> Agent Runtime 本身。
>
> 我需要直接控制几个核心边界：
>
> - 模型调用、工具执行和 State 如何连接；
> - Message、Event 和 State 的语义如何定义；
> - 当前模型实际看到了哪些上下文；
> - 压缩如何改变活跃视图但不删除原始事实；
> - 子 Agent 如何复用同一个 Runtime；
> - Trace 和 Eval 如何从运行事实中派生；
> - 不同 Provider 的协议差异在哪里转换。
>
> 如果直接使用大型框架，当然可以更快得到一个能运行的 Agent，但很多关键语义会被
> 框架的节点、回调、状态存储或配置机制包起来。对于这个项目而言，这会削弱可读性，
> 也不利于验证最小实现和做定制实验。
>
> 但我并不是认为现成框架没有价值。对于生产系统，我会根据团队已有基础设施、持久化、
> 调度、可观测性和运维需求评估是否使用框架。当前项目选择自研的范围也很明确：自研
> 的是核心 Runtime 和项目自己的协议，不是重新实现模型服务、Docker 或 Benchmark
> 评分器。
>
> 这样做的收益是核心机制可直接阅读和替换；代价是需要自己承担协议设计、边界测试、
> 错误处理和后续维护成本。

**设计取舍：**

| 选择自研的收益 | 代价 |
| --- | --- |
| 完全理解核心循环 | 需要自己维护 Runtime |
| 可以定义稳定的 Message/Event/State 协议 | 协议设计和兼容性由自己负责 |
| 方便做 Context、Trace、Eval 实验 | 初期开发速度可能较慢 |
| Provider、工具和 Workflow 边界清楚 | 需要补齐更多工程细节 |

**边界表述：**

> 当前项目的目标决定了自研核心 Runtime；如果目标改成快速交付生产应用，技术选择会
> 重新评估。

## 6. “轻量级”体现在哪些具体边界？它明确不解决什么问题？

**参考回答：**

> 这里的“轻量级”不是指功能少，而是指核心机制小、依赖方向简单、复杂能力不进入
> 核心循环，而且每一层复杂度都能解释它解决的问题。
>
> 具体体现在几个方面：
>
> 1. **核心循环单一**：所有普通 Agent、子 Agent 和 Workflow 最终复用同一个 `run()`
>    机制，没有多套互相不兼容的 Runtime；
> 2. **数据协议自有且简单**：核心围绕 `Message`、`Event`、`State` 和 `ContextView`
>    工作，不把 Provider SDK 对象直接带入核心状态；
> 3. **外围能力可选**：Memory、Skills、MCP、Workflow、Trace 和 Eval 通过工具、Hook、
>    初始化器或组合层接入，最小 Agent 不必依赖它们；
> 4. **依赖方向清楚**：核心不反向依赖 Workflow、Memory、MCP、Trace 或具体
>    Benchmark；
> 5. **运行方式直接**：`Agent.run()` 返回 State 和惰性 Event Stream，调用者可以直接
>    消费、观察和检查；
> 6. **没有隐藏式插件系统**：能力通过明确的 Builder、Tool、Hook、Session 和
>    Workflow 边界进入运行。
>
> 它明确不解决以下问题：
>
> - 不保证模型始终正确；
> - 不等同于完整的操作系统级安全沙箱；
> - 不提供生产级多租户权限和密钥治理；
> - 不以大规模分布式 Agent 调度为目标；
> - 不替代 Docker、Provider 服务或官方 Benchmark 评分器；
> - 不承诺跨进程恢复所有带副作用的工具执行；
> - 不把所有历史都自动变成可靠的永久 Memory；
> - 不证明某一个组件单独带来了 Benchmark 提升；
> - 不要求每个任务同时使用压缩、Memory、Workflow、MCP 和容器。
>
> 所以它更准确的定位是：一个能进入真实多步骤任务、同时适合学习、架构实验和小规模
> 评测的 Agent 基础，而不是完整的生产级 Agent 平台。
>
> 我刻意把“核心运行机制”和“生产系统能力”分开：当前项目把 Agent 如何持续行动、
> 记录、观察和评测讲清楚，但没有把分布式调度、多租户治理和完整安全平台伪装成已经
> 解决的问题。

## 8. 你亲自设计和实现了哪些部分？哪些是接入已有 SDK、Benchmark Harness 或开源方案？

**参考回答：**

> 我会把工作分成“项目自有设计与实现”和“外部能力接入”两部分。
>
> 项目自有的部分主要是 Runtime 的控制流和数据语义，包括：
>
> 1. 设计显式 Agent 循环，让模型调用、工具执行、上下文构建和停止判断按固定顺序推进；
> 2. 设计 `Message`、`Event`、`State` 这套项目自己的运行协议；
> 3. 把完整运行历史和当前模型可见上下文分开，通过 `ContextView` 做投影；
> 4. 设计压缩、Recall、Skills、Memory 和 Handoff 的边界，避免把所有能力都抽象成一个
>    模糊的 Memory；
> 5. 让 Task Tool、子 Agent 和 Workflow 复用同一个核心 Runtime，而不是各自实现一套
>    循环；
> 6. 让 Trace 从 Event 派生，并用 Suite、Backend、ArtifactStore 解耦评测任务、执行
>    环境和产物。
>
> 外部接入部分包括 OpenAI Chat、OpenAI Responses、Anthropic Messages、OpenAI-compatible
> 服务、MCP、Docker，以及 SWE-bench、Terminal-Bench、ProgramBench 等评测任务和官方
> 评分机制。
>
> 这些外部能力不是简单地调用 API。Provider Adapter 负责把项目内部的 `LLMRequest`
> 转换成具体 Provider 的请求格式，再把不同供应商的响应转换成统一的
> `AssistantMessage`、`ToolCallBlock` 和 `TokenUsage`。这样 Runtime 不需要写大量
> `if provider == ...` 的分支，也不会把 SDK 响应对象直接存进 State。
>
> Benchmark 方面，项目负责任务组装、运行环境、Agent 执行、轨迹和结果产物管理；官方
> 任务定义、隐藏测试和评分器的所有权仍然属于对应 Benchmark。

**一句话收束：**

> 我自研的是核心运行语义和系统边界，不是重新实现模型供应商、MCP、Docker 或
> Benchmark 本身。

如果实际没有亲自实现某一部分，应把“我设计和实现”改成“项目支持”或“我参与接入”。

## 9. 第一个能运行的版本是什么样的？后续为什么按这个顺序增加 Context、Workflow、Trace 和 Eval？

**参考回答：**

> 第一个可运行版本应该是最小的模型—工具闭环，而不是一开始就包含所有外围能力。
> 当前仓库中的最小示例使用 Fake Provider 和 Bash 工具，任务是执行：
>
> ```text
> Use bash to run command: printf 'hello-from-tool\n'
> ```
>
> 运行过程是：
>
> ```text
> 任务进入 State
> → 第一轮模型返回 Bash ToolCall
> → Runtime 执行 Bash
> → 工具结果写回 State
> → 第二轮模型读取工具结果
> → 返回 final Message
> ```
>
> 这个最小版本已经验证了 Agent 的核心闭环：模型可以提出工具调用，Runtime 可以执行
> 工具，工具结果可以回到下一轮模型输入，运行状态和事件可以被记录，Agent 可以根据
> `final` 停止。Fake Provider 不需要真实 API Key，适合先验证 Runtime 协议和测试。
>
> 后续能力按依赖关系增加。
>
> **第一步是 Context。** 当运行从两轮工具调用扩展到长任务后，完整历史会不断增长，
> 因此需要把完整历史、活跃上下文和单轮模型输入分开，再增加压缩和 Recall。Context
> 必须建立在稳定的 State 和 Message 协议之上。
>
> **第二步是 Workflow 和子 Agent。** 当单 Agent 能够稳定运行后，才有必要组合多个
> 独立运行。Task Tool、Planner/Executor、Reflection、Parallel 和 Goal Loop 都复用
> 普通 Agent Runtime，因此多 Agent 是组合层能力，而不是另一套运行协议。
>
> **第三步是 Trace。** Event 从核心循环一开始就存在，但完整的 Trace、Span、Model
> Turn、成本统计和 JSONL Viewer 需要稳定的事件语义，否则观察层只能依赖日志或终端
> 文本，无法准确回答某一轮模型实际看到了什么。
>
> **第四步是 Eval。** Runtime、Context 和 Trace 稳定后，才能把 Agent 放进本地进程、
> Docker 或远程环境做批量评测。Eval 再通过 Suite、Backend 和 ArtifactStore 分离
> 任务语义、执行环境和产物存储，并把 Agent 结果交给评分器验证。
>
> 这条演进路径可以总结为：
>
> ```text
> 最小运行闭环
> → 长任务上下文管理
> → 多 Agent 组合
> → 可观测轨迹
> → 可复现实验和 Benchmark
> ```
>
> 这不是声称所有项目开发都必须按这个固定顺序，而是说明当前架构的依赖关系：后面的
> 能力依赖前面的运行事实和边界。

**事实边界：**

当前文档和示例能够证明 Fake Provider + Bash 的最小闭环以及模块依赖关系，但不能自动
证明个人历史上的精确开发时间线。如果真实开发顺序不同，应按真实经历调整。

## 10. 你做过的最重要的三个技术决策是什么？每个决策解决了什么实际问题？

### 决策一：使用显式 Agent 循环和项目自有的 Message / Event / State 协议

**参考回答：**

> 第一个关键决策是没有让核心 Runtime 直接围绕某个 Provider SDK 或框架对象构建，而是
> 定义项目自己的 `Message`、`Event` 和 `State`。
>
> 这个决策解决了三个问题：
>
> 1. 核心 Runtime 不被 OpenAI、Anthropic 等供应商的数据结构绑定；
> 2. 工具调用、工具结果、停止原因和上下文压缩可以使用统一语义；
> 3. 运行过程可以被完整记录、测试，并派生为 Trace。
>
> 代价是需要自己维护协议、Adapter 和兼容性测试。收益是核心循环可以使用真实 Provider，
> 也可以使用确定性 Fake Provider；子 Agent、Workflow、Trace 和 Eval 也能复用同一套
> 运行语义。

### 决策二：把完整历史、活跃上下文和单轮模型输入分开

**参考回答：**

> 第二个关键决策是把“发生过什么”和“下一轮模型应该看到什么”分开。
>
> `State` 保留完整运行事实；压缩策略只改变活跃上下文索引，并追加摘要或替代消息；
> `ContextView` 再根据当前 Agent 的可见性策略构建单轮模型输入。
>
> 这个设计解决了长任务中的两个矛盾：如果只保留完整历史，模型上下文会不断变大；
> 如果直接删除旧消息，调试、审计和信息恢复会失去依据。当前方案能够控制模型上下文
> 规模，同时保留原始消息，Recall 还能根据索引找回本次运行中被压缩的证据。
>
> 代价是需要维护活跃索引、压缩事件、摘要和恢复关系，设计复杂度高于简单截断历史。
> 但它能明确区分有损摘要和原始证据恢复，避免把二者混为一谈。

### 决策三：把复杂能力放到组合层，并让它们复用同一个 Runtime

**参考回答：**

> 第三个关键决策是没有为 Task Tool、子 Agent、Workflow 和 Goal Loop 分别设计新的
> Agent 内核，而是让它们组合普通 Agent Run。
>
> Task Tool 把子 Agent 包装成父 Agent 可以调用的工具；子 Agent 使用独立 State，父
> Agent 接收子 Agent 的结果；固定 Workflow 则保存每个步骤的输出和完整 State。这样
> 既能支持动态委派，也能支持确定性编排。
>
> 这个决策解决了两个问题：
>
> 1. 避免系统出现多套不一致的消息、工具和停止语义；
> 2. 保证每个子运行可以独立审计，最终再派生出合并 Trace。
>
> 代价是组合层需要处理父子预算、失败传播、结果聚合和并行顺序。但相较于复制多套
> Runtime，这种方式更容易维护和验证。
>
> 同样的边界也延伸到 Eval：Suite 负责任务语义，Backend 负责执行环境，ArtifactStore
> 负责产物传输，三者独立替换，不把 Benchmark 逻辑塞进核心 Runtime。

**三项决策的简短总结：**

> 第一，使用自有运行协议解决供应商耦合和可观察性问题；第二，把事实和上下文视图分开
> 解决长任务信息管理问题；第三，让多 Agent 和评测能力建立在同一个核心 Runtime 之上，
> 避免系统出现多套不一致的执行语义。

如果面试官追问“为什么不是 Provider Adapter、Hook 或 JSONL”，可以补充：

> Provider Adapter、Hook 和增量 JSONL 都是重要设计，但它们更像是上述三个核心决策的
> 具体落地，而不是更上层的架构选择。
