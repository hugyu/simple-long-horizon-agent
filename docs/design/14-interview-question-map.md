# 14. Agent 项目面试问题地图

本文站在大厂 Agent 方向面试官的视角，只根据[第 15 篇简历项目描述](15-resume-project-description.md)
设计问题。默认面试官看不到仓库、源码和提交记录，因此不会从文件或类名开始提问，
而会通过架构图、伪代码、边界条件、失败案例和实验口径判断候选人是否真正主导并
理解项目。

本文只整理考察角度、主问题和潜在追问，不提供可直接背诵的标准答案。准备时应使用
真实经历回答，并明确区分已经实现、经过实验验证和未来可以补充的能力。

## 1. 面试官首先会判断什么

这份简历同时声称候选人从零建设了 Agent Runtime、长上下文、多 Agent、可观测性、
评测基础设施，并取得三项量化结果。面试官通常不会平均询问所有功能，而会优先验证
下面五件事：

1. **所有权**：项目中哪些目标、设计、实现和实验由候选人真正负责；
2. **核心机制**：候选人能否解释一次 Agent 运行的控制流与数据流；
3. **设计必要性**：每个模块解决了什么真实问题，为什么不能使用更简单的方案；
4. **工程边界**：异常、停止、安全、恢复和可观测性是否有清楚语义；
5. **实验可信度**：Benchmark 是否可比，数字能够证明什么，又不能证明什么。

问题按优先级分为：

- **P0**：简历中的核心主张，基本必问，必须达到项目作者级理解；
- **P1**：面试官确认候选人做过项目后，用于继续深挖设计和工程能力；
- **P2**：高级岗位、系统设计轮或压力面中可能出现的扩展问题。

## 2. 从简历文字到提问方向

| 简历信号 | 面试官的第一判断 | 主要追问方向 |
| --- | --- | --- |
| 项目作者 / 核心开发者 | 所有权很强，需要验真 | 团队分工、演进过程、失败方案、个人决策 |
| 从零设计并实现 | 不只是使用现有框架 | 为什么自研、最小版本、核心抽象、替代方案 |
| 显式 Agent 循环 | Runtime 是项目核心 | 生成器、回合状态机、工具反馈、停止与中止 |
| Message / Event / State | 有自有领域模型 | 三者语义、事实源、派生视图、重放能力 |
| Provider-neutral | 支持多个模型服务 | Adapter 边界、协议差异、特性保真、错误映射 |
| 长上下文管理 | 声称解决长任务信息问题 | 三层上下文、压缩、Recall、信息损失与 Token 收益 |
| Memory / Skills / Handoff | 概念较多，容易混淆 | 生命周期、所有权、检索方式、污染和过期 |
| 并行工具 / MCP / Hook | 能作用于真实环境 | 调度、超时、中止、资源生命周期和安全边界 |
| 子 Agent / 多种工作流 | 声称具备多 Agent 能力 | 动态委派、确定性编排、隔离、预算、收益和失败 |
| Trace / Eval | 不只做 Demo | 事实与派生视图、JSONL、评分隔离、可复现性 |
| 三项 Benchmark 提升 | 最强成果，也是最高风险点 | Baseline、公平性、相对提升、成本、消融和归因 |

## 3. 一场面试可能采用的完整路径

面试官常从宽到窄，再通过反例检查答案是否自洽：

```text
项目定位与个人职责
  → 一次 Agent Run 的完整链路
  → Message / Event / State 数据语义
  → Context、Tool 或 Multi-Agent 中任选一条深挖
  → Trace 与 Eval 如何验证行为
  → Benchmark 数字审计
  → 失败案例、替代方案和生产化边界
```

候选人需要准备一个能够贯穿全部模块的真实任务案例，而不是为每个名词准备彼此无关
的定义。

## 4. 项目定位与所有权验真

### 4.1 P0：项目解决什么问题

- 请用两分钟介绍这个项目，先讲问题和结果，不要罗列模块。
- 你所说的“长周期任务”如何定义：回合多、耗时长、上下文长，还是环境状态持续变化？
- 单轮模型回答为什么无法解决这类任务？
- 一个普通 ReAct 循环还缺少哪些关键能力？
- 项目的目标用户是谁，典型使用场景是什么？
- “轻量级”具体体现在哪里，可以用哪些指标或边界说明？
- 这个项目最核心、最不可替代的三个部分是什么？
- 如果删除 Memory、Workflow 和 Viewer，它是否仍然是一个长周期 Agent Runtime？
- 这个项目明确不解决什么问题？
- 为什么没有直接使用 LangGraph、AutoGen 或其他 Agent 框架？

### 4.2 P0：你究竟做了什么

- 这是个人项目还是团队项目？团队有多少人，如何分工？
- “项目作者”和“核心开发者”哪一个更准确？
- 哪些架构由你提出，哪些模块由你亲自实现，哪些只是接入或维护？
- 第一个可运行版本有哪些能力？后来按照什么顺序演进？
- 你做出的三个最重要技术决策是什么？
- 哪个决策后来被证明是错误的，你如何发现并修改？
- 项目中最难定位的一次 Bug 是什么？
- 如果没有你，项目会缺少哪部分关键能力？
- 你最熟悉和相对不熟悉的模块分别是什么？
- 如果现在重新实现一次，你会保留和删除什么？

### 4.3 P1：为什么相信这是你做的

- 请现场画出系统架构，不使用仓库中的模块名也要讲清边界。
- 请用伪代码写出最小 Agent 主循环。
- 请讲一次从失败现象、定位证据到最终修复的完整过程。
- 哪个设计不是看资料就能直接得到，而是你在运行中被迫引入的？
- 哪个模块功能很多，但对最终效果帮助可能有限？
- 你如何判断应该增加抽象，还是保留局部重复？

## 5. Agent Runtime 核心循环

### 5.1 P0：一次运行如何推进

- 从用户任务进入系统开始，到 Agent 停止为止，完整链路是什么？
- 每轮模型调用之前和之后分别发生什么？
- 模型返回纯文本、工具调用、空响应或非法响应时分别如何处理？
- 工具结果如何进入下一轮模型决策？
- 一轮和一次完整 Run 分别以什么作为边界？
- Runtime 如何区分模型决策、工具执行和调用者控制？
- 同一 Session 收到后续任务时，是新建 State 还是继续原 State？

### 5.2 P0：为什么使用生成器

- 为什么使用生成器，而不是普通 `while` 循环？
- 生成器为调用方提供了哪些观察和控制能力？
- `Agent.run()` 返回之后，Agent 是否已经开始执行？
- 如果调用方不消费事件迭代器，会发生什么？
- 生成器如何支持中止、流式展示和外部协调？
- 生成器带来了哪些复杂度或限制？
- 为什么不是 async generator？如果改成 async，哪些边界会变化？
- 生成器抛出异常后，已经发生的状态是否仍可检查？

### 5.3 P0：停止状态机

- 模型说“任务完成”是否等于任务客观完成？
- 正常完成、最大回合数、用户中止和工具主动终止有什么区别？
- 多个停止条件同时出现时，优先级如何确定？
- 工具超时后 Agent 应继续修正还是立即结束？
- 如何防止模型陷入无限循环或重复调用同一工具？
- 回合、Token、时间和成本预算分别应该由哪一层控制？
- 外部完成检查失败后，如何把反馈送回 Agent？
- Run 已经结束后还能否继续，继续运行的语义是什么？

### 5.4 P1：错误、重试和副作用

- Provider 请求失败时哪些错误可以重试？
- 模型请求重试与工具执行重试的风险有什么不同？
- 如何避免重试导致同一个有副作用的工具被执行两次？
- 工具异常应该抛给 Runtime，还是转换为模型可见结果？
- 用户中止时，正在运行的 Shell 及其子进程如何清理？
- 如果 Trace 写入失败，是否应该让 Agent 任务失败？
- 进程在一次工具调用后、结果入 State 前崩溃，如何判断恢复行为？

## 6. Message、Event 与 State

### 6.1 P0：三个概念为什么分开

- `Message`、`Event` 和 `State` 分别表达什么？
- 为什么 Message 不能承担全部状态？
- State 是当前快照、消息列表，还是追加式运行事实？
- Event 是领域事实、Trace 记录，还是面向 UI 的通知？
- 哪个对象是事实源，哪些对象是派生视图？
- 工具调用 ID 和工具结果 ID 如何建立因果关系？
- 为什么项目类型必须与 Provider SDK 对象分开？

### 6.2 P1：一致性与重放

- Event 如何保证稳定顺序和唯一身份？
- 是否能够仅根据 Event 重建 State 或 transcript？
- 状态重建与真正重新执行模型、工具有什么区别？
- 为什么带外部副作用的 Agent 不能简单地做确定性重放？
- Event 持续增长后，内存和存储如何处理？
- 派生视图计算错误会不会污染事实源？
- 如果一个 Event Schema 演进，旧轨迹如何兼容？

### 6.3 压力问题

- 如果只保存最终回答，会失去哪些调试和评测信息？
- 如果只保存 Message，不保存模型请求事件，能否知道某轮模型真正看到了什么？
- Event 和日志有什么本质区别？为什么不直接使用 Python logging？
- 不可变 Message 是否会造成大量复制，收益是否值得？

## 7. Provider Adapter 与多模型支持

### 7.1 P0：Adapter 边界

- 为什么核心 Runtime 不能直接使用 OpenAI 或 Anthropic 的响应对象？
- Runtime Message、LLM Message 和 Provider Wire 三层分别负责什么？
- 哪些信息应统一，哪些信息必须保留为 Provider-specific metadata？
- Provider Adapter 在请求和响应两个方向分别完成哪些转换？
- 供应商返回未知内容块或停止原因时如何处理？
- 如何使用 Fake Provider 做确定性测试？

### 7.2 P1：供应商协议差异

- OpenAI Chat、OpenAI Responses 和 Anthropic Messages 的工具调用表达有何差异？
- 工具调用 ID、工具结果、图片和推理内容如何跨协议映射？
- Provider-neutral 模型是否会牺牲某些供应商独有能力？
- OpenAI-compatible 服务只实现部分协议时如何降级？
- 流式响应中断时，已经收到的文本和工具调用如何处理？
- 缓存 Token、推理 Token 和普通 Token 如何统一统计？
- 限流、超时、鉴权失败和内容过滤是否采用相同重试策略？

### 7.3 反事实问题

- 如果系统永远只支持一家 Provider，Adapter 是否仍然有价值？
- 为什么不在主循环中使用 `if provider == ...`？
- 如果统一协议无法无损表示 Responses API 能力，你会修改核心协议还是增加扩展字段？

## 8. 长上下文、压缩与信息恢复

### 8.1 P0：三层上下文

- 完整历史、活跃上下文和单轮模型输入分别是什么？
- 为什么要分成三层，两层是否足够？
- 固定 system prompt 属于哪一层，在何时加入？
- Context 构建是纯投影还是会修改 State？
- 被移出活跃上下文的消息是否仍保存在完整历史中？
- 如何准确记录某一轮模型当时实际看到的输入？
- 为什么不能从最终 transcript 反推出历史某轮输入？

### 8.2 P0：压缩策略

- 什么条件触发压缩：Token、消息数量、工具结果大小还是模型主动判断？
- 工具结果压缩、模型摘要和 Agent 主动 Compact 有什么区别？
- 为什么需要多种压缩机制，而不是统一摘要？
- 压缩应该替换历史，还是只改变当前可见索引？
- 模型摘要产生幻觉或遗漏关键约束时怎么办？
- 多次摘要如何避免信息逐轮衰减？
- 代码、错误栈、文件路径和普通自然语言应该使用相同压缩策略吗？
- 如何评价压缩：Token、成本、时延和任务成功率分别如何变化？
- 如果没有消融数据，能否声称压缩提升了 Benchmark 分数？

### 8.3 P0：Recall、Skills、Memory 与 Handoff

- Recall、Skills、Memory、Handoff 和 State 分别解决什么问题？
- Recall 如何定位本次 Run 中已经被压缩的原始信息？
- Recall 返回摘要还是原文，为什么？
- Skills 为什么是按需方法知识，而不是跨任务 Memory？
- 文件型 Memory 在何时读取、何时写入？
- Memory 如何去重、更新、过期和纠错？
- 子 Agent Handoff 应传任务、摘要、证据还是完整父 State？
- Handoff 信息太少或太多分别会造成什么问题？

### 8.4 P1：安全与失败

- 恶意工具输出如何通过摘要或 Memory 形成持久 Prompt Injection？
- Memory 中的旧经验与当前事实冲突时谁优先？
- Recall 检索到同名但错误的历史片段时如何处理？
- 文件型 Memory 并发写入如何避免覆盖和损坏？
- 模型窗口足够大时，是否仍需要主动上下文选择？
- “精确信息恢复”依赖什么条件？摘要本身能否称为精确恢复？

## 9. 工具、MCP、Hook 与安全边界

### 9.1 P0：工具契约

- 工具输出过长时如何进入 State 和模型上下文？
- 并行工具调用如何保持结果与原调用正确配对？

### 9.2 P1：Bash、Read 与 Edit

- 两个并行 Edit 修改同一文件时怎么办？
- 工具是否应该自动修复失败，还是把错误交给模型？
- 一次部分成功的文件修改应该如何记录？

### 9.3 P1：MCP

- MCP 在系统中位于模型层、工具层还是编排层？
- MCP Tool 与本地 Tool 如何统一成同一执行语义？
- MCP Server 的连接和资源生命周期由谁管理？
- MCP Schema 动态变化或连接中断时如何处理？
- 为什么使用 MCP，而不是为每个外部服务直接编写 HTTP Tool？
- MCP 返回的资源是否可以直接进入模型上下文？

### 9.4 P0：Hook 与安全

- Hook 可以在哪些生命周期点拦截行为？
- Hook 是强制策略边界，还是普通通知回调？
- Prompt 要求绕过 Hook 时，Runtime 如何保证策略仍然生效？
- Bash Agent 如何限制高危命令、敏感目录和密钥访问？
- Docker、参数校验和 Hook 是否构成完整安全沙箱？
- Trace 如何避免保存 API Key、私有代码或隐藏评测数据？
- 如果面向多租户生产环境，现有安全边界还缺什么？

## 11. Event、Trace 与可观测性

### 11.1 P0：为什么 Event 之外还需要 Trace

- Event 已经记录运行事实，为什么还需要 RunTrace、Span 和 Model Turn？
- Trace 是事实源还是从 Event 派生的观察产品？
- RunTrace、Span 和 Model Turn 分别回答什么问题？
- 子 Agent 的 Span 如何合并，又为什么不能直接共享父 State？
- Viewer 为什么不能反向控制 Runtime？

### 11.2 P0：某轮模型究竟看到了什么

### 11.3 P1：增量 JSONL 与 Viewer

- 为什么选择 JSONL，而不是一个完整 JSON、关系数据库或 OpenTelemetry？

- 多线程读取 State 和写轨迹时如何避免竞争？

- Trace Schema 如何版本化，Viewer 如何兼容旧文件？
- Viewer 的路径、文件名和 Schema 契约如何防止漂移？
- Trace 写入失败为什么不能伪装成 Agent 行为失败？

### 11.4 P1：成本、隐私与训练导出

- Token 和成本按什么维度聚合？子 Agent 成本如何合并？
- 模型未返回 usage 时为什么不能记为精确的零成本？
- 价格表变化是否应该回写历史运行？
- Trace 中的代码、Prompt、密钥和工具输出如何脱敏？
- 训练数据导出如何保证与真实 Provider 请求格式一致？

## 12. Eval 基础设施

### 12.1 P0：三项正交协议

- Suite、Backend 和 ArtifactStore 分别负责什么，又明确不负责什么？
- 为什么这三个边界必须正交？
- 更换 LocalProcess 为 LocalDocker 时，Suite 为什么不应该修改？
- ArtifactStore 为什么不负责解释评分结果？
- Runner 的职责是什么，为什么不能吸收 Benchmark 领域逻辑？

### 12.2 P0：输入、结果和评分隔离

- 模型可见任务输入与私有评测输入如何分开？
- Gold answer、隐藏测试和官方评分脚本如何避免泄漏？
- `result.json` 为什么是 Agent 执行与评分之间的解耦点？
- Agent 声明完成但评分未通过，是任务结果还是基础设施错误？
- Oracle 模式能证明什么，为什么不能和真实模型成绩混合？

### 12.3 P1：Backend 与 Store

- LocalProcess、LocalDocker 和 RemoteDocker 的主要差异是什么？
- 为什么 LocalProcess 共享同一工作区时不适合并发？
- Worker 能访问 Host、只有 Host 能访问 Worker时，产物分别如何传输？
- 远程环境怎样实时同步轨迹？
- 实例 ID 如何防止路径逃逸？
- 容器结束但结果已经写入时，哪个事实决定最终状态？

### 12.4 P1：批量、重试与恢复

- Dataset 并发如何保证每个实例相互隔离？
- 哪些基础设施异常可以重试，哪些任务失败不应该重试？
- 结果顺序是否与并发完成顺序一致？
- Host 在批量任务提交中途崩溃，如何避免孤儿任务？
- Submit/Reconcile 为什么需要可持久化 RunHandle 和 manifest？
- Reconcile 为什么应该可以重复执行？
- Chain State、Agent State 和 Memory 有什么区别？

## 13. Benchmark 数字审计

简历中的三组数字是最醒目的成果，也是最可能被严格审计的部分。候选人至少应准备
每项评测的任务范围、模型、推理配置、任务预算、运行次数、评分器、成本、失败处理和
原始产物来源。

### 13.1 P0：基础口径

- SWE-bench Pro、Terminal-Bench 2.1 和 PostTrainBench 分别评测什么能力？
- 三项评测分别使用什么模型和推理等级？
- 63.20%、77.53% 和 45.88% 分别是什么指标？
- 每项评测包含多少任务，是否运行完整集合？
- Baseline 是自己在相同环境复跑，还是引用公开结果？
- “同模型、同任务预算”具体包括哪些相同条件？
- 模型版本、推理强度、Token、回合、时间、工具和重试是否都一致？
- 评测失败、环境失败和超时分别如何计分？

### 13.2 P0：相对提升与绝对百分点

- SWE-bench Pro 从 59.10% 到 63.20%，绝对提升和相对提升分别是多少？
- Terminal-Bench 从 64.70% 到 77.53%，为什么不是“提升 19.83 个百分点”？
- PostTrainBench 的 weighted average 如何计算？
- 为什么简历选择相对提升，而不是只报告绝对百分点？
- 面试官要求统一使用百分点时，应该如何准确表述？

计算口径为：

```text
绝对提升（百分点） = 项目结果 - Baseline
相对提升（%） = (项目结果 - Baseline) / Baseline × 100%
```

### 13.3 P0：公平性和可信度

- 项目与 Baseline 是否使用完全相同的任务子集和 Benchmark 版本？
- Terminal-Bench 的项目结果和 Baseline 是否来自相同版本的任务与评分器？
- 模型是否是完全相同的快照，而不只是相同系列名称？
- 每个任务运行一次还是多次，是否存在挑选最好结果？
- 温度、随机性和运行顺序如何控制？
- 是否报告置信区间或重复运行方差？
- 被基础设施问题影响的任务是否被排除？
- 是否可能存在训练数据污染、隐藏测试泄漏或 Prompt 泄漏？
- 官方 Harness 结果与内部结果如何映射和核对？

### 13.4 P0：能证明什么，不能证明什么

- 这些结果证明的是底层模型能力，还是 Agent 系统的组合效果？
- 分数提升能否单独归因于 Task Tool、压缩、Handoff 或某个 Workflow？
- 如果没有组件消融，最严格、最安全的结论是什么？
- 如何设计实验验证压缩模块的独立价值？
- 如何验证多 Agent 的收益不是因为调用了更多 Token？
- 如果同预算但实际工具权限不同，还能否公平比较？

当前结果只应支持整套 Agent 配置在对应口径下的组合效果。没有控制变量和组件消融
时，不能把提升单独归因于某个功能。

### 13.5 P1：消融与成本收益

- 请设计 Baseline、Context、Task Tool、Handoff 和 Workflow 的逐层消融实验。
- 除成功率外，还应报告哪些 Token、成本、时延和失败类型指标？
- 每个任务的平均成本、中位成本和长尾成本分别是多少？
- 成绩提升是否只是来自更多模型调用？
- 多 Agent 增加多少 Token、时延和方差？
- 如果成本预算减半，哪项机制最应该保留？
- 如何画出成功率与成本的 Pareto 前沿？
- 提升一个百分点所需的额外成本是否有业务价值？

## 14. 生产化与系统设计扩展

这些问题不要求当前项目已经实现全部生产能力，主要判断候选人能否清楚区分已有能力、
项目非目标和合理演进方向。

### 14.1 P1：恢复与幂等

- Agent 运行一半进程崩溃，如何恢复？
- Event/State 是否需要持久化，持久化粒度是什么？
- 工具已经产生副作用但结果未记录，恢复时如何处理？
- 如何设计幂等 Tool 或幂等键？
- 哪些步骤可以安全重放，哪些只能由人工确认？

### 14.2 P2：并发与分布式运行

- 如果要同时运行一千个 Agent，当前架构最先遇到什么瓶颈？
- Python 线程、进程和 async 分别适合哪些工具负载？
- CPU 型和 I/O 型工具应该如何调度？
- Provider 全局限流、租户限流和单任务预算如何协调？
- 如何实现任务队列、租约、心跳和孤儿任务恢复？

### 14.3 P2：可靠性、安全和治理

- Provider 服务降级时如何做重试、熔断和 fallback？
- 如何管理多租户的密钥、权限和工作空间隔离？
- 如何防止 Prompt Injection 驱动高危工具？
- 如何建立人工审批和不可绕过的 Policy Enforcement Point？
- Trace 包含用户代码时如何处理权限、保留周期和删除要求？
- 如何设置单任务和租户级成本上限？
- 哪些生产问题不应该放进核心 Agent Runtime？

## 15. 面试官常用的真实性检查方法

### 15.1 要求现场画图

候选人应能不依赖源码画出：

- 一次完整 Agent Run；
- Message、Event、State 和派生 Trace 的关系；
- 完整历史、活跃上下文、单轮输入、压缩与 Recall；
- 父 Agent、Task Tool、子 Agent 和 Handoff；
- Suite、Backend、ArtifactStore 与评分器；
- 一个 Benchmark 从任务输入到官方评分的链路。

### 15.2 要求写伪代码

高概率题目包括：

- 最小 Agent 主循环；
- 并行工具调用与结果归并；
- 停止条件状态机；
- Context View 构建；
- JSONL 增量写入；
- Eval 单实例 Runner。

### 15.3 询问失败案例

- 最严重的一次上下文信息丢失是什么？
- 哪次压缩导致模型后续判断错误？
- 哪次多 Agent 方案反而降低成功率？
- 哪类工具结果最容易撑爆上下文？
- 哪个 Provider 差异最难统一？
- Benchmark 中最常见的失败类型是什么？
- 哪个设计经过真实运行后被删除或重构？

回答应覆盖具体症状、证据、定位路径、修复和修复后的代价，不能只说“优化了性能”或
“提高了稳定性”。

### 15.4 反事实问题

- 如果不使用生成器，如何实现相同控制能力？
- 如果不保存 Event，只保存 Message，会失去什么？
- 如果模型上下文无限大，还需要主动上下文管理吗？
- 如果只有一个 Provider，还需要 Adapter 吗？
- 如果子任务没有并行性，多 Agent 有什么价值？
- 如果不做 Benchmark，Trace 是否仍然必要？
- 如果不能使用 Docker，怎样提高 Eval 可复现性？

## 16. 简历表述的高风险追问

### 16.1 “项目作者 / 核心开发者”

- 两种身份为什么同时出现？哪个是事实上的准确角色？
- 团队其他成员分别贡献了什么？
- 公开项目已有能力与个人新增能力如何区分？

准备原则：简历最终应选择真实、单一的身份，并能准确说明个人边界。

### 16.2 “从零设计并实现”

- “从零”是没有使用 Agent 框架，还是所有基础设施都独立实现？
- 使用了哪些 SDK、协议、Benchmark Harness 和第三方工具？
- 哪些思想参考了外部系统？

准备原则：从零不等于拒绝依赖，应准确限定为自研核心 Runtime 和项目边界。

### 16.3 “控制 Token 消耗”

- 压缩前后 Token、成本和成功率各变化多少？
- 如果没有量化对照，为什么使用“控制”而不是“提供控制机制”？

准备原则：没有实验时不要暗示已经证明单个压缩组件产生量化收益。

### 16.4 “精确信息恢复能力”

- 模型摘要能否精确恢复原文？
- 精确性依赖原始内容仍然存在，还是依赖检索结果没有误差？

准备原则：区分有损摘要和根据稳定引用返回原始证据的 Recall。

### 16.5 多种工作流名称

对于简历中的每个 Workflow，候选人都应能够回答：

- 它解决什么问题；
- 最小执行流程是什么；
- 停止条件是什么；
- 相比普通 Agent 的增量价值是什么；
- 增加了多少成本和失败面；
- 什么场景不应该使用它。

### 16.6 Benchmark 提升

- 为什么选取相对提升，而不是百分点？
- Baseline 是否真正同模型、同版本、同预算、同任务集合？
- 为什么不能将提升归因于某一个组件？

准备原则：同时给出原始分数、Baseline、绝对百分点、相对提升和实验限制。

## 17. 必须优先准备的十道问题

如果准备时间有限，先完成下面十题。每题都应能继续承受至少两轮追问：

1. 画出一次任务从输入到停止的完整执行链路。
2. Message、Event 和 State 为什么必须分开？
3. 为什么使用生成器，它带来了什么，又牺牲了什么？
4. 模型声明完成与任务客观完成有什么区别？
5. 完整历史、活跃上下文和单轮模型输入有什么区别？
6. Recall、Skills、Memory 和 Handoff 分别解决什么问题？
7. Task Tool 动态委派与确定性 Workflow 有什么本质区别？
8. Suite、Backend 和 ArtifactStore 为什么正交拆分？
9. 三项相对提升如何计算，Baseline 为什么公平？
10. 没有组件消融时，Benchmark 能证明什么，不能证明什么？

## 18. 贯穿项目的案例题

面试官可能要求候选人选一个真实任务，连续回答：

1. 任务目标和外部完成标准是什么？
2. 初始任务怎样成为 Message 并进入 State？
3. 第一轮模型实际看到了哪些内容？
4. 模型为什么选择某个工具，工具调用怎样执行？
5. 工具成功、失败或超时时分别产生什么事实？
6. State 和活跃上下文在多轮中如何变化？
7. 何时触发压缩，如何找回被压缩的信息？
8. 是否发生子 Agent 委派，父子状态如何隔离？
9. Agent 为什么停止，外部如何判断真正完成？
10. Trace 保存了哪些证据，Eval 如何取得产品并评分？
11. 最终 Token、成本、时延和分数如何统计？
12. 如果任务失败，能够从哪些事件和产物定位原因？

这个案例应来自真实运行。不要虚构线上规模、生产事故、消融结果或个人贡献。

## 19. 自我检查清单

在正式面试前，对每一条简历描述检查：

- 能否先解释它解决的问题，而不是先背模块名？
- 能否画出输入、输出、事实源和上下游？
- 能否写出最小伪代码？
- 能否说明停止、异常和恢复语义？
- 能否比较至少一种替代方案并解释取舍？
- 能否讲一个真实失败案例？
- 能否明确自己负责和没有负责的部分？
- 能否给出验证方式和原始实验口径？
- 能否区分代码事实、实验结论和个人评价？
- 能否明确当前系统没有解决的生产问题？

如果某个名词无法回答这些问题，应进一步学习对应设计材料，或从简历中删除该名词，
而不是只准备一个定义。
