# 14. Agent 项目面试问题地图（筛选版）

本文根据[第 15 篇简历项目描述](15-resume-project-description.md)重新筛选面试问题。
目标不是覆盖仓库里的每个名词，而是模拟大厂 Agent / Agent Infrastructure 面试官如何
从简历中的强主张出发，判断候选人是否真正做过、理解过并验证过这个项目。

本文只整理面试问题，不提供背诵答案。回答时必须区分：

- 已经实现的代码事实；
- 通过实验验证的结论；
- 根据经验做出的设计判断；
- 尚未实现的生产化设想。

## 1. 先看结论：简历真正暴露了什么

这份简历的风险不是技术点少，而是技术点很多。面试官不会平均询问
`MCP`、`Memory`、`PDR`、`JSONL`、`Docker` 等名词，而会优先验证下面六个主张：

| 简历主张 | 面试官真正想确认什么 | 优先级 |
| --- | --- | --- |
| 从零设计长周期 Agent Runtime | 你是否理解 Agent 的核心控制流，而不是只会组装框架 | P0 |
| Message / Event / State / Context 分层 | 这些抽象是否来自真实问题，边界是否稳定 | P0 |
| 上下文压缩、Recall、Memory、Handoff | 你是否真正解决过长任务的信息与状态问题 | P0 |
| 子 Agent 与多种 Workflow | 多 Agent 是否有清晰适用场景，而不是功能堆叠 | P0 |
| Trace / Eval 闭环 | 你是否能用证据定位问题并做可复现实验 | P0 |
| 三项 Benchmark 提升 | 结果是否可信，是否清楚归因边界 | P0 |
| Provider、MCP、Hook、并行工具 | 是否具备真实工程边界意识 | P1 |
| 分布式、多租户、治理、熔断 | 是否能做更大系统的设计推演 | P2 |

## 2. 面试官的实际筛选路径

一轮 45～60 分钟的项目面，大概率按下面顺序进行：

```text
项目介绍与个人贡献
  → 选一个真实任务还原完整 Agent Run
  → 深挖 Runtime / Context / Multi-Agent 中的一条主线
  → 追问失败案例和设计取舍
  → 核对 Trace / Eval 证据
  → 审计 Benchmark 数字
  → 根据岗位方向补问 Provider、工具或生产化
```

面试官通常只会从一条主线深入，不会在同一轮把所有模块都逐项检查。
因此准备策略应是：

1. 每个 P0 问题能回答清楚；
2. 至少准备一个真实任务，能串起 Runtime、Context、Tool、Trace 和 Eval；
3. 每个简历数字都能说明来源、配置、失败处理和限制；
4. 不要为了覆盖名词，虚构没有做过的线上规模或消融实验。

## 3. P0：项目定位与个人贡献

### 3.1 开场主问题

- 请用两分钟介绍这个项目，先讲它解决了什么问题、怎么解决、结果如何。
- 你说的“长周期任务”具体指什么？请用一个真实任务说明它为什么不能由一次模型调用完成。
- 这个项目最核心的设计是什么？如果只能保留一个部分，你保留什么？
- 这个项目和一个带工具的普通 ReAct Agent，关键差异在哪里？
- 为什么选择自己实现 Runtime，而不是使用 LangGraph、AutoGen 或其他现成框架？
- “轻量级”体现在哪些具体边界？它明确不解决什么问题？

### 3.2 所有权验证

- 这是个人项目还是团队项目？“项目作者 / 核心开发者”分别对应什么事实？
- 你亲自设计和实现了哪些部分？哪些是接入已有 SDK、Benchmark Harness 或开源方案？
- 第一个能运行的版本是什么样的？后续为什么按这个顺序增加 Context、Workflow、Trace 和 Eval？
- 你做过的最重要的三个技术决策是什么？每个决策解决了什么实际问题？
- 哪个设计后来被证明不够好？你通过什么证据发现，最后怎么改？
- 如果现在重做一次，你会删除简历中的哪个模块或表述？

### 3.3 这组问题在测什么

面试官不是在确认你是否能复述目录，而是在确认：

- 你能否讲出项目演进，而不是只讲最终架构；
- 你是否知道自己的责任边界；
- 你是否能承认某项能力只是机制，而不是已经证明的收益；
- 你能否把复杂系统压缩成清楚的问题、方案和结果。

## 4. P0：一次真实 Agent Run

这是整份简历最重要的主线。面试官可能要求你选择一次真实的代码任务、终端任务或
评测任务，按时间顺序讲完。

### 4.1 主问题

- 从任务进入系统到最终停止，完整的数据流和控制流是什么？
- 第一轮模型实际看到了哪些内容？模型返回后先记录什么，再执行什么？
- 工具调用如何进入 State，并在下一轮成为模型输入？
- 模型输出 `final`、工具调用、空响应或非法响应时分别发生什么？
- 一次 Turn 和一次完整 Run 的边界是什么？
- `Agent.run()` 为什么返回惰性 Event Stream？什么时候真正开始调用模型？
- `resume()` 和重新启动一个 Agent 有什么区别？
- Agent 为什么停止？谁判断任务真的完成？

### 4.2 必须追问的边界

- 模型说完成，但测试或外部检查不通过时，系统如何继续？
- 工具执行失败时，为什么通常要把失败作为模型可见结果，而不是直接让 Runtime 崩溃？
- 工具超时、用户中止、最大回合数和正常完成如何区分？
- 同一个有副作用的工具如果请求重试，如何避免重复执行？
- 如果进程在工具已经产生副作用、但结果尚未写入 State 时崩溃，当前实现能否恢复？
- 事件已经产生但调用者没有继续消费生成器时，State 处于什么状态？

### 4.3 面试官可能要求现场写的伪代码

- 最小 Agent 主循环；
- “模型输出工具调用 → 执行工具 → 写入 ToolResult → 下一轮”的控制流；
- `final`、`abort`、`max_turns` 和工具终止的停止判断。

### 4.4 不建议作为首轮重点的问题

“为什么不用 async generator”“生成器是否造成大量复制”等问题不是不能问，
但它们通常无法比一次真实 Run 更好地验证项目深度，属于回答过程中出现相关线索后
再追问的 P1 问题。

## 5. P0：上下文管理是第二条主线

简历写了“控制 Token 消耗、精确信息恢复、Compression、Recall、Skills、Memory、
Handoff”。这组表述会触发高强度追问，尤其要避免把不同生命周期的信息机制混成
一个“Memory”。

### 5.1 设计必要性

- 长任务中真正先出现的瓶颈是什么：上下文窗口、成本、延迟，还是信息找不到？
- 为什么要区分完整历史、活跃上下文和单轮模型输入？
- 压缩是在修改历史，还是只改变本轮可见视图？为什么？
- 你如何确保被移出活跃上下文的原始消息仍可审计或找回？
- 为什么不直接把全部历史交给上下文更大的模型？

### 5.2 压缩与恢复

- 什么时候触发压缩？阈值依据是什么？
- 工具结果压缩、模型摘要和 Agent 主动 Compact 分别适合什么场景？
- 摘要遗漏文件路径、错误信息或用户约束时，系统如何降低风险？
- 多次压缩如何避免摘要逐轮丢失信息？
- Recall 恢复的是摘要，还是原始证据？它依赖什么索引或引用？
- “精确信息恢复”这句话中，精确性来自哪里？摘要本身能否称为精确恢复？
- 如何验证压缩真正有价值，而不是只减少了 Token？

### 5.3 Compression、Skills、Memory、Handoff 的边界

- Recall、Skills、Memory 和 Handoff 分别跨越什么时间范围，数据所有权分别是谁？
- 为什么 Skills 是按需方法知识，而不是跨任务记忆？
- 为什么当前文件型 Memory 让模型主动读取，而不是每轮自动检索？
- 当前运行的临时摘要为什么不应直接写入永久 Memory？
- 当前工作区事实和旧 Memory 冲突时，谁优先？
- Handoff 为什么不直接传递父 Agent 的完整 State？
- Handoff 过少和过多分别会造成什么问题？

### 5.4 这组问题的真实考察点

面试官想知道的不是你能否背出四个定义，而是：

- 你是否按信息生命周期设计系统；
- 你是否知道摘要是有损的；
- 你是否保留了原始证据，而不是用“恢复能力”包装摘要；
- 你是否有压缩前后 Token、成本、时延和任务成功率的对照数据。

如果没有组件级数据，必须明确说：当前 Benchmark 结果只能支持整套 Agent 配置的
组合效果，不能把提升归因于 Compression、Recall 或 Handoff 中的某一个。

## 6. P0：多 Agent 与 Workflow

简历列出了 Task、规划执行、反思、路由、并行、PDR 和 Goal Loop。面试官不会要求
你逐一背定义，而会要求你说明为什么需要多次独立运行，以及组合后如何保持可控。

### 6.1 最可能的主问题

- 什么情况下单 Agent 不够，需要子 Agent 或 Workflow？
- Task Tool 的动态委派和固定 Workflow 的本质区别是什么？
- 为什么子 Agent 必须有独立 State，而不是共享父 Agent transcript？
- 父 Agent 传给子 Agent 什么，子 Agent 返回什么？
- 子 Agent 失败、超时或达到预算时，父 Agent 如何知道并继续决策？
- 为什么 Workflow 不再实现一套新的 Agent 主循环？
- Workflow 如何保存每一步的输出、State 和失败原因？

### 6.2 场景追问

- Planner/Executor 相比“让一个 Agent 先输出计划再执行”具体多了什么价值？
- Reflection 什么时候会变成昂贵但无收益的额外调用？
- Router 路由错误如何发现，是否有默认路径或回退？
- Parallel 的结果按完成顺序还是声明顺序返回？为什么？
- 多个 Worker 得到冲突结论时如何汇总？
- Goal Loop 如何区分“模型说完成”和“外部目标检查通过”？
- 如果成本预算减半，你会删除哪些协作步骤？

### 6.3 面试官希望听到的证据

- 一个真实任务为什么适合拆分；
- 拆分前后的成本、时延、成功率或失败类型；
- 子 Agent 的上下文隔离是否解决过具体问题；
- 一个多 Agent 方案失败或不如单 Agent 的案例；
- 你是否把 Workflow 视为编排层，而不是新的 Runtime。

## 7. P0：Trace、Eval 与“如何证明系统有效”

这部分是区分 Demo 工程和 Agent 基础设施工程的关键。

### 7.1 Trace

- 最终答案之外，你最需要观察什么，为什么？
- Event、RunTrace、Span 和 Model Turn 分别解决什么问题？
- 如何知道某一轮模型实际看到了什么，而不是只看最终 transcript？
- 为什么 Trace 应从运行事实派生，而不是让 Viewer 或日志成为事实源？
- 子 Agent 的 Trace 如何合并展示，同时保持父子 State 独立？
- 增量 JSONL 解决了什么问题？进程中途退出时如何保证产物可读？
- Trace 写入失败时，为什么不应该悄悄伪装成 Agent 行为失败？

### 7.2 Eval

- Unit Test、Smoke Run 和 Eval 分别验证什么？
- Suite、Backend、ArtifactStore 和 Runner 的边界为什么要拆开？
- 更换 LocalProcess、LocalDocker 或 RemoteDocker 时，为什么任务语义不应改变？
- Agent 可见的 task input 与私有 eval input 如何隔离？
- 任务未通过、评分器失败和基础设施失败如何区分？
- `result.json` 为什么是 Agent 执行与评分之间的解耦点？
- 如何从一次失败的评测产物定位：模型问题、工具问题、Runtime 问题还是环境问题？

### 7.3 面试官可能给出的设计题

- 设计一个最小的 Eval Runner，使同一 Suite 可以切换本地进程和 Docker。
- 设计一次失败运行的产物目录，要求能重现输入、环境、轨迹和评分路径。
- 设计一个能回答“模型这一轮到底看到了什么”的 Trace 数据结构。

## 8. P0：Benchmark 数字审计

简历中的 `63.20%`、`77.53%`、`45.88%` 和相对提升是高风险信号。
面试官通常会先问数字，再沿着实验条件追问，而不是先问实现细节。

### 8.1 基础口径

- 三项 Benchmark 分别评测什么能力？为什么选择它们？
- 每项结果的模型、模型版本、推理等级、任务集合和预算是什么？
- Baseline 是你在相同环境复跑的，还是引用公开结果？
- “同模型、同任务预算”具体保证了哪些条件相同？
- 每项评测运行一次还是多次？如何处理随机性？
- 任务失败、环境失败、评分失败和超时分别如何计分？

### 8.2 数字计算

- SWE-bench Pro 从 59.10% 到 63.20%，绝对提升是多少，相对提升是多少？
- Terminal-Bench 从 64.70% 到 77.53%，为什么不能说提升了 19.83 个百分点？
- PostTrainBench 的 weighted average 是如何得到的？
- 为什么简历同时保留原始分数、Baseline 和相对提升？

计算口径：

```text
绝对提升（百分点） = 项目结果 - Baseline
相对提升（%） = (项目结果 - Baseline) / Baseline × 100%
```

### 8.3 可信度与归因

- 项目结果和 Baseline 是否使用相同任务子集、评分器和环境版本？
- 是否可能存在挑选最好结果、任务污染或隐藏数据泄漏？
- 结果提升能证明整套配置有效，还是能证明某个组件有效？
- 没有组件消融时，最严格的结论应该怎么说？
- 如果让你补做实验，如何设计逐层消融：
  `Baseline → Context → Task Tool → Handoff → Workflow`？
- 除成功率之外，你还会报告哪些成本、Token、时延和失败类型指标？

## 9. P1：Provider、工具、MCP 与 Hook

这组问题与岗位方向有关。做 Agent Runtime、模型平台或工具基础设施的面试官可能
会深入；普通应用 Agent 面试通常只选其中一条。

### 9.1 Provider Adapter

- 为什么 Runtime 不直接保存 OpenAI 或 Anthropic SDK 对象？
- Runtime Message、供应商无关的 LLM Message 和 Provider Wire 如何分层？
- OpenAI Chat、Responses 和 Anthropic Messages 的工具调用差异如何统一？
- 哪些 Provider 特性必须保留，哪些可以接受能力损失？
- 请求重试为什么应该发生在进入 Runtime State 之前？
- 如何使用 Fake Provider 做确定性测试？

### 9.2 工具与安全边界

- 工具 Schema、参数校验、业务失败、异常、超时和主动终止如何区分？
- 并行工具调用如何按 Tool Call ID 配对结果，并保持稳定顺序？
- Bash 超时后如何清理子进程？
- Read/Edit 如何防止路径逃逸和工作区外修改？
- Hook 是普通回调还是强制策略边界？模型能否绕过它？

### 9.3 MCP

- MCP 在你的设计中解决了什么本地 Tool 无法优雅解决的问题？
- MCP Tool 如何适配到和本地 Tool 一样的执行语义？
- MCP 连接为什么需要 Session 管理，而不是在每次调用时临时创建？
- MCP 连接中断或 Schema 变化时，Agent 如何处理？

## 10. P1：失败案例与反事实问题

这些问题比“请解释某个类的职责”更能验证主导深度。

### 10.1 失败案例

- 讲一次最严重的上下文信息丢失：症状、证据、定位、修复和代价是什么？
- 讲一次工具结果撑爆上下文或导致模型误判的案例。
- 讲一次 Provider 差异导致的兼容性问题。
- 讲一次子 Agent 或 Workflow 反而降低效果的案例。
- 讲一次 Benchmark 结果无法解释或被基础设施问题污染的案例。
- 哪个设计在真实运行后被删除、简化或重构？

回答不能只说“提高了稳定性”或“优化了性能”，应能说明：

```text
现象 → 可观测证据 → 根因 → 修复 → 新增代价 → 修复后如何验证
```

### 10.2 高价值反事实

- 如果不使用生成器，如何仍然支持实时观察和中止？
- 如果只保存 Message、不保存 Event，会失去什么？
- 如果模型上下文足够大，还需要主动 Context 管理吗？
- 如果永远只支持一个 Provider，Adapter 仍然有什么价值？
- 如果任务没有明显并行性，多 Agent 的收益从哪里来？
- 如果不做 Benchmark，Trace 对开发和调试还有什么价值？

## 11. P2：只在岗位匹配时准备

这些问题可以体现系统设计能力，但不应作为当前简历的主线，也不能暗示当前项目
已经实现：

- 同时运行一千个 Agent 时，队列、租约、心跳和孤儿任务如何设计？
- Provider 全局限流、租户限流和单任务预算如何协调？
- 如何做多租户密钥、权限、工作区和成本隔离？
- 如何设计熔断、Fallback、人工审批和不可绕过的 Policy Enforcement Point？
- 如何处理跨进程恢复、工具幂等键和副作用重放？
- 如何在不能使用 Docker 时提高 Eval 环境可复现性？

回答这组问题时应明确说“这是合理的演进设计”，不要说成当前项目已经具备的能力。

## 12. 被降级或删除的原问题

现有版本中以下问题不是错误，但不适合作为主问题，已降级到 P1/P2 或删除：

| 原问题类型 | 处理 | 原因 |
| --- | --- | --- |
| “为什么不是 async generator？” | 降为 P1 | 简历没有把 async 作为成果，除非岗位明确要求异步运行时 |
| “Event 和 Python logging 有什么本质区别？” | 删除 | 过于概念化，真实面试更可能让你解释 Trace 如何定位问题 |
| “不可变 Message 是否造成大量复制？” | 降为 P1 | 需要先出现性能或内存证据，否则不是高概率追问 |
| “为什么不是 OpenTelemetry / 关系数据库？” | 降为 P1 | 只有在讨论规模、生态或生产落地时才有价值 |
| “模型上下文无限大还需要上下文管理吗？” | 保留为反事实 | 能验证你是否理解信息选择不只是窗口大小问题 |
| “如果要同时运行一千个 Agent 怎么办？” | 降为 P2 | 当前简历没有分布式规模证据，首轮询问会偏离项目事实 |
| “如何做多租户治理、Fallback、熔断？” | 降为 P2 | 属于岗位相关系统设计，不是当前项目已证明能力 |
| 逐一解释 PDR、Reflection、Router 的定义 | 删除逐项背诵 | 面试官更关心一个真实场景中的价值、失败和成本 |
| 逐一审问所有 Provider wire 字段 | 删除 | 细节应服务于一个兼容性问题，不应变成 API 记忆题 |
| “Viewer 为什么不能反向控制 Runtime？” | 保留但合并 | 作为 Trace 事实源与控制面分离的追问即可 |

## 13. 最终优先级清单

如果准备时间有限，按以下顺序准备：

1. 两分钟项目介绍，以及个人贡献边界。
2. 一个真实任务的完整 Agent Run。
3. 模型完成与外部完成检查的区别。
4. 为什么需要 Message / Event / State / Context 分层。
5. 压缩、Recall、Memory、Skills、Handoff 的生命周期边界。
6. 一个上下文失败案例，以及如何通过 Trace 定位。
7. Task Tool 与固定 Workflow 的区别，子 Agent 为什么独立 State。
8. 一个多 Agent 方案的收益或失败案例。
9. Suite、Backend、ArtifactStore 如何支撑可复现实验。
10. 三项 Benchmark 的原始分数、Baseline、绝对提升、相对提升和限制。
11. 没有消融时，结果能证明什么、不能证明什么。
12. Provider 或工具层中你最熟悉的一条真实工程问题。

## 14. 一道贯穿式案例题

正式面试前，应准备一个真实任务并能连续回答：

1. 任务的外部完成标准是什么？
2. 任务怎样进入 State 和模型上下文？
3. 第一轮模型实际看到了什么？
4. 为什么选择某个工具，工具结果如何进入下一轮？
5. 什么时候触发压缩？被压缩的信息如何恢复？
6. 是否发生子 Agent 委派？父子 State 如何隔离？
7. Agent 为什么停止？谁验证任务完成？
8. Trace 保存了哪些证据？
9. Eval 如何运行、提取结果和评分？
10. 失败时如何判断是模型、工具、Runtime、环境还是评分器的问题？
11. 最终成本、Token、时延和分数如何统计？
12. 哪些结论是代码事实，哪些是实验结论，哪些只是设计判断？

这个案例必须来自真实运行。不要虚构线上规模、生产事故、消融数据或个人贡献。

## 15. 自我检查标准

对于简历中的每个高风险名词，至少检查：

- 能否先解释它解决的真实问题，而不是先背定义？
- 能否画出输入、输出、事实源和上下游？
- 能否写出最小伪代码或时序？
- 能否说明正常、失败、停止和恢复语义？
- 能否讲一个真实失败案例？
- 能否比较一个更简单的替代方案？
- 能否给出验证方式和实验口径？
- 能否明确自己负责和没有负责的部分？
- 能否区分“机制存在”和“机制带来收益”？
- 能否明确当前系统没有解决的生产问题？

如果一个名词无法通过这套检查，应从简历中删除或降低表述强度，而不是只准备一句
定义。
