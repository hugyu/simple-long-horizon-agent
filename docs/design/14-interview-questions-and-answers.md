# 14. 无代码上下文的面试问题与模拟回答

> 本篇假设面试官只看过简历上的项目描述，并听过候选人的口头介绍，无法查看
> 仓库和具体实现。问题停留在项目目标、系统行为、架构取舍、验证结果和个人决策
> 层面；只有候选人主动引入某个内部概念后，追问才继续深入。

## 1. 使用边界

本篇所有回答都是模拟口径。项目事实以现有设计文档和实验结果为准；个人贡献
部分假设候选人负责“核心架构与评测闭环”，必须按真实经历修改。

适合无代码上下文的提问包括：

- 项目解决什么问题，为什么值得做；
- 一次任务如何流过系统，各模块如何分工；
- 为什么采用当前边界，替代方案有什么代价；
- 长任务、失败、安全和评测如何处理；
- 结果能证明什么，不能证明什么；
- 候选人做了什么决策，如何验证并复盘。

默认不问某个函数为何这样写、某个字段如何变化、某个测试覆盖哪一行，也不要求
候选人背诵目录结构。回答应先在 30～90 秒内讲清结论；面试官继续追问时，再补充
数据流、不变量、失败路径和证据。

## 2. 项目介绍与价值

### Q1. 请用一两分钟介绍一下这个项目

**模拟回答：**

Simple Long Horizon Agent 是一个面向学习、实验和真实多步骤任务的小型 Agent
Runtime。它解决的问题是：任务无法在一次模型回答里完成时，系统怎样让模型持续
规划、调用工具、观察结果、修正方案并接受外部验证，同时保持整个过程可理解。

项目把模型访问、工具、运行状态、上下文管理、工作流、轨迹和评测拆成明确边界。
核心仍是一套显式循环，复杂能力通过组合加入。它已经在软件工程、终端任务和自动
模型后训练三类长周期 Benchmark 上发布结果，因此不只是教学示例，也能用于真实
实验；但它不是生产级多租户平台或完整安全沙箱。

### Q2. 你说的“长周期任务”与普通聊天有什么本质区别

**模拟回答：**

普通聊天主要优化单次生成质量；长周期任务必须管理一个持续变化的外部世界。
模型要多次行动，每次都可能失败，还要在有限上下文里保留任务目标、关键证据和
当前进度。系统同时需要停止预算、错误反馈、上下文压缩、结果验证和可追溯轨迹。

所以难点不只是“允许多轮”，而是让多轮行动有状态、有边界、可恢复、可解释，
并且最终完成由外部事实确认，而不只依赖模型说“我完成了”。

### Q3. 这个项目主要面向谁

**模拟回答：**

第一类是希望看懂完整 Agent 循环的学习者和教学者；第二类是需要快速改造工具、
模型或工作流的小团队；第三类是需要真实轨迹和可重复运行的研究、评测人员。

项目优先级也由此决定：先保证概念清楚、边界可替换、实验可验证，再考虑生产级
吞吐、多租户控制面和复杂的隐式插件体系。

### Q4. 市面上已经有很多 Agent 框架，为什么还要做一套

**模拟回答：**

这个项目不是为了覆盖更多集成，而是为了让最关键的行为可以被检查和修改。大型
框架通常能减少接线工作，但模型循环、状态转换、重试和上下文策略可能藏在多层
抽象里，不利于教学和精确实验。

我们的取舍是保留少量项目自有协议和唯一的核心运行模型，再把 Provider、Tool、
Memory、Workflow 和 Eval 放在外围边界。代价是需要自行维护一些基础设施；收益是
能清楚说明一次行为为何发生，也能只替换一个变量做实验。

### Q5. 你如何判断这个项目做成功了

**模拟回答：**

我会看三类信号。第一是认知信号：新人能否解释核心循环和模块边界；第二是工程
信号：模型、工具、上下文策略和执行环境能否独立替换，并用确定性测试验证；第三
是效果信号：长任务能否在受控预算下运行，留下可分析轨迹，并由官方评测器评分。

Benchmark 总分证明组合方案在指定配置下有效，但它不能替代前两类信号，也不能
自动证明每个组件都有正向贡献。

## 3. 总体架构与运行机制

### Q6. 不看代码，你会怎样描述系统架构

**模拟回答：**

我把系统分成六个协作部分：运行核心维护任务循环；模型边界负责不同 Provider 的
输入输出转换；工具边界负责对外行动；上下文层控制模型当前能看到什么；工作流层
组合子 Agent 和多阶段任务；轨迹与评测层记录事实并验证结果。

依赖方向是从外围能力指向稳定核心。Provider 对象、Benchmark 数据和容器细节不
进入核心状态。这样系统可以换模型、工具或执行位置，而不改变任务循环的语义。

### Q7. 一个任务从进入系统到最终结束，经历哪些步骤

**模拟回答：**

任务先被记录为运行事实。每一轮开始时，系统根据完整历史生成受预算约束的模型
可见上下文，然后调用模型。模型可以给出最终回答，也可以提出工具调用。工具调用
经过校验和策略检查后执行，结果被记录并反馈到下一轮。

循环持续到模型正常完成、工具要求终止、外部中止或预算耗尽。整个过程中，模型
请求、响应、工具行动、压缩和停止原因都留下事件，后续轨迹和评分从这些事实派生。

### Q8. 为什么要区分“消息、事件和状态”，直接保存聊天记录不够吗

**模拟回答：**

聊天消息只描述模型可见对话，不能完整表达超时、工具执行过程、上下文压缩、成本
或外部停止。事件记录“发生过什么”，消息是其中一类模型可见事实，状态则是根据
事件得到的当前投影。

这个区分让系统既能重建模型当时看到了什么，也能解释那些不应该直接暴露给模型
的运行事实。它还避免 Trace、终端日志和 Runtime 各维护一份容易漂移的真相。

### Q9. 为什么要自己拥有消息协议，而不是直接保存模型厂商的响应

**模拟回答：**

不同厂商对角色、工具调用、图片、思考内容和流式事件的表达不同。如果把厂商对象
直接放进核心状态，换 Provider 会影响 Runtime、Trace、Memory 和 Eval。

项目先用自己的中立语义描述消息和工具交互，只在模型边界转换为厂商格式。这样
会损失一部分厂商特有便利，但可以保留原始响应作为边界证据，同时让核心行为保持
可移植和可测试。

### Q10. Agent 说任务完成了，系统为什么不能直接相信它

**模拟回答：**

模型的 final 只表示“模型认为完成”，不代表代码通过测试、环境达到目标或官方
评分器认可。项目把模型完成与外部完成分开：模型先给出候选结果，外部 Goal、测试
或 Scorer 再确认；失败反馈可以进入下一轮继续修正。

这样可以区分生成结束、工具终止、预算耗尽和真正目标完成，避免把语言声明当作
环境事实。

### Q11. 为什么核心循环强调简单和显式，功能会不会因此受限

**模拟回答：**

核心循环只负责所有 Agent 都共有的观察、生成、行动、反馈和停止。压缩、Memory、
子 Agent、实时轨迹和评测通过明确入口组合，不需要把每项能力写进循环。

简单不等于功能少，而是每种复杂度要有唯一所有者。它的限制是某些高级编排需要
更多显式接线；好处是行为、失败和测试边界不会被一个万能抽象掩盖。

## 4. 上下文与长周期能力

### Q12. 长任务最核心的上下文矛盾是什么

**模拟回答：**

完整历史越多，可追溯性越好；但模型窗口有限，把全部历史持续注入会增加成本并
最终溢出。若简单删除旧消息，又会失去关键证据和 Debug 能力。

项目的解决思路是把“已经发生的完整历史”和“本轮让模型看到的活跃上下文”分开。
完整事实保留，活跃视图可以压缩或重组，必要时再有界恢复精确信息。

### Q13. 你如何向面试官解释完整历史、活跃上下文和模型输入的区别

**模拟回答：**

完整历史是审计账本，记录本次运行发生过的消息；活跃上下文是系统当前选中的历史
投影；模型输入是在活跃投影基础上，再结合 Provider 格式和本轮工具声明形成的实际
请求。

三者分开后，压缩只改变模型当前视野，不删除审计证据；同时也能精确回答某一轮
模型到底看到了什么，而不是拿最终聊天记录反推。

### Q14. 压缩上下文会不会丢失重要信息

**模拟回答：**

摘要一定有损，所以设计目标不是承诺“绝不丢语义”，而是控制损失并保留恢复路径。
任务目标、系统约束、最近交互和工具调用/结果配对应被保护；摘要要能指向原历史，
原消息本身不被删除。

如果后续需要精确值，Agent 可以按稳定索引有界 Recall。压缩失败时应保留原视图，
不能用空摘要或损坏结构继续运行。

### Q15. Recall 与 Memory 有什么区别

**模拟回答：**

Recall 恢复的是“本次运行前面发生过什么”，来源是当前运行的完整历史；Memory
保存的是“以前的运行沉淀了什么经验”，生命周期跨越多个任务。

Recall 更接近审计检索，可信度来自当前 transcript；Memory 是外部知识，可能过时，
所以涉及当前代码、配置和环境时必须重新核验。把二者混在一起会模糊来源和新鲜度。

### Q16. Skills、Memory 和上下文压缩为什么不统一成一个记忆模块

**模拟回答：**

它们回答不同问题。压缩决定当前请求带多少历史；Recall 找回本次运行的旧证据；
Skills 提供这类任务通常怎么做；Memory 保存过去运行学到的经验。

它们的来源、写入时机、可信度和失效方式都不同。统一接口看起来简洁，却会让模型
无法判断信息是实时事实、历史摘要还是可能过时的方法知识。

### Q17. Handoff 与压缩是什么关系，为什么需要两种方式

**模拟回答：**

压缩在同一运行视图里用摘要替代部分旧内容；handoff 则让模型生成可继续工作的
持久说明，再用更小的上下文窗口继续。前者适合持续保留结构化历史，后者适合上下文
已接近窗口上限、需要明显重置时使用。

两者都必须保留原始轨迹并记录切换原因。它们是可比较策略，不应同时被描述成某个
结果提升的确定原因，因为当前没有组件级消融数据。

## 5. 工具、子 Agent 与工作流

### Q18. 模型怎样安全、可控地作用于真实环境

**模拟回答：**

模型不能直接改变环境，只能提出结构化工具调用。工具边界负责参数校验、权限或
Hook 检查、超时、执行和结果封装。成功或失败都会形成与调用身份配对的反馈，再由
模型决定下一步。

这提供的是清楚的能力边界，不等于完整安全沙箱。真正的文件、命令和网络权限仍需
宿主或容器强制限制。

### Q19. 工具调用失败时为什么要把错误反馈给模型，而不是直接抛出异常

**模拟回答：**

工具参数错误、未知工具或命令失败通常属于任务过程的一部分，模型可能根据错误修正
方案。把它们转换成结构化结果，可以保持调用与反馈配对，也让下一轮和 Trace 看见
真实失败。

只有无法继续的基础设施或程序错误才向调用者传播。关键是按故障边界分类，而不是
把所有错误都吞掉，或对所有错误统一重试。

### Q20. 多个工具并行执行时，如何保证结果可解释

**模拟回答：**

执行可以并发，但模型看到的结果按原始调用顺序组装，每个结果仍引用自己的调用
身份。这样完成顺序不会改变下一轮上下文，也便于复现实验。

不能安全并发的工具会声明顺序约束；同组存在这类工具时应串行，避免共享终端、
编辑会话或外部资源发生竞态。

### Q21. 为什么把子 Agent 设计成一种工具能力

**模拟回答：**

父 Agent 已经会通过工具表达“我需要一个外部能力并等待结果”。把子 Agent 放在
同一交互语义中，就能复用参数校验、执行事件、错误结果和下一轮反馈，不需要在核心
循环增加第二种委派协议。

子 Agent 有独立状态和上下文，最终只把有界结果返回父 Agent；完整子轨迹用于观察，
不会默认塞回父模型窗口。

### Q22. 什么时候用单 Agent，什么时候用 Workflow 或多个 Agent

**模拟回答：**

默认先用单 Agent，因为协调本身有 Token、延迟和信息损失成本。只有任务存在明确
阶段、可并行子问题、专业角色或需要独立批评/验证时，才引入组合。

确定流程适合显式 Workflow；运行中才知道是否需要专项能力时适合工具委派。选择
标准不是“Agent 越多越强”，而是新增协调成本是否换来了隔离、并行或验证价值。

### Q23. 多 Agent 如何避免状态互相污染

**模拟回答：**

每个子运行拥有独立的消息、事件、上下文预算和停止原因。父子之间通过明确任务和
结果传递信息，不共享可变 transcript，也不直接拼接所有历史。

只读配置或受控外部资源可以共享，但所有权和生命周期必须明确。全局 Trace 可以
在展示层合并父子过程，不能为了展示去修改各自的运行事实。

## 6. 可观测性、评测与实验结果

### Q24. 你怎么知道 Agent 为什么成功或失败

**模拟回答：**

系统记录模型当时看到的输入、模型输出、工具调用与结果、上下文压缩、耗时、usage
和停止原因。事件是原始事实，再派生 transcript、Span、成本和训练分析视图。

因此可以沿时间线定位是模型判断、工具执行、上下文管理、预算还是基础设施导致了
结果，而不是只看最后一句回答或一段终端日志。

### Q25. 普通日志为什么不够

**模拟回答：**

日志为人即时阅读，格式会变化，也容易缺失结构化身份和模型实际输入。长任务还有
压缩、并发工具和子 Agent，仅靠文本顺序很难恢复真实因果关系。

事件流保存稳定语义，日志和 Viewer 都是它的视图。这样观察产品可以演进，Runtime
不需要同时维护多份事实。

### Q26. 你如何保证一次评测可复现

**模拟回答：**

分数必须关联任务身份、模型与推理设置、Agent 配置、turn/时间/并发预算、执行
环境、轨迹、结果产物、评分方式和基础设施异常。只保存最终百分比不算可复现。

同时要区分 Agent 失败、评分未通过和基础设施故障。只有暂时的基础设施异常适合按
策略重试，不能把任务失败反复运行到成功。

### Q27. 如何防止 Benchmark 的标准答案泄漏给模型

**模拟回答：**

公开任务输入和私有评分输入属于不同边界。模型和 Agent 只接触完成任务所需的公开
部分；gold、测试密钥或官方评分数据留在评分环境或 Host 侧。

结果通过结构化 artifact 交给评分器，而不是把私有字段放进 prompt。Trace 也不能
因为便于 Debug 就把 gold 数据混入模型可见内容。

### Q28. 项目的实验结果怎样，应该如何表述

**模拟回答：**

已发布结果有三项。SWE-bench Pro 使用 GPT-5.4 xHigh，达到 63.20%，同模型同预算
Baseline 为 59.10%，绝对提升 4.10 个百分点，相对提升 6.94%，成本每任务
7.7823 美元。Terminal-Bench 2.1 使用 GPT-5.3-Codex xHigh，达到 77.53%，相比
64.70% 高 12.83 个百分点，相对提升 19.83%，成本每任务 0.5667 美元。

PostTrainBench 使用 GPT-5.5 xHigh，结果 45.88%，Baseline 43.97%，绝对提升
1.91 个百分点，相对提升 4.34%，成本尚未发布。回答时要区分百分点和相对百分比。

### Q29. 这些提升主要来自哪个模块

**模拟回答：**

当前证据只能证明指定配置下的组合方案优于列出的 Baseline，不能做组件级因果归因。
Task Tool、handoff、压缩和 Workflow 都有合理机制假设，但没有发布逐项消融结果。

如果要回答归因，我会固定模型、任务集合、预算和并发，只切换一个变量，使用同一批
任务做 paired 比较，并报告方差或置信区间。在此之前，我会明确说“这是机制假设，
不是实验结论”。

### Q30. 你能讲一个典型成功或失败案例吗

**模拟回答：**

当前设计文档没有绑定真实 instance id 的案例复盘，所以我不会临场编造。现阶段
可以讲分析方法：按定位、规划、工具执行、上下文、验证和预算阶段给轨迹分类，再选
一条真实成功轨迹和一条失败轨迹，说明关键决策、证据和可改进点。

正式面试前应补一条自己真正分析过的案例。如果没有做过，就应直接承认材料缺口，
而不是把一般性故障模式包装成项目事实。

## 7. 可靠性、安全与性能

### Q31. 系统如何处理故障和重试

**模拟回答：**

恢复策略按边界区分。Provider 暂时限流可以有限退避；非法工具调用可以让模型有限
修正；工具异常变成模型可见错误结果；评分未通过属于有效业务结果；容器或网络等
基础设施异常才由 Eval 层决定是否重试。

这种分类避免一个全局 retry 重复执行有副作用的操作，也保留了每类失败的真实语义。

### Q32. 进程突然崩溃后能否从原位置无损恢复

**模拟回答：**

当前不能做这个承诺。系统支持从调用者提供的运行状态继续，也有部分长运行的提交与
协调恢复能力，但还没有完整定义进程级 checkpoint、外部副作用幂等、schema 迁移和
exactly-once 语义；部分 chain 运行也明确要求使用新 run id 重启。

要补齐，需要 turn 边界 checkpoint、稳定 operation id、工具幂等声明、artifact
一致性检查和故障注入。现有能力应描述为“可恢复错误有分层处理”，不是“任意崩溃
都能无损续跑”。

### Q33. 这个 Agent 能执行命令和读写文件，如何保证安全

**模拟回答：**

Runtime 提供工具输入校验、超时、输出预算和高风险调用 gate，但项目明确不是通用
安全沙箱。真正的安全边界必须在模型之外实施，例如临时 workspace、容器非 root、
最小挂载、网络 allowlist、短期凭证、资源 quota 和人工审批。

安全结论要与部署环境绑定。若宿主给 Agent 任意文件和命令权限，Runtime 不能仅靠
prompt 防止越权。

### Q34. Prompt injection 怎么处理

**模拟回答：**

首先把仓库、网页和工具返回都视为不可信内容，不能让其中的自然语言直接升级权限。
其次把强控制放在工具和宿主边界：参数与路径策略、权限 allowlist、高风险审批、
秘密隔离和网络限制。

当前项目没有发布完整 prompt injection 防御和攻击测试，因此我会把这些描述为需要
补齐的威胁模型，而不是宣称已经解决。真正有效的验证应包含恶意仓库、路径逃逸、
秘密外传和资源耗尽用例。

### Q35. 系统性能和容量怎么样

**模拟回答：**

我们有实际运行配置，例如 Terminal-Bench 使用过 10 个 trial 并发，但没有发布
p95、吞吐、RSS、最大稳定并发或 soak test，所以 10 不能被当作容量上限。

我会用轨迹把排队、模型、工具/环境和评分耗时拆开，再做阶梯并发，观察吞吐、p95、
错误率、资源和单位任务成本。容量定义应是目标延迟与错误率内的最大并发，而不是
进程尚未崩溃时的线程数。

### Q36. 如果要把它用于生产，还缺什么

**模拟回答：**

至少还需要完整威胁模型和强制沙箱、密钥与租户隔离、容量基准和 SLO、持久化状态
与崩溃一致性、幂等副作用、审计与保留策略、告警、升级兼容和灾难恢复。

当前架构可以作为核心 Runtime 和实验基础，但不应因为能跑容器和 Benchmark 就声称
已经是生产平台。生产化更适合在外围增加控制面，而不是把所有运维复杂度塞进核心
循环。

## 8. 取舍、演进与扩展

### Q37. 这个项目最关键的设计取舍是什么

**模拟回答：**

最关键的是把完整事实与模型当前视图分开。只保存全量历史会耗尽窗口，只保存摘要
又失去证据；最终选择追加保存原始事件，同时让活跃上下文可压缩、可恢复。

这项决定同时影响 Runtime、Trace、Memory、Workflow 和 Eval，复杂度不低，但它让
长任务的成本控制和可解释性不再互相排斥。

### Q38. 你怎样描述这套方案的演进

**模拟回答：**

按逻辑可以分五步：先建立最小显式循环；再隔离模型和工具边界；随后加入完整历史、
压缩与 Recall 支撑长任务；再通过独立 State 组合子 Agent 和 Workflow；最后从事件
派生 Trace、成本和 Eval，形成验证闭环。

这是一条根据当前架构整理的逻辑叙事，不是已经核验的历史时间线。正式回答还要用
真实 commit、PR 或决策记录校正阶段顺序和个人参与范围。

### Q39. 如果增加一个新模型供应商或新工具，会影响哪些部分

**模拟回答：**

新 Provider 应在模型边界完成请求、响应、流式事件、usage 和错误映射，不让厂商
对象进入核心状态。新工具只需声明能力、校验输入、管理外部资源，并把所有结果转成
统一反馈。

两种扩展都要先定义反馈信号：Provider 用协议转换和错误分类测试，Tool 用成功、
异常、超时和终止测试。只有跨越稳定语义时才修改核心协议。

### Q40. 如何防止项目随着功能增加变成另一个重框架

**模拟回答：**

每项新能力先回答三个问题：它是否解决已出现的问题，谁拥有状态和生命周期，能否
通过现有边界组合。如果只是某个 Provider、Benchmark 或部署环境的特殊需求，就留在
外围模块，不提升为核心概念。

同时坚持唯一核心循环、单向依赖、可选依赖隔离和窄测试。复杂度必须能用明确收益
解释，而不是因为“以后可能需要”提前抽象。

### Q41. 如果继续做，你优先补什么

**模拟回答：**

第一优先是实验归因：补 Task Tool、handoff 和 compression 的配对消融，并加入实例
级成败轨迹。第二是可靠性：明确 fatal exception、checkpoint 和副作用幂等语义。
第三是工程边界：补容量曲线和威胁模型。

这个顺序先解决“为什么有效”，再解决“失败后怎么办”，最后回答“在多大负载和什么
威胁下可用”。它比立即扩展更多 Provider 或 Workflow 更能提高项目可信度。

## 9. 个人贡献类问题

> 以下回答假设候选人负责核心架构与评测闭环。仓库文档不能证明个人归属，使用前
> 必须替换为真实职责、产出、协作者和复盘证据。

### Q42. 你个人在项目里负责什么

**模拟回答：**

我的主责是核心架构与评测闭环，具体包括定义模型、工具、状态和编排之间的边界，
设计长上下文的压缩与恢复语义，并把运行事件打通到轨迹、成本和官方评测。

我不会把最终 Benchmark 分数全部归为个人贡献。个人价值需要用自己实际做出的设计
决策、实现、测试、实验配置和问题复盘来证明；模型能力、官方评分器和协作者成果要
清楚分开。

### Q43. 你解决过最难的技术问题是什么

**模拟回答：**

最难的是有限上下文与完整证据的冲突。直接截断会让 Agent 和人都无法恢复旧事实，
全量保留又无法支持长运行。我推动把完整历史、活跃视图和模型输入分层，压缩只改
视图，原始事件不删除，再用有界 Recall 恢复精确信息。

这里应补上本人真实负责的方案比较、验证方式和一次实际问题。若没有相关个人证据，
应把“我推动”改为“我参与设计”并说明具体动作。

### Q44. 你做过一个有争议或需要权衡的决定吗

**模拟回答：**

一个典型取舍是没有引入独立的多 Agent Runtime，而是让子 Agent 复用普通运行并以
工具结果返回。反对意见可能是专用调度器更灵活；我的判断是当前目标更重视语义一致、
状态隔离和可观察性，专用 Runtime 会产生第二套停止、错误和轨迹协议。

最终保留显式 Workflow 处理确定编排，把动态委派放进工具边界。回答时还应补充真实
讨论参与者、替代方案和验收信号，不能只讲事后看来合理的结论。

### Q45. 项目中有什么失败或遗憾，你学到了什么

**模拟回答：**

当前最大的材料缺口是有端到端结果，却缺组件消融、真实案例和不确定性分析。这使
我们能证明组合方案有效，却难以回答提升来自哪里。我的反思是反馈信号不应只定义为
最终总分，设计组件时就应同时规划对照组和实例级分析维度。

工程上，进程级恢复和完整威胁模型也没有闭环。正式面试最好换成自己真正经历的
失败：说明当时错误判断、发现证据、采取动作和后续机制，而不是只列项目 TODO。

### Q46. 面试官为什么应该认可你的项目贡献

**模拟回答：**

我希望被认可的不是“接了一个模型 API”，而是把长任务中的状态、上下文、工具、
验证和评测组织成一套边界清楚的系统，并能说明每个取舍的收益和限制。

最有说服力的证据应是三件事：一个本人负责的关键设计及替代方案、一条真实失败的
定位与修复记录、一组本人运行和解释过的实验结果。当前文档只提供回答结构，这三类
个人证据仍必须由本人补齐。

## 10. 压力追问

### Q47. 你一直强调“简单”，但项目模块很多，这不是自相矛盾吗

**模拟回答：**

简单指核心运行模型和职责边界简单，不是文件或能力数量少。长任务客观需要模型、
工具、上下文、观察和评测；把它们混成一个万能 Agent 对象，表面模块少，理解和修改
成本反而更高。

我判断复杂度是否合理的标准是：每个模块是否拥有独立变化原因，能否单独替换，删除
后是否会破坏明确能力。解释不了收益的抽象不进入核心。

### Q48. 没有消融实验，你凭什么说架构有效

**模拟回答：**

我会区分两种有效。端到端 Benchmark 相比同模型同预算 Baseline 有提升，能说明
整套配置有效；组件消融缺失，意味着不能说明每个模块分别贡献多少。这两个判断并不
冲突。

架构边界的价值还可以由确定性行为、可替换性和轨迹完整性验证，但若问题是“哪个
组件提高了分数”，只有控制变量实验才能回答，我不会用架构直觉替代数据。

### Q49. 如果只能保留三个能力，你保留什么

**模拟回答：**

我会保留显式运行循环、统一工具反馈和追加式事件状态。循环提供持续行动，工具反馈
让模型作用于环境并修正错误，事件状态提供上下文、观察和后续扩展的事实基础。

压缩、Memory、多 Agent 和 Eval 都很重要，但它们可以在这三个稳定基础上逐步增加；
如果连基础行动和事实语义都不稳定，上层能力只会放大不确定性。

### Q50. 这个项目最大的边界或风险是什么

**模拟回答：**

最大的边界是它仍是学习与实验 Runtime，不是生产控制面。它能让 Agent 行为更清楚、
有界和可评测，却不能保证模型始终正确，也不能替代宿主沙箱、租户隔离、容量治理和
灾难恢复。

最大的面试风险则是把机制假设说成实验归因，把设计方案说成现有能力，或把团队结果
说成个人贡献。我的回答会始终把已有证据、当前缺失和下一步验证分开。

## 11. 面试前检查

在使用本题库前，应确认自己能够：

1. 在两分钟内完成 Q1，不堆砌模块名；
2. 不看文档准确说出三项结果，并区分绝对百分点和相对提升；
3. 用一个任务流程解释架构，而不是背目录；
4. 清楚区分压缩、Recall、Skills 和 Memory；
5. 对消融、容量、安全和崩溃恢复缺口保持同一口径；
6. 为 Q30、Q42～Q46 换入真实案例和个人证据；
7. 遇到未知问题时先界定证据，不临场编造数字、案例或所有权。
