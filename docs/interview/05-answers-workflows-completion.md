# 05. Workflow 与完成判断

本文对应 [`question-checklist.md`](question-checklist.md) 中第五部分的问题。每道题包含可直接
口述的主回答；存在清单子问题时，保留追问原文和简短回答；最后记录整组问题对应的仓库实现。

## 46. 什么时候应该创建子 Agent？

### 口述主回答

当子任务相对独立、需要不同提示词或工具，或者可以并行探索时，我会考虑创建子 Agent。项目里
父 Agent 通过 `task` 工具选择已注册的子 Agent，子 Agent 使用普通 Runtime 独立完成任务，再把
结果返回父 Agent。

收益是上下文和职责更聚焦，也能隔离不同角色。代价是增加模型调用、上下文传递和结果合并成本；
如果任务强依赖共享状态、步骤很短或需要频繁往返，多 Agent 反而不如单 Agent 直接执行。

### 追问问题与回答

**追问：Sub-Agent 相比单 Agent 的收益是什么？**

它能隔离上下文、提示词和工具，让专门角色聚焦独立子任务，也便于并行探索和单独审计。

**追问：哪些情况下 Multi-Agent 反而比 Single-Agent 更差？**

任务很短、强依赖共享状态、需要频繁来回沟通，或委派和汇总成本高于任务本身时，多 Agent 会更差。

### 技术追问补充

- `task_tool(agents)` 在构造时校验子 Agent 列表，并按名称建立固定注册表；重复名称直接拒绝。
- 工具 Schema 中的 `subagent_type` 是注册名称枚举，父模型只能选择已登记的 Agent，不能动态导入。
- 每次委派调用选中 Agent 的普通 `agent.run()`，父 Runtime 不理解子 Agent 的内部 Turn。
- 当前没有自动判断“何时值得委派”的规则，是否调用 `task` 由父模型和 Prompt 决定。

## 47. 子 Agent 是否拥有独立上下文？

### 口述主回答

是的。`task` 工具会为选中的子 Agent 调用一次新的 `agent.run()`，因此它拥有独立的 State、
消息历史、压缩索引和事件流，不会把父 Agent 的完整对话直接复制过去。

父 Agent 传递的是明确子任务和可选背景说明。子 Agent 返回给父模型的是最终文本；完整子事件放在
工具结果的本地详情中，供 Trace 合并，不会全部塞回父 Agent 上下文。

### 追问问题与回答

**追问：Parent Agent 应该向 Child Agent 传递哪些任务、背景和约束？**

应传递自包含子任务、完成标准和必要背景，不直接复制父 Agent 的完整对话历史。

**追问：Child Agent 应该向 Parent Agent 返回最终文本、结构化结果，还是完整 Trace？**

当前默认返回最终文本；完整 Trace 作为本地详情保存。需要机器消费时，应为该工具定义明确的
结构化结果协议。

### 技术追问补充

- `task_tool` 的输入字段是 `subagent_type`、`task` 和可选 `context`；task 会成为子 State 的
  task Message，context 会在第一轮前记录为 `kind="context"` RuntimeMessage。
- 子 Agent 每次创建新 State，因此拥有独立 messages、events、Snapshot 和压缩上下文。
- 工具从子 State 中提取最后一条 `kind="final"` Message 文本作为父模型可见 ToolResult。
- 子 State 的完整事件列表保存在 `ToolResult.details["sub_events"]`，供 Trace 合并，不进入普通
  模型正文。

## 48. 子 Agent 能否调用父 Agent 的全部工具？

### 口述主回答

不会自动继承。每个子 Agent 在创建时已经绑定自己的工具集合、提示词和上下文策略，`task` 工具
只是从注册表选择并运行它。

因此工具权限应在子 Agent 组装阶段按最小权限配置。工作目录、MCP 连接和外部凭据也应按子任务
隔离，不能因为父 Agent 有权限就默认传给子 Agent。

### 追问问题与回答

**追问：Child 的 Toolset、权限和运行环境应该如何隔离？**

子 Agent 应独立绑定完成子任务所需的最小工具、凭据和工作目录，不自动继承父 Agent 的全部能力。

### 技术追问补充

- `task_tool` 接收的是已经组装完成的 Agent 对象，运行时直接使用该 Agent 自身的 tools、hooks 和
  `context_policy`，不会读取父 Agent 工具表。
- Bash、Read、Edit 等工具的工作目录在构造时闭包绑定；父子是否共享目录取决于调用者如何组装。
- MCP 等有生命周期资源由各自 Session/Toolset 管理，不会因为父 Agent 已连接就自动传给 Child。
- 当前没有统一权限继承协议；最小权限依赖 Builder、Session、Hook 和外部运行环境共同落实。

## 49. 子 Agent 可以继续创建自己的子 Agent 吗？

### 口述主回答

可以，只要子 Agent 自己也绑定了 `task` 工具。当前项目只限制每次子运行的回合数，并把父级的
中止信号传下去，还没有限制整棵委派树的深度、调用次数和总消耗。

如果允许递归委派，我会从根 Agent 创建一份共享的委派上下文，记录当前深度、祖先链、剩余委派
次数、回合和 Token 预算以及总截止时间。每次 `task` 工具准备启动子 Agent 时，先检查深度和祖先
环路，再从共享账本中预留本次预算；检查或预留失败就直接返回错误工具结果，不创建新的子 State。

子 Agent 继续委派时必须继承同一份上下文，不能重新获得一套完整预算。运行结束后再根据实际消耗
结算并归还未使用额度。这样单个子 Agent 仍有自己的独立 State，但整棵委派树共享一个控制预算；
根级取消也能传播到所有后代，避免通过不断创建新 Agent 绕过限制。

### 追问问题与回答

**追问：如何限制委派深度、调用次数和预算，防止无限递归？**

根 Agent 创建共享委派账本；每次启动子 Agent 前原子检查深度、祖先环路和剩余预算并预留额度，
子 Agent 继承同一账本。超限时返回明确错误，不再继续创建后代。

### 技术追问补充

- 只要 Child 自身 tools 中再次包含 `task`，它就可以继续委派；核心 Runtime 不区分委派层级。
- `task_tool(max_turns=...)` 为单次子运行设置硬上限；`soft_turn_limit` 只在指定 Turn 后注入一次
  剩余回合提醒，不增加额外模型 Turn。
- 父调用的 abort flag 会传入子 `agent.run()`，可中止当前委派链上的运行。
- 可以新增共享 `DelegationContext`，包含委派路径、当前深度、最大深度、剩余调用次数、全局回合
  和 Token 预算、截止时间以及共享中止信号；它属于控制面，不合并父子 State。
- `task` 工具应在调用 `agent.run()` 前执行“检查并预留”。并行分支必须在锁内或通过原子操作更新
  账本，先预留最坏预算，避免多个分支同时通过检查后共同超额。
- 子运行结束后，从其 Event 和 usage 统计实际回合与 Token，结算预留额度并归还未使用部分；异常
  或取消也必须在 `finally` 中完成结算。
- 祖先链使用稳定 Agent 身份或委派节点编号。默认拒绝再次选择祖先中的 Agent，防止
  A → B → A 环路；确需循环工作流时应由显式 Workflow 控制，而不是开放递归工具调用。
- 深度、次数或预算不足时，`task` 工具返回 `is_error=True` 的结构化结果并记录拒绝原因，使父模型
  可以改为自己完成、缩小子任务或停止，而不是静默截断。
- 子事件当前已经保存在 `ToolResult.details["sub_events"]` 中，可用于递归 Trace 和事后用量统计；
  扩展后的共享账本负责执行前控制，两者不能互相替代。
- 当前没有 `max_depth`、全局委派计数或跨 State Token 账本；可复用现有 `max_turns`、abort、
  `sub_events` 和独立 State，新增共享委派上下文与原子预算结算。

## 50. 父子 Agent 同时修改同一个仓库时如何避免冲突？

### 口述主回答

独立 State 只能隔离消息和事件，不能隔离文件系统，所以我不会让父子 Agent 并发写同一个规范
工作区。简单的强依赖任务直接串行，并在父子之间显式移交写权限；真正需要并行时，每个写入者都从
同一个基线提交创建独立 worktree。

子 Agent 不直接把修改写回主工作区，而是返回基线提交、补丁或临时提交、修改文件列表以及验证
结果。父 Agent 也不负责边运行边随意合并，我会设置一个单独的集成阶段，按照确定顺序逐个应用
修改。应用前检查主工作区是否已经偏离基线；出现冲突就保留双方改动并返回冲突信息，不能按完成
顺序覆盖。

每次集成后先运行受影响范围的检查，全部修改合并完成后再运行最终验证。这样规范工作区始终只有
一个写入者，子 Agent 可以并行探索，但最终进入主分支的内容仍然经过串行、可审查的提交过程。

### 追问问题与回答

**追问：应该共享工作区、使用独立 worktree，还是通过串行提交合并结果？**

只读任务可以共享；强依赖写操作使用独占写权限串行执行；独立写任务使用不同 worktree，并由唯一
集成阶段按基线、补丁和验证结果串行合并。

### 技术追问补充

- 子 Agent 的独立 State 不包含文件系统快照；如果工具闭包绑定相同 cwd，父子仍操作同一目录。
- 通用 `task_tool` 不创建、重置或合并 git worktree。
- SWE 工作流的 PDR 组装会为并行尝试创建 detached worktree，并把最终 Agent 绑定到规范工作区。
- 可以定义子任务产物，至少包含 `base_commit`、补丁或临时提交、修改路径、验证命令和结果；父模型
  可见文本只做摘要，真正合并使用结构化产物。
- 规范工作区由唯一集成者持有写权限。集成前检查当前提交和 dirty 状态，再按声明顺序应用补丁；
  不能根据子 Agent 完成先后决定覆盖顺序。
- 补丁无法干净应用、两个子任务修改同一区域或验证失败时，停止该项集成并生成冲突结果；可以让
  原子任务基于最新主工作区重新执行，但不能静默选择一方。
- 子 Agent 的 worktree 应在补丁和 Trace 持久化后再清理；清理失败不应影响已经保存的任务结果。
- git worktree 只能隔离仓库文件，数据库、远端服务和其他外部副作用仍需要资源锁、事务或独立测试
  环境。
- 当前 PDR 的最终 Agent 会在规范工作区重新完成任务，而不是自动合并各 worktree；完整的补丁产物
  和集成协议仍属于需要新增的 Workflow 能力。

## 51. 子 Agent 的 Token Budget 如何分配？

### 口述主回答

我会把 Token Budget 设计成“根预算、层级子预算和共享账本”三层结构，所有 Agent 的模型调用都从
同一个预算账本中扣减。根任务开始时先确定总预算，并为父 Agent 保留后续决策、验证和汇总所需的
额度，剩余部分才作为可委派额度。

父 Agent 每次通过 `task` 委派前，根据子任务的优先级和复杂度申请一个局部预算；申请必须原子完成，
并发委派的预留总额不能超过当前余额。子 Agent 如果继续委派，只能从自己的预算中切分，不能重新
向根任务申请额度。每个子 Agent 同时设置软上限和硬上限：接近软上限时通过上下文提醒它收敛，达到
硬上限后不再发起新的模型调用或子任务，并返回明确的预算耗尽结果。Goal Loop 的每次继续也从同一
个子预算中扣除，不能让每次 `resume` 都重新获得一份预算。

预算执行时，单次模型请求要把剩余预算作为 `max_tokens` 上限传给模型，防止最后一次调用突破总额；
响应返回后，再根据实际的 `output_tokens` 结算，未使用的预留额度归还账本。这样并行、递归委派和
Goal Loop 都受同一套预算约束，同时保留父 Agent 完成最终判断和汇总的能力。

### 追问问题与回答

**追问：Parent 和多个 Child 之间如何设置局部预算与全局预算？**

根预算先保留父 Agent 的决策和汇总额度；每个 Child 启动前从剩余额度中原子预留局部预算，结束后
按实际用量结算并归还余额。所有后代继续使用同一账本，余额不足就拒绝新委派。

## 51A. 项目提供了哪些工作流？

### 口述主回答

项目当前提供七类工作流，它们都复用同一个 Agent Loop，只负责决定 Agent 以什么顺序运行、怎样
传递结果以及何时停止。顺序链把多个固定阶段串起来；路由从多个专家中选择一个；并行工作流同时
执行多个独立任务或候选答案；Planner-Executor 先规划再执行；Reflection 通过批评和修订提高语义
质量；PDR 用多轮并行探索和信息提炼处理高难任务；Goal Loop 则让同一个 Agent 持续工作，直到
外部完成检查通过或预算耗尽。

选择时我主要看任务的依赖关系和反馈信号：步骤固定且前后依赖明确，用顺序链；任务只需要选择一个
专业方向，用路由；子任务彼此独立或需要多个候选，用并行；执行前需要先控制计划和副作用，用
Planner-Executor；缺少确定性检查但有明确评价标准，用 Reflection；搜索空间大、一次尝试容易走错，
并且预算允许多轮探索时用 PDR；单个 Agent 已经具备能力，但需要外部验证推动它持续完成任务时用
Goal Loop。

我不会为了使用多 Agent 而叠加工作流。默认先选择能表达任务结构的最简单方案，只有不同阶段确实
需要不同角色、并发、批评或完成控制时再组合。当前项目不会自动替调用者选择工作流，这属于任务
组装和评测决策。

### 追问问题与回答

**追问：这些工作流分别适合什么场景？**

固定流水线用顺序链，专家分流用路由，独立拆分或多候选用并行，先计划后执行用
Planner-Executor，语义审查用 Reflection，多轮高预算探索用 PDR，需要持续执行直到外部验证通过时
用 Goal Loop。

### 技术追问补充
**路由（Routing）**是“先判断任务属于哪个专业方向，再只运行一个对应专家”。

当前流程是：

```text
原始任务
  → Router Agent 判断类别
  → 根据名称匹配 Route
  → 运行被选中的 Specialist Agent
  → 返回专家结果
```

例如配置 `coder`、`researcher`、`writer` 三个 Agent，Router 只输出其中一个名称，Runtime 再把原始任务交给对应专家。它适合几个方向互斥、每次只需要一个专家处理的场景。它和 `task` 工具的区别是：`task` 是父 Agent 在运行过程中主动委派，Routing 则是在正式处理前先做一次集中分流。

**Reflection（反思/批评修订）**是“先生成，再审查，再修改”的质量提升循环，不是任务分流。

当前流程是：

```text
Generator 生成初稿
  → Critic 对照任务检查并提出问题
  → Generator 根据反馈生成完整修订稿
  → 再次 Critic
  → 直到 Critic 输出 APPROVED 或达到轮数上限
```

Critic 重点检查完整性、正确性和约束满足情况；它不直接修改结果，只提供反馈。`run_reflection()` 保存每一轮的生成、批评和修订步骤，最终返回最新版本。它适合代码、证明、结构化写作等有明确质量标准的任务。

两者的区别可以概括为：

- **Routing** 解决“应该由哪个专家处理”；
- **Reflection** 解决“当前结果是否足够好，以及如何改进”。

Reflection 的批准标记只是工作流停止信号，不等于客观正确性证明；需要验证真实环境时，应该使用 Goal Loop 的外部 `CompletionCheck`。
| 工作流 | 结束依据 | 是否等于任务完成 |
|---|---|---|
| Sequential | 所有阶段按顺序运行完，最后一个阶段输出结果 | 不一定 |
| Routing | Router 选出一个专家，专家运行结束 | 不一定 |
| Parallel | 所有 Worker 完成，Aggregator 返回结果 | 不一定 |
| Planner-Executor | Planner 产出计划，Executor 执行结束 | 不一定 |
| Reflection | Critic 输出 `APPROVED`，或达到反思轮数上限 | 只是质量信号，不是客观证明 |
| PDR | 每轮尝试后可选执行 `CompletionCheck`；否则按轮数和 Finalizer 结束 | 配置了检查器时可以提前确认 |
| Goal Loop | 每次 `run/resume` 后执行 `CompletionCheck`，通过才返回 `complete` | 是，完成条件由外部检查决定 |

## 52. Planner 和 Executor 为什么需要分开？

### 口述主回答

我把 Planner 和 Executor 分开，不只是为了拆分提示词，而是为了建立决策和执行的权限边界。
Planner 负责分解目标、列出约束和假设、定义步骤与验收条件，但不能修改环境；Executor 持有真实
工具，根据环境反馈执行并记录证据，但不能擅自改变用户目标和验收标准。

项目当前已经体现了这个边界：默认 Planner 没有工具，输出的计划单独保存在一个 State；Executor
使用另一个 State，接收原任务和计划后执行。这样可以独立检查计划质量，也能分别限制工具、预算和
模型配置。

两者之间需要有明确契约：Planner 提供“要完成什么和怎样判断完成”，Executor 返回“实际发生了
什么、哪些步骤完成、哪些假设失效”。是否修改计划由 Workflow 决定，而不是让 Executor 静默改写。
代价是多一次调用，并且计划可能过时，所以只适合确实需要多步协调和审计的任务。

### 追问问题与回答

**追问：Planner 和 Executor 分别负责什么，哪些状态和决策不应该混在一起？**

Planner 负责目标分解、约束、假设和验收条件；Executor 负责工具调用、环境事实和执行结果。环境
状态不能由 Planner 编造，用户目标和验收标准也不能由 Executor 擅自修改。

## 53. Planner 输出什么结构？

### 口述主回答

当前实现输出自然语言编号计划，适合教学和简单任务，但 Runtime 无法据此可靠判断步骤依赖、完成
状态和计划是否失效。

如果要支持动态执行，我会把计划表示成带版本的结构化步骤列表。计划保存原始目标、约束、假设和
验收条件；每个步骤有稳定编号、依赖关系、预期产物和完成检查。简单任务仍可以是线性列表，只有
确实存在并行或汇合关系时才使用依赖图，不必所有任务都建复杂流程图。

计划更新不能原地覆盖旧文本。Executor 只提交步骤结果和新发现，Workflow 需要重规划时生成新版本，
保留已完成步骤和证据，只替换尚未执行或已经失效的部分。这样可以解释计划为何变化，也能避免已经
验证的工作被重复执行。

### 追问问题与回答

**追问：Plan 是自然语言、结构化 Step 列表，还是带依赖关系的执行图？**

当前是自然语言编号计划。扩展后以结构化步骤列表为基础，步骤之间确有依赖时再增加依赖边。

**追问：Plan 是一次性生成，还是允许在执行过程中动态修改？**

当前只生成一次。扩展后允许 Workflow 根据执行证据创建新版本，但不原地改写旧计划，已完成步骤和
证据继续保留。

### 技术追问补充

- Planner System Prompt 要求输出简短、有序、可执行的编号步骤，并明确列出假设，不执行任务或
  输出最终答案。

## 54. Executor 执行失败后由谁决定是否重新规划？

### 口述主回答

Executor 执行失败后，不应该由 Executor 自己决定是否重新规划，而应由连接 Planner 和 Executor
的外层编排逻辑决定。Executor 只负责按照计划执行、调用工具并返回环境事实；Planner 负责生成计划。
只有掌握原始目标、当前计划和执行结果的一方，才能判断是局部动作失败，还是计划本身已经失效。

我会先按失败影响范围分类。参数错误、工具超时或一次性的执行异常，通常由 Executor 在当前 Agent
Loop 中根据 `ToolResult` 修正，不需要重新调用 Planner。若执行证据表明前置条件不成立、路径或
依赖发生变化，说明当前计划已经失效，编排逻辑才把原始目标、已完成步骤、失败证据和最新环境状态
交给 Planner，生成新的计划版本，再交给 Executor。若是权限拒绝、预算耗尽，或者用户目标发生变化，
则不能靠重新规划绕过，应直接停止或请求用户确认。

项目里的 `run_planner_executor()` 体现了这个边界：它先运行 Planner，再把原任务和计划交给 Executor；
两个 Agent 使用独立的 State，最终结果由 Executor 返回。重规划判断应继续放在这个外层入口，不能让
核心 Runtime 直接理解计划语义，也不能让 Executor 静默修改原计划。

### 追问问题与回答

**追问：如何区分可重试的步骤失败、局部计划失效和整体目标变化？**

同一目标下能够通过改参数或短暂重试解决的是动作失败；某个步骤的方法或依赖不成立是局部计划
失效；用户目标、验收条件或关键假设变化才需要整体重规划或用户确认。

**追问：Runtime、Planner、Executor 和 Workflow 分别负责什么？**

Runtime 负责模型和工具循环；Planner 生成计划版本；Executor 返回步骤结果和证据；Workflow 维护
步骤状态、判断失败类别并决定是否重新规划。

### 技术追问补充

- Executor System Prompt 明确允许步骤错误或不可执行时“合理适应并说明”，因此局部失败可在其
  普通 Agent Loop 中根据 Tool Result 自我修正。
- 核心 Runtime 不读取计划文本，也没有 step failure、plan invalid 或 replan 等事件类型。
- `run_planner_executor()` 返回 Executor 结果后直接结束，不检查失败类型，也不再次调用 Planner。
- 可以定义步骤结果，记录完成、可重试失败、计划失效、目标变化或策略阻止，以及证据和建议动作。
- Workflow 对可重试失败设置次数和退避；局部失效只重规划未完成子图；目标变化需要用户确认后才能
  生成新计划，不能由模型自行改写。
- 重规划必须有总次数、Token 和时间预算；连续出现相同失效原因时应停止，而不是形成
  “规划失败后继续规划”的无限循环。
- 当前需要由自定义 Workflow 重新组合 Planner 调用；可以复用 `WorkflowResult.steps` 保存每轮
  Planner 和 Executor 的独立 State，新增计划版本和失败分类状态机。

## 55. Planner 是否可以调用工具？

### 口述主回答

可以，但只应该调用帮助形成计划的只读工具。项目默认 Planner 不绑定工具，这是最清楚的权限边界；
如果任务必须先了解仓库结构、接口定义或服务状态，我会给它专门的读取、搜索和查询工具。

不能只在提示词里要求“不要执行”。Planner 的工具列表本身就不应包含编辑、部署、发送消息等有
副作用的能力，执行前策略还要根据规范化参数再次确认资源范围。像 Bash 这种很难判断副作用的通用
工具，不应直接交给 Planner，除非运行在只读或一次性隔离环境中。

Planner 通过工具得到的事实应带来源，并记录生成计划时的环境版本。Executor 开始执行时仍要重新
核对关键前提，因为规划阶段的只读快照可能已经过时。

### 追问问题与回答

**追问：如果 Planner 可以调用 Tool，如何避免它越过规划边界直接完成执行任务？**

只暴露专用只读工具，并在执行前再次校验工具和资源参数；通用命令工具放入只读隔离环境。真正的
写操作能力只绑定给 Executor。

### 技术追问补充

- `make_planner_agent()` 的接口没有 `tools` 参数，内部调用 `make_role_agent()` 时工具集合为空。
- 核心 `Agent` 本身支持绑定任意 AgentTool，因此调用者仍可手动构造有工具 Planner，Runtime
  不识别 Planner 角色并禁止工具。
- Planner Prompt 只是一层行为约束；真正的权限边界来自实际工具列表、Hook 和运行环境。
- 默认 Executor Builder 显式接受 `tools=`，体现副作用能力属于执行阶段。
- 扩展时优先提供 read、search、describe-schema 和 status 这类专用工具；不要通过命令文本猜测
  Bash 是否只读。
- `PRE_TOOL_USE` 可以按 Planner 身份和规范化资源参数拒绝写操作，但不可见工具应先在 Agent 组装
  时移除，避免模型反复尝试。
- 规划观察应记录文件哈希、版本号或查询时间；Executor 执行前发现版本变化时，应报告计划前提失效，
  由 Workflow 决定局部调整或重新规划。

## 56. Planner 和 Executor 应该使用同一个模型吗？

### 口述主回答

不要求相同，但也不能简单认为 Planner 一定要用更强模型、Executor 一定可以用便宜模型。项目里
两者是独立 Agent，可以分别配置模型；具体选择应看每个阶段真正的能力瓶颈。

Planner 主要看目标分解、约束保持、长上下文理解和结构化计划稳定性；Executor 主要看工具调用参数
准确率、根据真实反馈修正的能力、延迟和成本。工具复杂、错误恢复要求高时，Executor 可能比
Planner 更需要强模型；简单任务则使用同一个模型更容易控制变量和调试。

我会先用同一模型建立基线，再在相同任务、工具和总预算下分别替换 Planner 或 Executor，比较端到
端成功率、工具调用错误、重规划次数、成本和延迟。只有异构组合稳定改善整体结果时才采用，而不是
根据模型价格或角色名称直接决定。

### 追问问题与回答

**追问：如何根据推理能力、延迟、成本和上下文需求选择模型？**

先识别瓶颈：计划质量不足就提升 Planner，工具调用和恢复不稳定就提升 Executor；再在相同任务和
总预算下比较成功率、错误率、成本和延迟，决定是否值得使用不同模型。

### 技术追问补充

- `make_planner_agent(provider=...)` 和 `make_executor_agent(provider=...)` 分别接收 Provider，
  两者没有共享模型约束。
- Planner 和 Executor 是独立 Agent，分别保存 system prompt、工具、请求参数和模型超时。
- `run_planner_executor()` 分别提供 `planner_max_turns` 与 `executor_max_turns`，但不自动做模型
  路由或成本优化。
- 每一步 State 都保留模型和 usage，可在 Eval 中比较同模型与异构模型方案的成功率和成本。
- 评测应使用相同任务集、工具、总 Token 或成本预算以及停止条件，至少比较同模型基线、只替换
  Planner、只替换 Executor 和两者都替换四种配置。
- Planner 侧可观察计划解析成功率、约束遗漏和首次计划可执行率；Executor 侧可观察无效工具调用、
  参数修正次数、步骤完成率和平均重试次数，最终仍以端到端任务结果为准。
- 模型选择还要考虑上下文形状：Planner 读取任务和背景材料，Executor 会积累计划、工具结果和错误
  证据，后者不一定需要更小的上下文窗口。
- 当前没有自动模型路由；扩展后即使增加路由策略，也应在任务开始或计划版本边界切换，避免同一步骤
  中途改变模型导致行为难以归因。

## 57. Reflection 为什么有用？

### 口述主回答

Reflection 有用的关键不是“让模型再想一次”，而是把生成和评价使用的标准分开。Generator 负责
产出完整方案，Critic 回到原任务逐项检查约束、证据和前后逻辑，输出具体问题；Generator 下一轮
必须针对这些问题修订，而不是重新自由生成。

项目当前实现了“初稿、批评、修订”的有界循环，并保存每一步 State。它特别适合质量标准可以描述、
但难以完全写成程序检查的任务，例如多项要求覆盖、长文一致性、设计取舍和边界情况。

如果完善这套机制，我会让 Critic 按检查项输出问题、证据、严重程度和修改建议，只有阻塞问题全部
关闭才允许批准。它不适合简单低风险任务，也不能替代测试、编译和真实环境检查；涉及事实时，
Critic 必须读取可核对证据，否则两个模型可能共同接受同一个错误前提。

### 追问问题与回答

**追问：Reflection 适合发现哪些问题，哪些任务不值得增加 Reflection 阶段？**

它适合检查要求遗漏、内部矛盾、论证缺口、边界情况和表达结构。简单低风险任务，或能够通过快速
测试直接判定的问题，通常不值得增加模型批评。

### 技术追问补充

- `run_reflection()` 先运行 Generator 生成初稿，再在最多 `max_rounds` 个循环中运行 Critic；
  未批准时再运行 Generator 修订。
- Critic 输入包含原任务和当前完整草稿；默认 `make_critic_agent()` 不绑定工具。
- Critic Prompt 要求输出具体、可执行且按重要性排序的反馈；满意时输出批准标记。
- Reflection 达到轮数上限时返回最新草稿，不会伪造批准；批准仍是模型判断，不是外部验证。
- 可以把批评扩展为结构化问题列表，每项包含检查标准、问题描述、草稿证据、严重程度和修改建议；
  Generator 修订时逐项回应，下一轮检查尚未关闭的问题。
- 检查标准应来自用户要求、验收条件和外部验证结果，不能由 Critic 在审查时自行改变目标。
- 对代码、文件或外部事实的批评需要只读工具或验证产物；默认无工具 Critic 只能检查它看到的文本。

## 58. Reflection 和简单地再次调用一次模型有什么区别？

### 口述主回答

简单再次调用模型，本质上通常是重新采样一个答案；第二次调用未必知道第一版哪里错，也没有必须
保留什么、修改什么的约束。Reflection 则先产生显式评价信号，再把原任务、旧草稿和具体问题一起
交给 Generator，因此第二次调用有明确修订方向。

它还建立了可追踪的问题闭环：Critic 给每个问题编号，Generator 说明如何处理，下一轮再检查问题
是否关闭。Workflow 保存初稿、批评和修订，并根据问题状态、外部检查和轮数预算停止，而不是仅仅
比较两个自由答案。

当前项目已经显式区分三种输入，并保存每次运行；不足是批准仍靠字符串标记，批评也不是结构化问题
列表。扩展时应把批准条件改成“没有未解决的阻塞问题”，重要任务还要同时满足外部验证。

### 追问问题与回答

**追问：Critic 接收什么输入、输出什么反馈，Revision 如何使用这些反馈？**

Critic 接收原任务、验收条件、当前草稿和可用证据，输出带编号的问题列表；Generator 接收同样的
目标、旧草稿和问题列表，逐项修复后返回完整新版答案。

### 技术追问补充

- 初稿 Prompt 只包含原任务；批评 Prompt 包含原任务和当前草稿；修订 Prompt 包含原任务、旧草稿
  和 Critic 反馈。
- 每个 Generator、Critic 和 Revision 都通过 `run_agent()` 形成独立 StepResult 和 State，
  `WorkflowResult.steps` 按实际执行顺序保留全部步骤。
- 修订 Prompt 明确要求返回完整新版答案，而不是差异或局部修改。
- `is_approved()` 当前以不区分大小写的字符串包含判断批准标记；它是 Workflow 停止协议，不证明
  结果客观正确。
- 扩展后可用稳定问题编号维护打开、已解决、拒绝和重新打开状态；新一轮 Critic 应先复查旧问题，
  再增加新发现，避免每轮生成互不相关的批评。
- Generator 对每项问题应记录采用、部分采用或拒绝及原因；Workflow 再从完整修订稿和问题状态判断
  是否进入下一轮。
- 同一个模型也可以承担两个角色，但角色分离并不等于判断独立；高风险任务可使用不同提示、模型或
  外部检查降低相关错误，是否有效仍需评测。

## 59. Reflection 会增加 Token、延迟和调用成本，如何判断是否值得？

### 口述主回答

我不会固定对每个任务执行 Reflection，而是看它的预期收益是否高于额外成本。主要判断三个信号：
错误代价是否高、任务是否包含很多难以程序化检查的约束，以及第一次结果或外部检查是否暴露了语义
问题。简单回答、低风险任务或已有快速确定性验证时，通常直接验证和修复更有效。

具体流程是先运行便宜的规则、测试和格式检查；如果它们能够给出明确错误，就直接把结果反馈给
Generator。只有检查缺失、失败原因需要语义判断，或者任务风险较高时，才增加 Critic。先执行一轮，
如果没有发现新的重要问题，或者修订后外部检查已经通过，就停止，不机械跑满轮数。

为避免强化幻觉，Critic 应根据原任务和证据引用提出问题，事实类结论需要工具或外部产物支持。
当前 `run_reflection()` 还没有自动触发和收益判断；这些条件应由外层 Workflow 根据风险、验证结果、
剩余预算和历轮改进幅度决定。

### 追问问题与回答

**追问：Reflection 应该每次固定执行，还是根据任务风险和外部验证结果按需触发？**

应该按需触发。先使用便宜的确定性检查；高风险、约束复杂、缺少客观检查或检查暴露语义问题时，
再进入 Reflection。

**追问：Reflection 是否可能强化原答案中的 hallucination，如何降低这种风险？**

可能，因为 Critic 可能接受草稿中的错误前提。应要求事实问题附证据，给 Critic 只读验证能力，
并让外部检查优先于模型批准；没有证据的批评不能直接写入最终答案。

### 技术追问补充

- `run_reflection()` 被调用后必定先运行一次 Generator；每轮至少运行一次 Critic，未批准时再运行
  一次 Generator 修订，因此成本随 `max_rounds` 线性增加。
- 当前函数没有风险评分、测试结果判断或自动触发条件；是否调用 Reflection 由外层调用者决定。
- 默认 Critic 无工具，只看到任务和当前草稿，因此无法独立核验文件、命令或外部事实。
- 停止条件是 Critic 输出中出现批准标记或轮数耗尽；批准标记不是客观正确性证明。
- 可以在外层定义触发条件：任务风险等级、约束数量、确定性检查结果、模型不确定性信号和剩余预算；
  触发规则应可记录和评测，而不是让 Generator 自己决定是否需要审查。
- 停止条件可以组合为外部检查通过、没有新的高严重度问题、连续两轮问题集合不再改善、达到轮数或
  预算上限；批准标记只作为其中一个信号。
- 评估 Reflection 是否值得，应在相同任务和总预算下比较一次生成与批评修订的成功率、成本、延迟
  和回归率，不能只观察个别答案看起来更完整。
- Critic 与 Generator 使用相同模型时错误相关性可能较高；更换模型、增加证据或使用确定性检查是否
  能改善结果，需要分别做对照，不能默认“多一个模型调用”就更可靠。

## 60. 如何判断一个 Agent 任务真的完成了？

### 口述主回答

我会区分三层：模型输出 `final`，只代表它声明当前回答结束；Runtime 停止，只说明循环因为终止工具、
预算或 abort 结束；任务客观完成，则需要测试、命令或其他外部检查通过。

项目用 Goal Loop 把完成判断放在内层 Agent Loop 之外。每次运行结束后，完成检查读取当前 State 和环境；
检查未通过就继续同一会话，直到验证成功、阻塞、预算耗尽或被中止。

### 追问问题与回答

**追问：为什么不能只依赖模型输出 `Done`？**

模型可能遗漏要求、误判工具结果，或者没有真正执行验证，所以 `Done` 只能算声明，不能算完成证据。

**追问：Agent 声明完成、Runtime 停止和任务客观完成有什么区别？**

Agent 声明是模型判断；Runtime 停止是控制流状态；客观完成是外部检查确认目标已经满足。

### 技术追问补充

- 核心 Runtime 收到当前 Agent 的 `kind="final"` 后记录 `AgentEndEvent(reason="done")`，只结束当前
  内层运行。
- Goal 模式可由 Agent 调用 `update_goal` 声明 `complete` 或 `blocked`；`model_declared_check()`
  从工具结果的 `details` 中读取该声明。
- `run_goal_loop()` 在每段 `run/resume` 后调用独立 `CompletionCheck`；未通过时在同一 State 上追加
  继续任务。
- Goal 终态包括 `complete`、`blocked`、`budget_exhausted` 和 `aborted`；相同 blocker 连续三次才
  进入 `blocked`。

## 61. 什么是 External Validation Signal？

### 口述主回答

外部验证信号就是由 Agent 之外的检查器产生的、能够证明任务状态的结果。它不是模型输出的 `final`，
而是对当前环境或产物重新执行检查，例如测试命令是否通过、固定规则是否满足，或者独立 Judge 是否
确认结果符合要求。

在项目里，Goal Loop 把它作为外层停止条件。Agent 完成一段 `run` 或 `resume` 后，`CompletionCheck`
读取当前 State 和环境，返回 `done`、`blocked` 以及原因。如果检查通过，Goal Loop 才返回 `complete`；
如果没有通过，就把检查结果转成继续提示，让同一个 Agent 继续工作；如果连续多轮因为同一个原因阻塞，
或者达到 Token、回合、时间预算，就结束为相应的非成功状态。

所以，模型的 `final` 只表示“我认为这一轮可以结束”，外部验证信号才决定“任务是否真的达到验收条件”。
这能避免 Agent 因为误读工具结果或遗漏要求而过早宣布完成。

### 追问问题与回答

**追问：验证信号由谁产生，Goal Loop 如何使用它决定继续、完成或终止？**

验证信号由命令、测试、规则、Judge 或其他外部检查器产生；Goal Loop 根据检查结果完成、继续、
标记阻塞，或在预算和 abort 条件下终止。

### 技术追问补充

- `CompletionCheck` 是 `Callable[[State], CompletionResult]`，结果字段为 `done`、`blocked` 和
  `reason`；检查器实现位于 Workflow 边界。
- Goal Loop 每次先检查 abort，再调用 CompletionCheck；done 立即返回 complete，blocked 会累计
  相同原因，未完成则检查预算后 resume。
- 回合与输出 Token 耗尽返回 budget_exhausted，墙钟截止和调用者 abort 返回 aborted。
- 每次继续和终止都会追加 `GoalStatusEvent`，记录 objective、状态、回合、Token 和原因。

## 62. SWE 类任务可以使用哪些 Validation Signal？

### 口述主回答

单元测试证明被覆盖的行为是否通过，静态检查发现类型或格式问题，构建结果证明项目能够编译或打包，
Patch 只能证明产生了修改，官方评分器才最接近 Benchmark 的最终成功定义。任何单一信号都可能覆盖不完整。

如果测试通过但实现仍不符合用户要求，我会把用户验收条件、针对性复现、回归测试、构建结果和必要的
语义审查组合起来，不能把单个测试通过当成全部要求满足。

### 追问问题与回答

**追问：单元测试、静态检查、构建结果、Patch 和官方评分器分别能证明什么？**

单测证明覆盖行为，静态检查发现类型和格式问题，构建证明可编译打包，Patch 只证明产生修改，官方评分器
最接近 Benchmark 的最终标准。

**追问：如果测试通过，但实现不符合用户要求，如何组合多个验证信号？**

同时检查用户验收条件、针对性复现、回归测试、构建结果和必要的语义审查，不能把单个测试通过当作全部
要求满足。

### 技术追问补充

- `command_verifier_check(command)` 直接执行固定命令，退出码为 0 才返回 `done`。
- `executed_completion_check()` 先读取 Agent 的 complete 声明和 `verify_command`，再重新执行该非空
  命令；命令失败或缺失时保持未完成。
- `default_check(verifier=...)` 允许外部 verifier 否决模型的 complete 声明，调用者也可以实现组合多个
  信号的自定义 `CompletionCheck`。
- SWE 官方 scorer 位于 Eval/Host 边界，不是 Goal Loop 每轮默认调用的检查器。

## 63. 没有 deterministic verifier 的任务如何判断完成？

### 口述主回答

没有确定性验证器时，我不会把模型输出的 `final` 直接当成完成，而是把完成判断变成一个基于证据和
风险的决策。我会先把用户目标拆成若干可检查的验收条件，并要求 Agent 对每项给出结论、证据来源和
未解决问题。证据可以来自工具结果、生成的产物、执行日志或独立检查。

然后由独立 Judge 对照原始目标逐项审查：证据充分且没有冲突，才允许返回完成；缺少证据或发现矛盾，
就把具体问题反馈给 Agent，让它继续补充或修正。风险不同，门槛也不同。低风险任务可以由一个独立
Judge 根据完整证据放行；中风险任务需要额外复核，意见不一致时回到原始证据；高风险或不可逆操作
不能依赖模型判断，必须进入人工确认。

这个结果最终通过 `CompletionCheck` 返回给 Goal Loop：通过才是 `complete`，否则继续运行，直到
阻塞、预算耗尽或被中止。

### 追问问题与回答

**追问：应该使用 LLM Judge、规则检查、人工确认，还是风险分级的混合方案？**

采用风险分级的组合方案：规则负责能够明确检查的部分，Judge 逐项审查语义和证据，中风险分歧时
继续补证据，高风险或不可逆操作必须人工确认。
