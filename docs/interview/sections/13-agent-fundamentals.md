# 第十三部分：Agent 相关八股问答

## 1. Agent 基础概念

### 1. 什么是 LLM Agent？它与普通聊天机器人有什么区别？

**回答：** LLM Agent 是以大模型作为决策组件，能够读取环境状态、选择并调用工具、观察结果、更新状态并持续执行直到满足停止条件的系统。普通聊天机器人通常以生成回复为终点，而 Agent 的目标是通过多轮行动改变外部环境并完成可验证的任务。

### 2. Agent、Workflow、Copilot 和 RPA 的区别是什么？

**回答：** Agent 由模型动态决定下一步行动；Workflow 按预先定义的节点、分支和状态转换执行；Copilot 强调人机协作，由人掌握最终决策；RPA 主要按照固定规则模拟重复操作。实际系统通常是混合形态，例如 Workflow 控制边界，Agent 处理开放决策，Copilot 提供人工确认。

### 3. 一个最小 Agent 系统由哪些核心组件构成？

**回答：** 最小系统需要模型客户端、上下文或状态、工具注册与执行器、Agent Loop，以及停止条件。工程上通常还会补充预算控制、异常处理和事件记录，但它们不是概念上的最小闭环。

### 4. Agent Loop 中 Observation、Thought、Action 分别代表什么？

**回答：** Observation 是环境反馈，例如工具结果、错误或用户输入；Thought 是模型基于当前状态形成的内部决策过程；Action 是可执行的外部行为，例如调用工具或提交答案。生产系统不应依赖保存或展示模型的完整隐藏思维链，而应记录可审计的决策摘要、工具调用和结果。

### 5. Agent 的环境、状态、动作空间和反馈信号分别是什么？

**回答：** 环境是 Agent 可以观察和影响的外部世界；状态是系统保存的任务、消息、计划和执行进度；动作空间是允许调用的工具和终止操作；反馈信号是工具结果、测试、评分器或人工意见。设计关键是让动作受约束、反馈可验证、状态可恢复。

### 6. 什么是 Agent 的自主性？自主性越高是否一定越好？

**回答：** 自主性表示 Agent 在目标分解、工具选择、执行顺序和停止判断上拥有多少决策权。自主性越高，适应开放任务的能力越强，但不可预测性、成本和风险也越高，因此应根据任务风险设置权限、预算和人工审批边界。

### 7. 确定性工作流与模型驱动的动态决策分别适合什么场景？

**回答：** 确定性工作流适合流程稳定、合规要求高、步骤和分支可枚举的任务；动态决策适合输入开放、路径难以预先穷举、需要探索和纠错的任务。常见做法是用确定性外壳限制权限、预算和阶段，在局部节点中允许模型动态选择。

### 8. 为什么 Agent 通常比单次 LLM 调用更不稳定？

**回答：** Agent 将多个概率性模型决策、工具调用和环境变化串联起来，早期误差会影响后续状态并累积放大。并发、网络、外部服务和重试还会增加非确定性，所以必须通过状态约束、外部验证、幂等工具和轨迹记录控制风险。

### 9. Agent 的能力上限主要由模型、工具还是运行时决定？

**回答：** 三者共同决定。模型决定理解、规划和选择能力，工具决定能够作用于什么环境，运行时决定状态、预算、恢复、安全和反馈闭环；任一部分明显不足都会成为系统上限，因此不能把最终能力只归因于模型。

### 10. 如何判断一个业务问题是否真的需要 Agent？

**回答：** 如果任务路径无法预先枚举，需要根据中间结果动态选择工具并多轮修正，Agent 才有明显价值。若流程固定、规则清晰、风险高且要求强一致性，优先使用普通程序或 Workflow，只在少数语义判断节点引入模型。

### 11. Agent 完成任务与模型生成了最终文本有什么区别？

**回答：** 最终文本只是模型声明完成，任务完成必须由外部事实验证，例如测试通过、文件生成、订单状态变化或评分器满足条件。可靠系统把“模型认为完成”和“验证器确认完成”分成两个状态。

### 12. Agent 系统最常见的失败模式有哪些？

**回答：** 常见失败包括目标理解错误、计划漂移、工具选择或参数错误、上下文丢失、重复循环、错误停止、工具副作用、权限越界和成本失控。诊断时应区分模型决策、运行时编排、工具实现、外部环境和评测器五类原因。

## 2. 模型交互与提示词

### 1. System Prompt、Developer Prompt 和 User Prompt 分别承担什么职责？

**回答：** System Prompt 定义平台级身份、安全和最高层行为约束；Developer Prompt 承载应用开发者设定的业务规则、工具使用方式和输出要求；User Prompt 表达当前用户目标与数据。冲突时应遵循平台规定的指令优先级，低优先级内容不能覆盖高优先级约束。

### 2. 提示词中的指令、上下文、示例和输出约束应该如何组织？

**回答：** 先写稳定的角色、目标和硬约束，再提供完成任务所需的上下文，然后给少量代表性示例，最后明确输出结构和验收标准。不同区块应使用清晰边界，外部数据必须标记为数据而非指令，避免模型混淆。

### 3. Zero-shot、Few-shot 和动态示例选择有什么区别？

**回答：** Zero-shot 只依赖任务说明，成本低但一致性较弱；Few-shot 在提示中放固定示例，能校准格式和决策模式；动态示例选择根据当前输入检索相似案例，适应性更强，但引入检索质量、延迟和污染风险。

### 4. Temperature、Top-p 和最大输出 Token 会如何影响 Agent？

**回答：** Temperature 和 Top-p 控制采样分布，值越高通常越多样但越不稳定；最大输出 Token 限制单次响应长度，过低可能截断工具参数或结论，过高则增加成本和延迟。通常只调整 Temperature 或 Top-p 中的一项，并为工具调用和最终回答分别设置合适预算。

### 5. 为什么低 Temperature 也不能保证 Agent 行为完全确定？

**回答：** 模型服务可能存在并行计算、版本更新和同分 Token 选择差异，工具与外部环境也会变化。即使单次生成接近确定，多轮执行仍会放大微小差异，因此需要固定模型版本、记录输入和配置，并用外部验证而不是依赖确定性假设。

### 6. 什么是结构化输出？它与要求模型返回 JSON 有什么区别？

**回答：** 结构化输出通过模型或 API 的 Schema 约束机制，使输出在语法和字段结构上符合指定模式；普通提示“返回 JSON”只是自然语言要求，仍可能产生多余文本、缺失字段或错误类型。结构化输出提高可解析性，但不保证字段值在业务语义上正确。

### 7. JSON Schema 能解决哪些问题，不能解决哪些问题？

**回答：** JSON Schema 可以约束对象结构、字段类型、必填项、枚举和部分数值或字符串条件。它不能验证事实正确性、业务权限、跨资源一致性或工具操作是否安全，这些仍需程序校验和外部验证。

### 8. 模型输出不符合 Schema 时应该重试、修复还是直接失败？

**回答：** 若供应商支持严格结构化输出，应优先在生成阶段约束；否则先做本地校验，对可恢复的格式错误进行有限次数的反馈重试。涉及金额、权限或副作用的字段不能静默修复，超过重试预算后应明确失败或转人工。

### 9. 如何减少模型幻觉？Agent 使用工具后为什么仍然可能幻觉？

**回答：** 应提供权威上下文、要求引用证据、使用检索和工具、缩小输出自由度，并用程序或验证器检查结果。工具只提供证据，模型仍可能误读、忽略、错误归纳或把旧信息当作新结果，所以工具结果必须结构化、标注来源并接受验证。

### 10. 提示词过长会带来哪些问题？

**回答：** 过长提示会增加延迟和成本，稀释关键指令，并加剧位置偏差、冲突指令和无关信息干扰。优化时应删除重复内容，把稳定前缀用于缓存，把大型资料交给检索，并将硬约束放在清晰、稳定的位置。

### 11. Prompt Caching 适合缓存哪些内容？

**回答：** 适合缓存多个请求共享且前缀稳定的内容，例如系统说明、工具定义、固定策略和大型参考资料。动态用户数据、频繁变化的时间信息和敏感内容要谨慎缓存，同时需要考虑供应商的前缀匹配规则、缓存时效和隐私边界。

### 12. 为什么不能把核心业务约束只写在 Prompt 中？

**回答：** Prompt 是概率性指令，可能被忽略、误解或受注入攻击影响。权限、金额上限、数据访问范围、幂等性和审批要求必须在确定性代码、策略引擎或执行层再次强制校验。

## 3. Tool Calling 与 MCP

### 1. Function Calling 的完整执行流程是什么？

**回答：** 应用先向模型提供工具名称、描述和参数 Schema；模型返回工具调用意图及参数；应用校验权限和参数后执行真实函数；再把带调用标识的结果返回模型；模型基于结果继续调用工具或生成最终答案。模型只负责提出调用，真正的执行权始终在宿主应用。

### 2. 模型选择工具与程序真正执行工具之间的边界是什么？

**回答：** 模型负责根据语义选择工具并生成候选参数，程序负责权限检查、类型与业务校验、实际执行、超时、重试和审计。任何具有副作用的操作都不能因为模型输出了工具调用就直接信任执行。

### 3. 一个高质量工具描述应该包含哪些信息？

**回答：** 应明确工具用途、适用与不适用场景、参数语义、约束、返回值和主要副作用。描述应短而具体，并用互斥边界区分相似工具，避免用实现细节或模糊宣传语增加选择难度。

### 4. 工具粒度应该尽可能细，还是提供高层复合工具？

**回答：** 细粒度工具组合灵活、可观察，但会增加调用轮次和决策错误；高层工具更可靠高效，但可复用性和透明度较低。高频、稳定、强约束的业务流程适合复合工具，开放探索任务适合少量边界清晰的基础工具。

### 5. 如何设计工具参数 Schema，降低模型调用错误率？

**回答：** 使用明确字段名、具体描述、必填项、枚举和合理边界，避免同义字段、深层嵌套和自由格式字符串。能够由系统推导的参数不要让模型填写，时间、金额、资源 ID 等关键字段还要在执行层做语义校验。

### 6. 工具返回值应该是自然语言还是结构化数据？

**回答：** 优先返回稳定的结构化数据，包括状态、结果、错误码、证据和可继续操作的标识；必要时附加简短的人类可读摘要。只返回自然语言难以可靠解析，只返回巨大原始对象又会浪费上下文，因此应提供精简结构和按需读取能力。

### 7. 如何区分只读工具和具有副作用的工具？

**回答：** 只读工具不改变外部状态，例如查询和读取；副作用工具会写文件、发送消息、扣款或修改资源。工具元数据应声明风险等级和副作用，执行器据此应用不同的权限、确认、幂等和审计策略。

### 8. 什么是幂等工具？为什么 Agent 工具需要考虑幂等性？

**回答：** 幂等表示对同一目标重复执行相同请求，最终效果与执行一次一致。Agent 可能因超时、重试或恢复重复调用工具，因此写操作应使用幂等键、条件更新或去重记录，避免重复付款、发送或修改。

### 9. 工具调用失败后，哪些错误可以重试，哪些不应该重试？

**回答：** 网络抖动、限流、临时不可用等瞬时错误可以采用限次指数退避重试；参数错误、权限拒绝、资源不存在和确定性业务冲突通常不应原样重试。副作用操作只有在能确认未执行或具有幂等保障时才能自动重试。

### 10. Tool Choice 使用 Auto、Required 和指定工具分别适合什么情况？

**回答：** Auto 适合允许模型在回答与调用工具之间自主选择；Required 适合当前步骤必须获得外部证据或执行动作；指定工具适合流程已经确定、只需要模型填充参数。选择越强制，行为越可控，但也越可能在不合适输入上产生无意义调用。

### 11. 什么是 MCP？它主要解决了什么问题？

**回答：** MCP 是用于 AI 应用连接外部工具和上下文来源的开放协议，统一能力发现、调用和消息交换方式。它主要减少每个 Agent 应用为每个数据源或工具重复编写专用适配层的问题，但不替代业务权限、沙箱和安全审核。

### 12. MCP Client、MCP Server 和 Host 分别承担什么职责？

**回答：** Host 是承载模型和用户体验的应用，负责安全边界、授权和整体编排；Client 是 Host 内与某个 Server 建立协议会话的组件；Server 暴露工具、资源和提示等能力。通常一个 Host 可以管理多个 Client，并分别连接多个 Server。

### 13. MCP 中 Tools、Resources 和 Prompts 有什么区别？

**回答：** Tools 是模型或应用可调用的操作，可能产生副作用；Resources 是可寻址、可读取的上下文数据；Prompts 是服务器提供的可复用提示模板或交互入口。三者分别对应“执行动作”“读取内容”和“组织交互”，权限和调用方式不同。

### 14. MCP 与普通 HTTP API、Function Calling 的关系是什么？

**回答：** HTTP API 是服务传输和业务接口形式；Function Calling 是模型表达工具调用意图的机制；MCP 则定义 Host 与能力服务器之间的发现、描述和调用协议。MCP Server 内部可以调用 HTTP API，Host 也可以把 MCP Tool 转换成模型可见的 Function Tool。

### 15. 使用第三方 MCP Server 时有哪些安全风险？

**回答：** 风险包括恶意工具描述、提示注入、过度权限、数据外泄、命令执行、依赖供应链攻击以及服务器更新后的行为变化。应进行来源审核、最小权限授权、网络和文件隔离、参数校验、敏感信息脱敏、人工确认与完整审计。

### 16. 如何对高风险工具增加用户确认和权限控制？

**回答：** 在工具元数据中标记风险和所需权限，执行前由策略层检查用户、资源范围和操作内容，并向用户展示具体影响而不是笼统确认。确认结果应绑定本次参数和有效期，执行后记录调用者、参数摘要、结果及审计标识。

## 4. 推理、规划与反思

### 1. ReAct 的核心思想是什么？

**回答：** ReAct 将推理与行动交替进行：模型根据当前观察决定下一步工具调用，再利用新观察继续决策。它比一次性生成完整答案更能利用外部证据和纠正路径，但需要限制循环、工具权限和上下文增长。

### 2. ReAct 与 Plan-and-Execute 有什么区别？

**回答：** ReAct 每一步都根据最新观察即时决策，适合路径不确定的探索任务；Plan-and-Execute 先形成相对完整的计划，再逐项执行，适合目标可分解、步骤依赖明确的任务。实际系统常将两者结合：先给粗粒度计划，执行时局部 ReAct，并允许重新规划。

### 3. 什么情况下应该先生成完整计划，什么情况下应该边执行边规划？

**回答：** 依赖关系明确、执行代价高、需要审批或并行分工时，应先形成计划；环境变化快、信息不足或每一步结果都会改变后续路径时，应边执行边规划。计划的价值在于约束和协调，而不是预测所有细节。

### 4. 长任务中的计划应该如何表示？

**回答：** 计划应表示为可更新的结构化状态，至少包含步骤 ID、目标、依赖、状态、验收条件和产物引用。不要只保存自然语言清单，否则难以可靠地更新进度、恢复执行和检测遗漏。

### 5. 如何判断计划已经失效，需要重新规划？

**回答：** 当关键假设被工具结果否定、依赖资源不可用、连续失败超过阈值、预算明显不足或目标发生变化时，应触发重新规划。重新规划要保留已验证事实和有效产物，避免从头开始造成重复劳动。

### 6. 计划粒度过粗或过细分别会产生什么问题？

**回答：** 过粗会缺少可执行动作和验收点，Agent 容易漂移；过细会增加规划成本，并使计划在环境变化后迅速过期。合适粒度应让每一步能在有限时间内执行、产生可观察结果，并能独立验证。

### 7. Reflection、Self-Critique 和 Self-Consistency 有什么区别？

**回答：** Reflection 通常基于执行轨迹总结问题并调整后续策略；Self-Critique 是模型审查某个候选输出并指出缺陷；Self-Consistency 是生成多个独立候选并通过投票或聚合选择结果。三者都可能提升质量，但都会增加成本，且不能替代外部验证。

### 8. 反思为什么可能无法纠正原始错误？

**回答：** 反思模型可能共享原模型的知识盲区、错误前提和偏见，只是在错误轨迹上生成更流畅的解释。如果没有新证据、独立验证器或不同搜索路径，反思容易重复或合理化原始错误。

### 9. 如何避免 Agent 陷入“执行失败—反思—再次失败”的循环？

**回答：** 记录失败签名和已尝试策略，禁止无变化的重复动作，并设置重试、反思次数和总预算上限。每次重试必须引入新的参数、证据或策略，否则应降级、重新规划或请求人工介入。

### 10. Tree of Thoughts 与普通线性推理有什么区别？

**回答：** 线性推理沿一条路径持续生成；Tree of Thoughts 同时维护多个中间候选，对其评分、扩展和回溯。它能提高复杂搜索任务的覆盖率，但分支数量会快速增加，因此需要可靠评分器和严格剪枝。

### 11. 搜索式推理中的候选生成、评分和剪枝分别如何实现？

**回答：** 候选生成可以由模型采样多个动作或方案；评分可由规则、环境验证器、独立模型或组合指标完成；剪枝根据得分、重复度、风险和预算淘汰分支。评分器若不可靠，扩大搜索只会更昂贵地选择错误路径。

### 12. 是否应该让 Agent 展示完整思维链？为什么？

**回答：** 不应把完整隐藏思维链作为产品依赖、审计依据或用户必须看到的内容。系统应提供简洁的决策理由、证据、工具调用和可验证结果，这些信息更稳定，也更适合安全审计和故障定位。

### 13. 如何使用外部验证器代替模型自我判断？

**回答：** 将完成条件转换为可执行检查，例如单元测试、Schema 校验、数据库查询、规则引擎、编译器或人工审批。模型可以提出候选方案，但是否通过应由与生成过程相对独立的验证信号决定。

### 14. 为什么可验证奖励对软件工程 Agent 特别重要？

**回答：** 软件任务通常存在编译、测试、静态检查和行为断言等客观反馈，可以直接区分“看起来合理”和“实际可用”。这使 Agent 能够根据真实失败信息迭代，而不是依赖模型对自身代码的主观评价。

## 5. Context、Memory 与 RAG

### 1. Context Window 与模型真正能够有效利用的信息量是否相同？

**回答：** 不相同。Context Window 只是模型允许接收的最大 Token 数，信息越长并不代表模型能同等关注和准确使用所有内容；位置偏差、干扰信息、推理负担和输出预算都会降低有效利用率。

### 2. 什么是 Lost in the Middle 问题？

**回答：** Lost in the Middle 指模型对长上下文中间位置的信息利用往往弱于开头和结尾。缓解方法包括检索相关片段、重排关键证据、分层摘要和在决策前重新呈现必要约束，而不是简单扩大上下文。

### 3. 为什么不能把所有历史记录直接放入上下文？

**回答：** 全量历史会增加成本和延迟，引入过期、冲突和无关信息，并最终超过窗口限制。应把完整历史作为可审计存储，把当前需要的信息组织成受预算约束的活跃上下文。

### 4. Sliding Window、摘要压缩和检索恢复分别适合什么情况？

**回答：** Sliding Window 适合近期信息最重要的连续交互；摘要压缩适合保留阶段性结论和任务状态；检索恢复适合从大量历史中找回少量原始证据。长任务通常组合使用三者，而不是只依赖一种策略。

### 5. Context Compression 的主要信息损失风险是什么？

**回答：** 摘要可能遗漏约束、混淆时间顺序、弱化不确定性，或把错误结论固化为事实。应保留原始记录和引用位置，区分事实、推断与未决项，并允许按需回读证据。

### 6. 短期记忆、工作记忆和长期记忆有什么区别？

**回答：** 短期记忆通常是最近交互；工作记忆是当前任务主动使用的目标、计划和证据；长期记忆是跨会话保留的稳定事实或经验。边界应由生命周期、访问范围和更新策略定义，而不是只按存储介质区分。

### 7. Semantic Memory、Episodic Memory 和 Procedural Memory 分别是什么？

**回答：** Semantic Memory 保存概念和事实；Episodic Memory 保存某次任务发生了什么及结果；Procedural Memory 保存如何完成某类任务的步骤和策略。工程上分别可对应事实库、运行轨迹和 Skills 或流程模板。

### 8. Memory 的写入、检索、更新和遗忘策略应该如何设计？

**回答：** 写入要依据稳定性、复用价值和可信来源筛选；检索结合相关性、时效和权限；更新保留版本与来源；遗忘处理过期、冲突和用户删除要求。不能让模型无条件把每次推断写成长期事实。

### 9. 什么是 RAG？RAG 与 Agent Memory 的区别是什么？

**回答：** RAG 在生成前从外部知识源检索相关内容并加入上下文，重点是获取任务所需知识；Agent Memory 保存和恢复 Agent 或用户在历史任务中形成的信息。二者都可使用检索技术，但数据来源、生命周期、权限和写入机制不同。

### 10. Embedding 在检索系统中起什么作用？

**回答：** Embedding 将文本或其他内容映射到向量空间，使系统可以按语义相似度召回候选。它适合发现措辞不同但含义相近的内容，但相似不等于事实相关或可回答，因此通常需要过滤和重排。

### 11. 文档切片的大小和重叠范围会如何影响检索结果？

**回答：** 切片过小会丢失上下文，过大则混入无关内容并消耗 Token；适度重叠可保留跨边界信息，但会增加索引和重复召回。应根据文档结构、查询粒度和模型窗口通过评测选择参数。

### 12. 关键词检索、向量检索和混合检索各有什么优缺点？

**回答：** 关键词检索擅长精确名称、代码和编号，速度快且可解释；向量检索擅长语义近似，但可能错过精确实体；混合检索融合两者，覆盖率更好，但需要分数归一化、去重和额外调参。

### 13. 什么是 Rerank？为什么向量相似度不能直接代表答案相关性？

**回答：** Rerank 使用更强的模型或规则对初步召回结果按当前查询重新排序。向量相似度只衡量表示空间中的接近程度，不能充分判断时效、权威性、上下文关系和是否真正支持答案。

### 14. 如何评估检索的 Recall、Precision 和最终回答质量？

**回答：** 用带相关性标注的数据集计算 Recall@k、Precision@k、MRR 或 NDCG，并单独评估答案正确性、引用支持度和拒答能力。要区分“没有召回证据”“召回但模型没使用”和“使用后推理错误”三类失败。

### 15. 检索到错误或恶意内容时，Agent 应该如何处理？

**回答：** 将检索内容视为不可信数据，保留来源和权限信息，隔离其中的指令，并与更权威来源交叉验证。涉及敏感操作时，检索文本不能直接改变系统规则或触发工具执行。

### 16. 如何避免跨用户、跨租户和跨任务的 Memory 污染？

**回答：** 在存储和检索层强制使用租户、用户、任务和敏感级别等命名空间与访问控制，并对写入来源和所有权做校验。过滤不能只依赖模型提示，删除和导出也必须覆盖索引、缓存和派生摘要。

## 6. 多 Agent 系统

### 1. 多 Agent 相比单 Agent 的核心收益是什么？

**回答：** 多 Agent 可以按专业能力和上下文拆分任务，支持并行探索、独立验证和更清晰的职责边界。收益只有在任务可分解、沟通成本可控且合并结果可验证时才成立。

### 2. 多 Agent 为什么可能比单 Agent 表现更差？

**回答：** 任务切分错误、上下文传递损失、重复劳动、冲突结论和额外模型调用都会降低效果。多个相同模型还可能共享同一种错误，角色数量增加并不等于认知多样性增加。

### 3. 多 Agent 系统常见的组织结构有哪些？

**回答：** 常见结构包括主管者分派 Worker、Router 路由到专家、Planner-Executor、并行候选加裁判、层级团队和共享黑板。选择结构应由依赖关系、并行度、风险和可验证性决定。

### 4. Supervisor、Router、Planner 和 Worker 分别承担什么职责？

**回答：** Supervisor 管理总体目标、预算和汇总；Router 选择适合的处理者或路径；Planner 分解任务和依赖；Worker 执行具体子任务并返回产物。小系统中这些角色可以合并，避免为了角色而增加调用。

### 5. 中心化编排与去中心化协作有什么区别？

**回答：** 中心化编排由一个控制者掌握任务状态和分配，易于审计和控制；去中心化允许 Agent 直接协商和委派，灵活但更难防止循环、冲突和失控。生产系统通常偏中心化，并只在局部允许自治。

### 6. Agent 之间应该传递完整对话还是结构化任务状态？

**回答：** 默认传递结构化任务说明、约束、证据引用、已完成工作和验收条件，必要时再按引用读取原始对话。完整转发会增加成本、泄露无关信息，并使接收者难以区分事实和过程噪声。

### 7. 如何为子 Agent 划分互不冲突的任务边界？

**回答：** 按独立产物、文件范围、数据分区或职责划分，并明确输入、写权限、禁止修改范围和完成条件。存在共享写入时，应由单一所有者合并，或使用版本与冲突检测机制。

### 8. 如何避免重复劳动、循环委派和任务遗漏？

**回答：** 为每个子任务分配唯一 ID，维护依赖图、所有者和状态，并记录委派链与已尝试工作。限制委派深度和重复签名，汇总时根据验收清单检查是否覆盖全部目标。

### 9. 并行 Agent 的结果应该如何聚合和验证？

**回答：** 先让每个 Agent 返回结构化产物、证据和置信说明，再由确定性合并器或独立验证者检查冲突、重复和完整性。不能只让另一个模型对多段自然语言做无约束总结。

### 10. 多个 Agent 结论冲突时如何仲裁？

**回答：** 优先使用外部事实、测试、权威数据和明确规则仲裁；若无法客观验证，应保留分歧、比较证据并请求更高权限模型或人工决策。多数投票只有在候选相对独立且错误不高度相关时才可靠。

### 11. 如何限制子 Agent 的递归深度、Token 和执行时间？

**回答：** 由父任务分配硬预算，包括最大深度、调用次数、Token、墙钟时间和工具权限，运行时在每次委派前检查剩余预算。子 Agent 不能自行扩大预算，超限后应返回部分结果和未完成原因。

### 12. 一个子 Agent 失败时，主流程应该重试、降级还是终止？

**回答：** 根据错误是否瞬时、子任务是否关键、是否有替代路径和副作用风险决定。可恢复错误限次重试，非关键任务可降级，关键且无替代路径时应终止或转人工，并保留已经完成的有效产物。

### 13. 多 Agent 的性能提升应该如何评估？

**回答：** 在相同模型、任务、工具和总预算下与单 Agent 基线比较成功率、成本、延迟、方差和人工介入率。还应做角色或通信机制消融，确认收益来自协作结构而不是简单增加计算量。

### 14. 什么情况下角色扮演只是增加复杂度，没有实际价值？

**回答：** 当所有角色使用相同上下文、相同工具、相同模型且没有独立目标、信息或验证职责时，角色往往只是不同提示词标签。若任务本身简单或无法有效分解，单 Agent 加确定性检查通常更可靠。

## 7. Agent Eval 与可观测性

### 1. Agent Eval 与普通 LLM Eval 有什么区别？

**回答：** 普通 LLM Eval 常评估单次输入输出，Agent Eval 还要评估多轮决策、工具调用、状态变化、环境副作用、预算和最终结果。Agent 的失败可能来自模型、工具、编排或环境，因此必须同时观察结果和轨迹。

### 2. 如何定义 Agent 的任务成功？

**回答：** 应把成功定义为可执行或可独立检查的验收条件，例如测试通过、目标资源达到指定状态、约束全部满足。不能仅依据 Agent 自述完成，也不能只检查最终文本是否流畅。

### 3. 最终答案正确是否足以说明 Agent 执行过程正确？

**回答：** 不足。Agent 可能通过越权、泄露信息、破坏环境或偶然猜测得到正确答案，因此还要检查过程合规性、副作用、成本和证据链；高风险场景中过程违规应直接判失败。

### 4. Outcome Evaluation 与 Trajectory Evaluation 有什么区别？

**回答：** Outcome Evaluation 只判断最终结果是否满足目标；Trajectory Evaluation 检查中间动作、工具参数、顺序、证据和策略质量。前者更客观简洁，后者更利于诊断，但标注成本高且容易引入主观偏差。

### 5. 离线评测、在线评测和生产监控分别解决什么问题？

**回答：** 离线评测用于发布前比较版本和发现回归；在线评测通过真实流量实验衡量业务效果；生产监控持续发现延迟、成本、错误、安全和数据漂移。三者不能互相替代，应形成发布前后闭环。

### 6. Pass@1、Pass@k、成功率和平均奖励分别适合什么场景？

**回答：** Pass@1 衡量单次执行可靠性；Pass@k 衡量允许生成 k 个候选时至少一次成功的能力；成功率适合二元完成条件；平均奖励适合质量连续或包含多个维度的任务。报告时必须同时说明采样次数、选择机制和预算。

### 7. Agent 评测为什么需要控制模型、预算、工具和环境变量？

**回答：** 这些变量都能显著影响结果；若同时变化，就无法判断提升来自 Agent 设计还是更多计算、不同工具或环境差异。公平比较应固定关键变量，并完整记录无法固定的因素。

### 8. 如何处理模型随机性和任务环境不稳定带来的方差？

**回答：** 对任务进行多次独立运行，固定可控配置，记录模型版本、随机参数和环境快照，并报告均值、分布或置信区间。还要分别标注环境失败和 Agent 失败，避免基础设施波动污染结论。

### 9. LLM-as-a-Judge 有哪些优点和风险？

**回答：** 优点是能够低成本评估开放文本、遵循复杂 Rubric 并扩展到大量样本；风险包括位置、长度、措辞、自我偏好和知识错误。它适合作为规模化近似评估，但关键结论应由人工抽检或客观验证器校准。

### 10. 如何校准 LLM Judge，降低位置偏差、长度偏差和自我偏好？

**回答：** 使用明确 Rubric 和参考样例，随机交换候选顺序，隐藏模型身份，限制无关长度影响，并与人工标注计算一致性。必要时使用多个 Judge 或重复评审，但不能把简单多数票当作绝对真值。

### 11. 什么是消融实验？它能回答什么问题？

**回答：** 消融实验是在其他条件尽量不变时移除、替换或关闭某个组件，观察指标变化。它能估计组件对特定配置和任务集的边际贡献，但不能自动证明所有场景下的因果效果。

### 12. 为什么成功率提升不一定代表系统整体更好？

**回答：** 提升可能以更高成本、延迟、风险、方差或人工介入为代价，也可能只对特定数据分布有效。应联合报告质量、资源消耗、安全指标和失败严重度。

### 13. 如何同时衡量质量、延迟、Token、成本和人工介入率？

**回答：** 为每次运行记录统一指标，并按任务类型汇总成功率、端到端延迟分位数、输入输出 Token、货币成本和人工介入次数。比较版本时使用多目标约束或帕累托前沿，而不是把所有指标随意合成单一分数。

### 14. Trace 至少应该记录哪些关键事件？

**回答：** 至少记录任务与运行 ID、模型请求和响应元数据、状态转换、工具调用及结果、错误、重试、预算变化、人工审批和最终验证结果。敏感内容应脱敏或仅保存引用，同时保留父子 Span 和时间信息。

### 15. 如何通过 Trace 区分模型错误、工具错误、编排错误和环境错误？

**回答：** 查看模型当时可见输入和决策、工具请求与实际返回、运行时状态转换以及外部服务状态。建立稳定错误码和因果链后，才能判断是错误决策、工具实现失败、控制流缺陷还是环境不可用。

### 16. 如何构建可复现的 Agent Benchmark？

**回答：** 固定任务版本、模型标识、配置、预算、工具权限、容器镜像、依赖和评分器，隔离每次运行并保存完整产物与 Trace。对非确定性部分进行多次运行，并提供一条命令可重建环境和重新评分。

## 8. 安全、可靠性与生产工程

### 1. 什么是 Prompt Injection？它与 Jailbreak 有什么区别？

**回答：** Prompt Injection 是不可信输入试图改变应用原有指令或诱导模型误用工具；Jailbreak 通常指绕过模型自身的安全策略。二者可能重叠，但 Agent 场景更关注注入导致的数据访问和外部操作风险。

### 2. 直接 Prompt Injection 和间接 Prompt Injection 有什么区别？

**回答：** 直接注入来自用户明确输入；间接注入藏在网页、邮件、文档、工具结果等 Agent 读取的外部内容中。间接注入更隐蔽，因此所有外部内容都应作为低信任数据处理。

### 3. 为什么工具返回内容和检索文档都不能被默认信任？

**回答：** 它们可能包含错误、过期、恶意或越权内容，也可能夹带针对模型的指令。系统应保留来源与信任等级，隔离数据和控制指令，并在执行副作用操作前重新做权限和业务校验。

### 4. 如何防止模型泄露 System Prompt、密钥和用户隐私？

**回答：** 不把密钥放进模型上下文，按租户隔离数据，对输入输出和 Trace 做最小化与脱敏，并在工具层实施访问控制。System Prompt 不能作为秘密保护机制，真正的机密必须保存在模型不可直接读取的执行环境中。

### 5. 最小权限原则如何应用到 Agent 工具系统？

**回答：** 每个工具只获得完成当前任务所需的资源、动作、时间和数据范围，默认拒绝其余访问。权限应绑定用户和任务，短期授权，到期撤销，并对读、写、执行和外发分别控制。

### 6. 沙箱能够隔离哪些风险，不能隔离哪些风险？

**回答：** 沙箱可限制进程、文件、网络、系统调用和资源消耗，降低恶意代码影响宿主机的风险。它不能判断业务操作是否合法，也不能阻止 Agent 使用已授权 API 泄露数据，因此仍需要身份、策略和审批控制。

### 7. 哪些 Agent 操作必须经过 Human-in-the-loop？

**回答：** 高金额交易、不可逆删除、对外发布、权限变更、敏感数据导出以及法律或人身安全相关决策通常需要人工确认。是否审批应由影响范围、可逆性、置信度和组织政策共同决定。

### 8. 如何为高风险操作设计确认、审批和审计机制？

**回答：** 执行前展示具体对象、参数、影响和回滚方式，审批必须绑定本次操作而不是授予模糊长期许可。执行后记录请求者、审批者、时间、参数摘要、结果和证据，并支持撤销或补偿。

### 9. 如何实现任务级的超时、取消、重试和熔断？

**回答：** 运行时维护统一截止时间和取消令牌，并向模型调用、工具和子任务传播；重试按错误类型限次退避；持续失败时熔断依赖并快速降级。取消后还要回收子进程、连接和临时资源。

### 10. 如何保证有副作用操作的幂等性和一致性？

**回答：** 使用幂等键、唯一约束、条件写入、事务或操作日志，使重复请求不会重复产生效果。跨系统操作无法使用单一事务时，应设计状态机、补偿动作和人工处理队列。

### 11. 如何处理模型 API 的限流、超时和供应商故障？

**回答：** 实施客户端限速、带抖动的指数退避、截止时间、熔断和请求队列，并区分可重试与永久错误。切换供应商前要检查模型能力、工具协议和数据合规是否兼容，不能只替换 URL。

### 12. Agent 服务如何进行并发控制和背压？

**回答：** 按租户和资源设置并发上限，用有界队列、信号量和优先级调度控制模型与工具调用。下游过载时应拒绝、排队、降级或取消低优先任务，而不是无限积压请求。

### 13. 如何降低 Agent 的端到端延迟？

**回答：** 减少不必要模型轮次，缩短上下文，并行执行无依赖工具，使用更快模型处理简单步骤，缓存稳定前缀和结果。优化前应从 Trace 分解模型、工具、排队和编排耗时，避免只优化非瓶颈部分。

### 14. 如何控制单任务和单用户的 Token 成本？

**回答：** 设置输入、输出、轮次、子 Agent 和总金额预算，调用前预估、执行中累计、接近上限时压缩或降级。还应按用户和租户设置配额、告警和硬上限，并把重试纳入同一预算。

### 15. 哪些内容适合缓存？缓存会引入哪些一致性和隐私问题？

**回答：** 稳定系统前缀、工具定义、公开检索结果和确定性计算适合缓存。用户数据、权限相关结果和动态资源必须使用正确的租户、版本和权限作为缓存键，并设置失效策略，防止陈旧结果和跨用户泄露。

### 16. 如何设计 Agent 的降级策略？

**回答：** 预先定义能力等级，例如从多 Agent 降为单 Agent、从高成本模型降为轻量模型、从自动执行降为只给建议，或转人工处理。降级必须保持安全约束，并明确告诉调用方哪些能力或质量发生变化。

### 17. 如何进行 Agent 配置、Prompt、工具和模型的版本管理？

**回答：** 为每次运行记录不可变版本标识，将 Prompt、工具 Schema、策略、模型和评测配置纳入发布流程。变更通过离线回归、灰度和可回滚部署发布，避免无法解释线上行为来自哪个组合。

### 18. Agent 上线前应该设置哪些质量门槛和安全门槛？

**回答：** 质量门槛包括目标任务成功率、关键回归、延迟、成本和稳定性；安全门槛包括越权、注入、数据泄露、高风险操作确认和审计完整性。高严重度安全失败应作为阻断项，而不能被平均成功率掩盖。

## 9. Agent Skills 与能力封装

### 1. Agent Skill 是什么？它解决了什么问题？

**回答：** Agent Skill 是对某类任务所需知识、步骤、工具使用规则和资源的可复用能力封装。它让通用 Agent 在需要时按统一方法完成专业任务，减少重复提示、行为漂移和项目间复制。

### 2. Skill 与 Prompt、Tool、Workflow、Plugin 和 Sub-agent 分别有什么区别？

**回答：** Prompt 是给模型的指令；Tool 是可执行动作；Workflow 是确定性的控制结构；Plugin 是能力的安装和分发载体；Sub-agent 是拥有独立上下文和执行循环的工作单元。Skill 位于这些概念之上，描述“如何完成一类任务”，并可组合 Prompt、工具、脚本、资源和流程。

### 3. 为什么不能把一段很长的 System Prompt 直接视为 Skill？

**回答：** 长 Prompt 缺少独立的名称、触发条件、输入输出契约、依赖、版本和评测边界，也会永久占用上下文。Skill 应可被发现、按需加载、单独测试和治理，而不是把所有知识堆进全局提示。

### 4. 一个完整的 Skill 应该包含哪些组成部分？

**回答：** 通常包括名称与描述、适用边界、输入输出、操作步骤、完成条件、工具与环境依赖，以及必要的模板、示例、脚本和资源。生产级 Skill 还应声明权限、安全约束、版本、测试和维护者。

### 5. Skill 的输入、输出、前置条件和完成条件应该如何定义？

**回答：** 尽量使用结构化、可校验的契约，明确必填字段、类型、资源引用和允许范围。前置条件描述执行前必须成立的环境与权限，完成条件则应能由测试、文件、状态或评分器独立验证。

### 6. Skill 应该封装领域知识、操作流程，还是工具使用方法？

**回答：** 三者都可以封装，但必须围绕一个明确任务目标组织。领域知识解释判断依据，流程规定执行顺序，工具说明负责落地；若只是一条简单 API 调用规则，更适合放在工具描述中。

### 7. 什么情况下应该创建 Skill，什么情况下普通 Prompt 或工具就足够？

**回答：** 当一类任务反复出现，包含多步决策、固定约束、专用资源或需要独立测试时，适合创建 Skill。一次性说明用 Prompt 即可，单一确定性动作应直接做成 Tool。

### 8. Skill 的粒度应该如何划分？过大或过小分别有什么问题？

**回答：** 合适粒度应对应一个可独立描述、执行和验收的用户目标。过大会包含过多分支和依赖，难以触发和测试；过小会造成选择次数增加、组合复杂和上下文碎片化。

### 9. Skill 应该由模型自主选择，还是由程序显式指定？

**回答：** 开放任务可让模型基于元数据选择，流程确定或高风险场景应由程序指定或限制候选集合。常见方案是程序先按权限和场景过滤，再让模型在小范围内选择。

### 10. Agent 如何发现当前环境中有哪些可用 Skills？

**回答：** 运行时从受信任的注册表或目录加载 Skill 元数据，按权限、环境、依赖和任务相关性形成候选列表。模型通常先看到精简的名称和描述，选择后再读取完整说明。

### 11. Skill 的名称和描述为什么会影响模型的选择准确率？

**回答：** 模型往往依靠名称和描述完成第一阶段语义匹配；名称含糊或多个描述重叠会造成误选。描述应明确解决什么问题、何时使用和何时不要使用，而不是只写宽泛能力。

### 12. 如何设计 Skill 的触发条件，避免误触发和漏触发？

**回答：** 同时定义正向适用条件、反向排除条件、所需输入和典型示例，并减少 Skills 之间的语义重叠。通过真实任务集统计选择的 Precision、Recall 和混淆矩阵，再迭代名称与描述。

### 13. 多个 Skills 都可能适用时，Agent 应该如何选择？

**回答：** 先按权限、依赖和前置条件过滤，再比较任务匹配度、专用程度、成本和风险。若多个 Skill 是顺序关系，应生成组合计划；若互斥且无法确定，应请求澄清而不是随机选择。

### 14. 如何处理 Skill 之间的优先级、冲突和覆盖关系？

**回答：** 使用显式作用域、优先级和兼容性声明，并让系统级策略始终高于 Skill 指令。发生冲突时应由确定性规则拒绝或选择，而不是把相互矛盾的完整内容交给模型自行猜测。

### 15. 什么是渐进式披露？为什么不应该一次性把所有 Skill 内容放入上下文？

**回答：** 渐进式披露是先提供少量元数据，只有 Skill 被选中或执行到特定步骤时才加载完整说明和资源。这样可以降低 Token、减少无关指令干扰，并缩小敏感信息暴露范围。

### 16. Skill 的元数据与完整操作说明应该分别在什么时候加载？

**回答：** 启动或路由阶段只加载名称、摘要、触发边界、风险和依赖等元数据；确认选中后再加载完整步骤、模板和示例。大型资源应继续按需读取，而不是随说明一次全部注入。

### 17. Skill 执行过程中需要哪些状态？这些状态应该保存在哪里？

**回答：** 通常需要输入快照、步骤进度、已验证事实、产物引用、错误、剩余预算和审批记录。状态应由 Agent Runtime 或任务存储管理，Skill 定义本身应保持只读和可版本化。

### 18. Skill 如何声明自己依赖的工具、模型能力、运行环境和外部服务？

**回答：** 使用机器可读元数据声明工具名称与版本、所需模型能力、系统依赖、环境变量、网络访问和外部服务。加载和执行前由运行时检查，不能只在自然语言步骤中隐藏依赖。

### 19. Skill 依赖的工具不存在、权限不足或执行失败时应该如何降级？

**回答：** 执行前发现依赖缺失应拒绝启用或选择兼容 Skill；运行中失败则按错误类型重试、切换只读或人工模式，或返回部分结果。降级不能绕过原有权限和安全要求。

### 20. Skill 是否应该直接执行操作，还是只指导 Agent 调用工具？

**回答：** Skill 可以包含受控脚本或调用流程，但所有真实操作仍应经过宿主运行时和工具权限层。Skill 不应获得绕过审计、确认和沙箱的隐藏执行通道。

### 21. 一个 Skill 可以调用另一个 Skill 吗？如何防止递归调用和循环依赖？

**回答：** 可以组合调用，但应记录调用栈和依赖图，并设置最大深度、预算与重复调用检测。发布前做静态循环检查，运行时发现相同调用签名重复出现则终止或重新规划。

### 22. 如何组合多个 Skills 完成一个复杂任务？

**回答：** 先把目标分解为有明确输入输出的子任务，再根据依赖关系形成 DAG 或受控 Workflow，并通过结构化产物传递结果。组合层负责顺序、并行、错误传播和最终验收，单个 Skill 不应了解所有全局细节。

### 23. Skill 与确定性 Workflow 应该如何配合？

**回答：** Workflow 管理稳定的阶段、分支、审批和失败处理，Skill 在需要语义判断或专业操作的节点中执行。也可以由 Skill 调用小型确定性流程，但关键控制边界应由代码而不是模型维持。

### 24. Skill 与 Memory 如何配合？哪些信息属于 Skill，哪些属于长期记忆？

**回答：** Skill 保存跨用户稳定的“如何做”，Memory 保存某个用户或任务形成的事实、偏好和历史经验。Skill 可以按权限读取 Memory 作为输入，但不应把动态个人数据固化进共享 Skill。

### 25. Skill 与 RAG 的区别是什么？Skill 是否可以包含检索步骤？

**回答：** Skill 是任务能力和执行方法，RAG 是获取外部知识的机制。Skill 可以规定何时检索、查询什么来源、如何重排和验证，但检索到的内容仍是运行时数据，不属于 Skill 定义本身。

### 26. Skill 如何支持不同模型和不同 Provider？

**回答：** 使用供应商中立的输入输出、工具和事件协议，把 Provider 特有格式留在适配层。若 Skill 确实依赖视觉、长上下文或严格结构化输出等能力，应显式声明并提供兼容检查或替代路径。

### 27. 如何避免 Skill 依赖某个模型的特殊提示词习惯？

**回答：** 把关键约束做成结构化契约和程序校验，减少依赖特定措辞、隐藏推理格式和脆弱示例。用多个目标模型做回归测试，并将不可移植能力记录为显式依赖。

### 28. Skill 中的示例、模板和脚本各自适合解决什么问题？

**回答：** 示例用于校准模型对任务和输出的理解；模板用于稳定重复产物的结构；脚本用于确定性计算、转换和验证。能由脚本可靠完成的步骤不应完全交给模型自由生成。

### 29. 如何保证 Skill 中的脚本、命令和资源路径可移植？

**回答：** 使用相对 Skill 根目录的路径、声明运行时和依赖版本，避免硬编码用户目录与机器配置。通过标准入口解析资源，并在干净环境或容器中执行安装和烟雾测试。

### 30. 如何测试一个 Skill，而不依赖真实用户和完整生产环境？

**回答：** 使用固定输入、Fake Model、模拟工具和临时文件系统构建最小执行环境，验证选择、参数、状态和产物。对外部服务使用契约测试或录制的脱敏响应，只保留少量受控端到端测试。

### 31. Skill 的单元测试、集成测试和端到端评测分别应该验证什么？

**回答：** 单元测试验证纯逻辑、模板和校验器；集成测试验证 Skill 与工具、运行时和依赖的接口；端到端评测验证真实模型在代表性任务上的成功率、成本和安全行为。

### 32. 如何衡量 Skill 的触发准确率、任务成功率和成本收益？

**回答：** 用带“应触发或不应触发”标签的数据集计算选择 Precision 和 Recall，再统计启用后的任务成功率、Token、延迟与人工介入率。与无 Skill 或旧版本基线比较，避免只报告成功案例。

### 33. 如何判断任务失败来自 Skill、模型、工具还是运行环境？

**回答：** Trace 应记录 Skill 版本、选择原因、加载内容、模型输入输出、工具请求结果和环境错误。通过重放与分层测试判断：固定模型替换工具、固定工具替换模型，逐步定位最先偏离预期的边界。

### 34. Skill 更新后如何避免已有任务能力发生回归？

**回答：** 维护覆盖典型、边界和对抗输入的回归集，比较新旧版本的触发、成功率、成本与安全指标。使用灰度发布和版本固定，失败时能够立即回滚到已验证版本。

### 35. 如何对 Skill 做版本管理、兼容性管理和变更记录？

**回答：** 为 Skill 发布不可变版本，记录输入输出契约、依赖和行为变化；破坏性变更提升主版本，兼容增强和修复分别提升次版本或补丁版本。任务 Trace 应保存实际使用的精确版本。

### 36. 多个团队共享 Skill 时，如何进行发布、发现、复用和废弃治理？

**回答：** 建立带所有者、审核、版本、权限和质量指标的 Skill Registry，并提供检索与依赖解析。废弃时先标记替代版本和截止时间，分析使用方，保留迁移期，最后阻止新引用。

### 37. 第三方 Skill 可能带来哪些供应链和 Prompt Injection 风险？

**回答：** 第三方 Skill 可能包含恶意指令、脚本、依赖、外部下载或过度权限，也可能在更新后改变行为。应固定版本和完整性摘要，审核来源与内容，在隔离环境运行，并默认不给网络、密钥和写权限。

### 38. 如何限制 Skill 可以访问的文件、网络、工具和敏感数据？

**回答：** 通过宿主运行时的能力授权和沙箱实施允许列表，按任务挂载最小文件范围、网络域名和工具集合。Skill 的文字声明只能表达需求，真正的限制必须由执行层强制。

### 39. Skill 中的外部内容为什么也应该被视为不可信输入？

**回答：** 模板、样例、下载资源和检索结果都可能被篡改或包含注入指令。加载时应验证来源与完整性，区分数据和指令，并禁止外部内容自动提升权限或改变系统规则。

### 40. 如何对高风险 Skill 增加权限声明、人工确认和审计记录？

**回答：** 在元数据中声明具体权限、风险等级和副作用，启用前由策略引擎过滤，执行关键步骤前展示精确参数供人工批准。审计记录应包含 Skill 及版本、调用链、审批、工具动作、结果和失败信息。

### 41. 用户指令、系统规则和 Skill 指令发生冲突时，优先级如何处理？

**回答：** 系统和平台安全规则优先，其次是应用开发者规则，再到用户目标和 Skill 内部说明；Skill 不能提升自己的权限或覆盖上层约束。无法兼容时应拒绝冲突步骤并说明可执行边界。

### 42. Skill 是否应该允许动态生成或自我修改？这样做有什么风险？

**回答：** 可以让 Agent 生成候选 Skill，但不应未经审核直接覆盖正在使用的受信任版本。风险包括错误固化、权限扩大、提示注入持久化、不可复现和供应链污染，因此应经过隔离、测试、审查、签名和版本化发布。

### 43. 如何设计可观测性，记录 Skill 的选择、加载、执行和退出过程？

**回答：** 为 Skill 调用建立独立 Span，记录候选集合、选择理由摘要、版本、加载资源、输入输出引用、工具调用、预算、错误和退出原因。敏感正文应脱敏或保存安全引用，以支持回放和归因分析。

### 44. 如果 Skill 数量增长到数百或数千个，如何保证发现效率和选择质量？

**回答：** 先按权限、环境和依赖做确定性过滤，再用分类、关键词与语义检索召回小规模候选，必要时通过 Reranker 或分层 Router 选择。持续用真实查询评估误触发和漏触发，并治理重复、低质量和过期 Skills。
